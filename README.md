# TaskPlan Pro (OMG) — движок продукта

## 1. Что это

OMG ведёт продукт от намерения до скомпилированного плана работ. Один конвейер стадий (`src/pipeline/contracts.ts`): `discovery → concept → operation-map → specification → features → om-g2 → compilation → execution`. Первые пять — исследовательские: на каждой движок задаёт вопросы по требованиям стадии, факты подтверждаются источниками, решения записываются как решения, принятая стадия становится входом следующей. Операционная карта — один граф четырёх уровней (`src/graph/model.ts`: product 0, block 1, operation 2, work 3), который уточняется фазами `R0 → L1 → R1 → L2 → R2 → L3 → R3`; R3 проверяет реализуемость, после неё компилятор (`src/compiler/`) выводит машинный план задач, а исполнение (`src/execution/`) прогоняет задачи через адаптеры исполнителя и ревьюера до коммита.

Блок OM (`src/om/`) — проход без участия пользователя над той же картой. Он собирает входной контракт из принятых стадий (M1), замыкает горизонт по зависимостям (M2), взвешивает и выстраивает блоки в очередь (M3), выводит операции из привязок (M4), ищет пробелы валидатором и проверяет их выводимость (M5, M6), выводит атомарные работы (M7), проверяет реализуемость горизонта (M8) и передаёт результат компилятору (M9). Что нельзя вывести кодом, спрашивается у модели: MC1 — исследование невыводимого пробела, MC2 — проектное решение по операциям и работам; ответы проходят ворота (G1 вход, G2 горизонт, G3 слой, G4/G4b пробелы и готовность ответов, G5 атомарность, G6 реализуемость, G7 повтор, G8 вызов модели). Каждая попытка, вызов и отказ записываются; проход заканчивается конечным исходом, а не ожиданием человека.

## 3. Запуск

CLI (`src/cli.ts`): `npm start -- <команда> [база] [каталог снимков]`; база по умолчанию `.omg/state.sqlite`, каталог снимков `.omg/backups`.

| команда CLI | что делает |
|---|---|
| `init`, `inspect` | открыть базу (при отсутствии — создать и мигрировать схему) и напечатать её `databaseId` и список текущих записей; в коде обе команды делают одно и то же |
| `backup` | снимок базы в каталог снимков (`Store.snapshot`) |
| `restore` | восстановление базы из каталога снимков (`restoreSnapshot`) |
| `command` | читает одну команду продукта в JSON из stdin, печатает один JSON-ответ |
| `serve [база] [порт]` | локальный HTTP-сервер и UI; порт по умолчанию 4318 |

Пример одной команды:

```bash
printf '%s' '{"type":"create-project","project":"demo","title":"Демо"}' | npm start -- command .omg/state.sqlite
printf '%s' '{"type":"project","project":"demo"}' | npm start -- command .omg/state.sqlite
```

Ответы различаются по команде: `create-project` возвращает созданную запись `{"id":"project:demo","kind":"project","revision":1,"hash":"…","value":{"id":"demo","title":"Демо"}}`, `project` — проекцию проекта (объект с полями `project`, `stages`, `graph`, `questions`, `sources`, … — то, что показывает UI). Команды блока OM (`om-*`) отвечают результатом единицы в stdout с кодом выхода 0: проверять поле `ok` — при `{"ok":false,"refusal":{"code":"…","message":"…","at":{…},"route":"…"}}` это типизированный отказ (например, `om-continue` без начатого прохода даёт `record_missing`), при `{"ok":true,"value":{…}}` читать результат соответствующей команды; для `om-start` и `om-continue` отдельно разбирать `value.end` (`complete | unable | waiting | stopped | busy`), у `om-state` результат `{run, control}`, у `om-stop` — состояние управления, у `om-spend` — отчёт расхода. Только исключение — ошибка команды или движка (`src/cli.ts:32–34`) — печатается в stderr как `{"error":"<код>","message":"…"}` с кодом выхода 1.

Сквозной путь одной стадии командами (так его проходит `test/product.test.ts`): создать проект, дать источник, подготовить исследование стадии, ответить на вопросы, собрать артефакт стадии из черновика, принять стадию — и так для каждой из пяти исследовательских стадий; карта строится из принятой концепции (`build-map`), уточняется фазами, после R3 компилируется план.

```bash
cmd() { printf '%s' "$1" | npm start -- command .omg/state.sqlite; }
cmd '{"type":"create-project","project":"demo","title":"Демо"}'
cmd '{"type":"source-document","project":"demo","id":"brief","text":"Краткое описание продукта","media":"text/plain","expected":0}'
cmd '{"type":"prepare-stage","project":"demo","stage":"discovery"}'        # ответ: черновик с id вопросов
cmd '{"type":"answer-decision","question":"<id вопроса>","expected":1,"value":"Решение"}'
cmd '{"type":"answer-fact","question":"<id вопроса>","expected":1,"source":{"id":"source:demo:brief","revision":1,"hash":"<hash>"},"selector":{"kind":"text-range","start":0,"end":10}}'
cmd '{"type":"draft-stage","project":"demo","stage":"discovery","draftId":"<id черновика>","expected":0}'
cmd '{"type":"accept-stage","project":"demo","stage":"discovery","expected":1}'
```

Ссылка на запись всегда точная — `{id, revision, hash}`; команда с устаревшей ревизией или чужим хэшем отвергается.

UI: `npm run dev` (или `npm start -- serve`) печатает ссылку вида `OMG: http://127.0.0.1:4318/#token=<64 hex>`. Её нужно открыть в браузере: токен из фрагмента ссылки UI кладёт в `sessionStorage` и шлёт заголовком `X-OMG-Token` (`ui/app.tsx`). Сервер (`src/server.ts`) слушает только `127.0.0.1`; на каждый запрос он проверяет заголовок `Host` с портом (`127.0.0.1:<порт>` или `localhost:<порт>`, иначе `host_forbidden`) и, если задан `Origin`, его совпадение с адресом (`origin_forbidden`); страница `GET /`, `/app.js` и `/app.css` отдаются без токена, все `/api/*` требуют верный токен (`session_forbidden`). Разделы UI: Обзор, Карта, Исследования, Источники, Настройки, Чат; слева — стадии конвейера. API сервера: `GET /api/projects`, `GET /api/project?id=…` (проекция, `engine.projection`), `POST /api/command` (та же команда, что в CLI), `POST /api/chat`, `GET /api/directories`, `GET /api/providers`.

## 5. Проход OM

`om-start` (`src/om/run-driver.ts`) записывает первый вход B1 проекта, намерение и машинные основания прохода (`src/om/run-bases.ts`), затем двигает проход шагами `advanceRun` (`src/om/run.ts`): шаг — одно выбранное действие (открытие серии, пакет вопроса модели, вызов `cycle`, оценка ответа, принятие слоя, подтверждение достижений, закрытие попытки, пересборка оснований, …); выбор шага сохраняется в записи прохода, затем шаг исполняется и его завершение записывается отдельно, а само действие может сохранить несколько записей — `cycle` запускает производителя вызова модели и пишет вызов, ответ и продукты. Исходы драйвера: `complete` (M8 и M9 пройдены, план скомпилирован), `unable` (список причин — например, вопросы, на которые нет производителя ответа), `waiting` (ожидание, которое повтор не меняет), `stopped`, `busy`. Состояние — `om-state`: фаза `ready | step | waiting | complete | unable`, сохранённый шаг, последний отказ.

Единицы блока по принятой карте (`PREPARATIONS/OM-DESIGN/om-design.json`):

| единица | роль | код |
|---|---|---|
| M1 · входной контракт OM | собрать вход B1 из принятых стадий и инвентаря | `src/om/input.ts` |
| M2 · горизонт | замкнуть горизонт по зависимостям и намерению запуска | `src/om/horizon.ts` |
| M3 · очередь блоков | вес и очерёдность блоков (запись `block-weight`) | `src/om/queue.ts` |
| M4 · каркас операций | вывести операции из структурированных привязок | `src/om/frame-obligations.ts`, `frame-proposals.ts` |
| M5 · пробелы | найти пробелы валидатором, адресовать вопросы | `src/om/gaps.ts`, `addressing.ts` |
| M6 · маршруты | проверить выводимость пробела, собрать партии вопросов | `src/om/routes.ts` |
| M7 · работы и соседи | вывести атомарные работы и внешние входы | `src/om/works-frame.ts`, `atomic-gate.ts` |
| M8 · реализуемость | проверить реализуемость горизонта в среде | `src/om/feasibility.ts` |
| M9 · передача компилятору | отдать принятый горизонт компилятору | `src/om/obligations.ts`, `src/compiler/` |
| MC1 · исследование пробела | вопрос модели о невыводимом факте | `src/om/question-packet.ts`, `model-call.ts` |
| MC2 · проектное решение | раскрытие узла: операции и работы | `src/om/question-packet.ts`, `frame-candidate.ts` |
| G4b · готовность ответов | какие партии вопросов обслуживаются и чем | `src/om/answers-gate.ts` |
| G7 · повтор | закрытие попытки с исходом, остановка серии | `src/om/repeat-gate.ts`, `series.ts` |
| G8 · вызов модели | допуск отправки, учёт расхода | `src/om/model-call.ts`, `call-record.ts` |

Ворота повтора G7 закрывают каждую попытку с её исходом; три завершённые попытки без продвижения останавливают серию, остановку разбирает анализ (A6), а не человек. Повтор после перезапуска процесса читает сохранённую историю и не платит дважды: вызов модели, уже отправленный, не отправляется заново.

**Настоящие вызовы модели стоят денег.** Адаптер `src/adapters/codex-stdio.ts` запускает внешний процесс модели; `configure` задаёт команды исполнителя и ревьюера, `configure-om-dispatch` — протокол. Инструкция оператора для живого прохода — `PREPARATIONS/OM-LIVE/RUNBOOK.md` (ветка подготовки, см. раздел 8): точка запуска, проверки среды, запуск в отдельном процессе, наблюдение через `om-state`/`om-spend` не чаще раза в 5 с, остановка. Для сухих проверок есть скриптовый адаптер `test/om-adapter-fixture.mjs` — он отдаёт заранее записанные ответы и ничего не отправляет.

Хранилище. Таблицы `revisions` (запись = `entity_id`, `revision`, `kind`, `body` в каноническом JSON, `sha256`), `heads` (текущая ревизия каждой записи), `events`, `identity`, `migrations`, `snapshot_stamp`. Ревизии неизменяемы (триггеры запрещают UPDATE/DELETE); новое состояние — новая ревизия. Запись `Store.writeMany(inputs, guards)` — одна транзакция: у каждого входа ожидаемая ревизия (`expected`), у транзакции охраны — точные ссылки `{id, revision, hash}` или `{id, absent: true}`; изменение охраняемой записи между проверкой и записью — отказ (`input_stale`), не тихая перезапись. Чтение — `get(id, revision?)`, `list(kind?)`, `history(id)`; `changeStamp()` и `identities()` отвечают за неизменность прочитанного без декодирования тел. Снимки `backup`/`restore` — два чередующихся слота A/B (`src/storage/snapshots.ts`); `restore` берёт новейший исправный слот и требует НОВОГО пути базы: по нему не должно быть ни файла, ни `-wal`, ни `-shm` (`restore_target_exists`), каталог создаётся сам.

Принципы кода.
- **Вывести → записать.** Производная запись сначала выводится из точных источников (`prepare*`), потом записывается под охранами (`write*`); потребитель получает копию, не делящую объектов с источником.
- **Чтение не слабее записи.** Исторический читатель строит запись заново тем же общим выводом, что и производитель, и сравнивает: форма, хэш или наличие поля доказательством не считаются. Общий механизм исторических чтений — `withHistoricalReads`/`historicalRead` в `src/om/input.ts`: доказательства одной операции разделяются, их зависимости проверяются по штампам хранилища.
- **Эры записей.** Записи читаются правилами своей эры: первый вход B1 проекта — граница эры OM (`#omProject` в `src/product/engine.ts`), у серий исправлений своя неизменяемая метка эры (`om-series-era` в `src/om/series.ts`); новые проверки не перепроверяют прошлое.
- **Типизированные отказы.** Движок бросает `EngineError(code, message, details)` (`src/errors.ts`); единицы OM возвращают `OmResult` — `{ ok: true, value }` либо `{ ok: false, refusal }` (`src/om/refusal.ts`). Отсутствие обязательного поля или источника — отказ с адресом, не значение по умолчанию.

```json
{ "ok": false, "refusal": { "code": "record_missing", "message": "OM provenance requires the exact first B1 input",
    "at": { "unit": "product", "target": "om-input:demo", "field": "revision" }, "route": "producer" } }
```

Маршрут отказа (`route`) — кому он возвращается: производителю данных, в пробел, владельцу или на пересмотр готовности; сам отказ ничего не переключает. Охраны транзакции записи выглядят так: `[{ "id": "graph:demo", "revision": 3, "hash": "<sha256>" }, { "id": "om-input:demo", "absent": true }]` — первая требует точной ревизии, вторая — отсутствия записи на момент записи.

`scripts/check-backend.mjs` компилирует проект и запускает каждый набор отдельным процессом; `npm test` запускает всё, включая UI-набор на Playwright. Тесты не ходят в сеть и не вызывают настоящие модели: среда в фикстурах указывает на скриптовый адаптер.

Кольцо импортов (`test/import-ring.test.ts`) — храповик: по AST TypeScript строятся граф загрузочных импортов и полный граф (с типовыми рёбрами), размер крупнейшей сильно связной компоненты не может расти (пределы 84 и 133 файла на момент введения); уменьшение — подсказка снизить предел.
