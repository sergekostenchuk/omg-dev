# OMG: проект решения проблемы расхода токенов

Статус: проект решения для обсуждения. Реализация и исследовательские прогоны остаются на паузе по указанию владельца.

## 1. Цель и основания

Сократить суммарный расход токенов на получение правильного продуктового результата на всех стадиях OMG. Сохранить полные сведения о проекте, происхождение решений, существенные зависимости, границы ответственности и критерии результата. Разгрузить пользователя и обеспечить автоматический переход от исследованного продукта к машинному плану атомарных задач.

Приоритет — уменьшение самих запросов, ответов и числа обращений. Более дешёвые модели дополняют это сокращение. Кэширование, специальные тарифы и другие возможности провайдеров применяются после этого и не являются условием работы решения.

Основания:

- [OMG-ENRICHED-PIPELINE-CORRECTIONS.md](OMG-ENRICHED-PIPELINE-CORRECTIONS.md) — требуемое поведение общего конвейера.
- [OMG-TOKEN-CONTEXT-PROBLEME.MD](OMG-TOKEN-CONTEXT-PROBLEME.MD) — результаты аудита, предложения Codex и Fable, описание идеи h-proto.
- Уточнение владельца: независимость от поставщика моделей, отдельные методы для каждой стадии, настраиваемое назначение чтения быстрым и дешёвым моделям.

Документ описывает функции продукта. Он не добавляет процедуры разработки, ручной TASK-PLAN, новые инженерные ворота или подтверждение владельца для каждой обычной задачи. HTML/UI этим документом не реализуются.

## 2. Подтверждённая проблема

По сохранённому проходу OMG до паузы:

| Стадия | Попытки вызова автора | Средний / максимальный контекст запроса | Наибольший сохранённый ответ автора |
|---|---:|---:|---:|
| Первоначальное Discovery | 14 | 101 / 164 тыс. символов | 40 тыс. символов |
| Концепция | 7 | 104 / 161 тыс. | 25 тыс. |
| Первоначальная OM | 16 | 193 / 280 тыс. | 106 тыс. |
| ТЗ | 5 | 250 / 287 тыс. | 51 тыс. |
| Подготовка фич | 5 | 177 / 200 тыс. | 45 тыс. |
| R1, незавершённый | 51 | 360 / 421 тыс. | 16 тыс. |

Пять начальных стадий: 47 попыток, 7,37 млн символов контекста автора. R1 к моменту паузы: ещё 18,34 млн. Это размер сериализованного контекста перед попыткой отправки; он не доказывает фактическую доставку каждого запроса и не является счётом оплаченных токенов. Инструкции адаптера и отдельные запросы оценщика в эти суммы не включены.

Причины: полный общий пакет на каждом чтении; чрезмерное наследование предыдущих стадий; растущие поля черновика; повтор прочитанных фрагментов в истории; регенерация полного графа; крупный повторный пакет оценщику; отсутствие общего учёта токенов и бюджета всех ролей.

Незакоммиченная частичная оптимизация на одном срезе уменьшала пакет с 388 779 до 307 374 символов, приблизительно на 21%. Она не решает проблему целиком и не является доказательством экономии нового подхода.

## 3. Что означает сохранение контекста

Различаются три обязательства:

1. **Сохранность информации.** Исходные тексты, кодовые основания, ответы, наблюдения, решения и версии сохраняются полностью. Проекция для модели не заменяет оригинал.
2. **Достаточность пакета.** Для текущего решения передаются обязательные ограничения, нужные сведения и зависимости; дополнительные данные доступны по точному адресу.
3. **Качество понимания.** Содержательная полнота вывода проверяется подходящими доказательствами и оценкой. Ни полный запрос, ни короткий пакет сами по себе этого не гарантируют.

Программно можно гарантировать сохранность байтов, разрешимость ссылок и включение всех явно заданных обязательств. Нельзя заранее гарантировать, что алгоритм найдёт каждую ещё неизвестную смысловую зависимость. Поэтому discovery сохраняет противоречия и пробелы, умеет расширять область исследования и не объявляет неизвестное неприменимым.

SQLite остаётся единственным каноном состояния. Git хранит код. Читаемые файлы стадий и исследований — автоматически обновляемые проекции; A/B-снимки — резервные копии. Протокол доказательств не создаёт второй канон рядом с базой.

## 4. Общий механизм с политиками отдельных стадий

Контекст запроса собирается из четырёх частей:

- **Общий контекст продукта:** цель, пользователи и потребители, область текущей работы, существенные решения владельца, обязательные ограничения и известные сквозные противоречия. Каждое положение связано с каноническим основанием.
- **Рабочий набор:** текущий вопрос или связанная группа вопросов, необходимые факты, решения, контракты, фрагменты источников и состояния зависимостей.
- **Адресный каталог:** доступные разделы, узлы, источники и подробности с идентификаторами, версиями и кратким объяснением содержания.
- **Текущее действие:** что требуется получить, допустимая форма изменения, предмет коррекции и оставшийся бюджет.

Общий контекст не является свободным кратким пересказом всей истории. Явные запреты и обязательные ограничения сохраняют точную формулировку либо проверяемое структурированное представление. Человекочитаемые пояснения не подменяют исходные основания.

Сборщик использует зависимости требований, сценариев, данных, состояния, полномочий, производителей и потребителей. Поиск по похожим словам — дополнительный способ обнаружения материалов. Он не определяет полноту сам по себе. Фиксированное число соседей или глубина графа не служат доказательством достаточности.

В начале проекта зависимости ещё неизвестны: применяется более широкий обзор с сохранением реестра неизвестного. По мере подготовки выборки становятся точнее. Пакеты разных стадий не обязаны иметь одинаковый размер.

## 6. Чтение, рабочая память и изменения

### 6.1. Пакетное получение сведений

Движок должен поддерживать получение нескольких связанных фрагментов за одну операцию: файлов/символов, узлов и коннекторов, контрактов, полей стадий, наблюдений и доказательств. Запрос указывает цель чтения и точные версии, если они уже известны.

Список файлов, чтение байтов, поиск текста, разбор поддерживаемой структуры, вычисление хешей, разрешение ссылок и перенос готовых полей выполняются без LLM. Модель используется там, где требуется смысловой отбор, сопоставление или извлечение из неоднозначного материала.

Ответ чтения содержит результат и указание полноты: что прочитано, какая область остаётся неразобранной, какие ссылки отсутствуют. Ограниченный результат не выдаётся за полный. Продолжение чтения имеет адрес; молчаливое обрезание существенных данных запрещено.

### 6.2. Рабочий набор вместо последних восьми ходов

Прочитанный материал остаётся в активном контексте, пока нужен текущему рассуждению. Завершённый вывод может использоваться через содержательную запись с основанием; исходные фрагменты остаются доступными. Вытеснение определяется зависимостями работы, а не только возрастом сообщения.

Каждый отдельный вызов получает явный рабочий набор. Нельзя считать, что модель помнит текст, которого нет в её текущем контексте. Ссылка на источник сохраняет доступность, но сама не переносит его смысл.

Дословные повторы одного и того же значения можно заменять ссылкой на значение, которое уже присутствует в данном пакете. Отклонённые предложения, противоречия и незавершённые рассуждения не исчезают под видом дедупликации.

### 6.3. Изменения вместо полной регенерации

Ответ модели связывается с базовой версией и содержит добавляемые, изменяемые или удаляемые сущности/поля, основания и ещё не разрешённые вопросы. Движок разрешает ссылки, применяет изменение с контролем версии и собирает полный канонический результат.

Неизменившиеся уровни, тексты и идентификаторы наследуются программно. При новом исходном документе его содержание действительно нужно создать; экономия не означает заранее обрезать полезный результат. При коррекции не требуется повторно генерировать весь артефакт.

Смена базы до применения изменения даёт адресный отказ и восстановимое продолжение. Повтор не подхватывает чужую новую revision как разрешение на перезапись принятого результата.

## 7. Настраиваемый пресет маршрутизации моделей

### 7.1. Роли

| Роль | Назначение | Ограничения |
|---|---|---|
| Детерминированные инструменты | Чтение, поиск, разбор структуры, ссылки, схемы, хеши, сборка и сравнение | Не требуют модели; доступны до выбора reader |
| Reader | Смысловое извлечение из ограниченного набора источников, поиск релевантных фрагментов, сопоставление сведений | Быстрая и дешёвая подходящая модель; без права менять код, канон, полномочия или принимать стадию |
| Analyst | Продуктовые и архитектурные выводы, устранение неоднозначностей, проектирование | Получает структурированные извлечения и необходимые оригинальные фрагменты; сохраняет факты отдельно от предложений |
| Assessor | Оценка содержательной достаточности и соответствия основаниям | Независимая роль по действующей политике; точный предмет оценки и достаточные доказательства |
| Implementer / Reviewer | Реализация и независимое ревью кода | Действующие границы записи, кандидата, проверок и принятия |

Назначение reader не означает вызов LLM на каждый файл. Если скрипт может вернуть требуемые данные непосредственно, такой вызов не делается. Reader не становится обязательным посредником для каждого простого чтения.

### 7.2. Пресет как данные продукта

Пресет версионируется в SQLite и может выбираться для проекта с переопределениями по стадиям и ролям. Он определяет:

- разрешённых провайдеров, подключения и модели;
- обязательные возможности: доступные инструменты, формат ответа, поддерживаемый язык/тип источника, допустимое окно контекста;
- назначение reader, analyst, assessor и ролей исполнения;
- режим выбора: фиксированная модель, автоматический выбор из разрешённого набора, предложение основной модели с проверкой движком;
- приоритеты стоимости, задержки и пригодности; источник этих оценок и статус неизвестных значений;
- допустимые режимы усилия и скорости отдельно от идентификатора модели;
- лимиты запроса, ответа, чтения, стадии и всего прохода; общий бюджет дочерних обращений;
- допустимые повторы, резервные модели и условия эскалации;
- максимальную параллельность чтений и правила объединения запросов;
- степень принудительности маршрутизации и правила обработки неподдерживаемого адаптера.

Пример назначения пресета: `economy-research` — детерминированное извлечение первым; смысловое чтение направляется в разрешённый быстрый экономичный reader; проектирование выполняет analyst; при отсутствии пригодного reader применяется только заранее разрешённая альтернатива.

Названия GPT-5.3 Spark, Luna Fast, Sonnet Fast — примеры предпочтений владельца. Они не являются здесь подтверждёнными идентификаторами API, обещанием доступности или утверждением о сравнительной цене. Движок разрешает их в конкретные доступные модели и поддерживаемые режимы. Слово `fast` само по себе не доказывает низкую стоимость.

### 7.3. Актуальный каталог доступных моделей

Адаптер известного провайдера получает доступный каталог через предусмотренные им API, CLI или данные подключённой среды. Каталог хранит провайдера/подключение, точный ID, отображаемое имя, возможности, режимы, сведения о доступности, время получения и источник данных. Отсутствующие сведения обозначаются как неизвестные.

Публичная модель в каталоге вендора не обязательно доступна конкретному аккаунту. Доступность, тариф API, режим подписки и фактический расход квоты различаются. Они не подменяются друг другом.

Пользователь может выбрать модель из актуального списка либо разрешить автоматический выбор внутри заданных ограничений. Для иных провайдеров допускается явная конфигурация совместимого адаптера; ядро не требует наличия API OpenAI.

Реальный выбранный ID и режим фиксируются для каждой попытки. Обновление каталога может влиять на будущие назначения, но не переписывает происхождение прошлых результатов. Платные пробные генерации для обнаружения моделей автоматически не запускаются.

### 7.4. Принудительное делегирование

Маршрутизация обеспечивается движком:

1. Analyst запрашивает сведения через контролируемое действие получения доказательств, задавая вопрос, область и ожидаемый результат.
2. Движок сначала применяет подходящие детерминированные инструменты.
3. Если требуется смысловая обработка, движок выбирает reader по пресету и доступности.
4. Reader получает ограниченный пакет источников, а не весь проект и историю analyst.
5. Движок сохраняет извлечение с происхождением, проверяет ссылки и передаёт analyst результат и необходимые точные фрагменты.

Если основная модель сама предлагает исполнителя чтения, её предложение ограничено актуальным разрешённым набором. Движок валидирует и исполняет назначение. Модель не может обходить бюджет или незаметно назначать себя вместо reader.

Строгий пресет должен опираться на реально ограниченные инструменты адаптера. Одного текста «передавай чтение дешёвой модели» недостаточно. Если адаптер оставляет неподконтрольный путь самостоятельного чтения/вызова моделей, он не объявляется совместимым с принудительным режимом. Возможен явно выбранный рекомендательный режим с честно указанными ограничениями.

Прямое адресное чтение оригинала analyst допускается по условиям пресета: противоречие, неоднозначное извлечение, критичное ограничение, неразрешённый пробел. Причина и расход фиксируются. Это ограниченное расширение рабочего контекста; оно не должно приводить к автоматической загрузке всего проекта.

Пресет имеет область действия. Делегирование подготовительного чтения не запрещает основной модели понимать полученные материалы и не лишает implementer нужного исходного кода.

### 7.5. Резервные варианты и полномочия

Если выбранная модель недоступна, следующая выбирается только из разрешённых резервных вариантов с соблюдением стоимости, возможностей и области передачи данных. Молчаливого перехода к дорогой основной модели нет.

Переход между провайдерами допустим только в пределах действующих разрешений владельца на передачу данных. Разрешение отправлять приватный код одному провайдеру не означает разрешение отправлять его всем. Настройка разрешённого набора — решение пользователя; повторные вопросы на каждое штатное чтение не нужны.

Если допустимого варианта нет, сохраняется техническая пауза с причиной и возможным продолжением. Недоступность reader не превращается в вопрос пользователю по существу продукта. При исчерпании бюджетов не запускаются новые дорогие попытки.

### 7.6. Качество извлечения

Результат reader содержит наблюдения с источником/версией/селектором, точные фрагменты для существенных утверждений, противоречия, неизвестное и границы исследованного материала. Предположение помечается предположением. Уверенность reader не является доказательством.

Движок проверяет разрешимость ссылок и соответствие извлечённых буквальных значений исходнику. Содержательные обобщения оцениваются в существующем цикле подготовки связанного результата. Отдельный дорогой assessor на каждое простое чтение не вводится автоматически.

Недостоверное извлечение нельзя принять только потому, что модель дешёвая или её ответ короткий. Повтор, другой reader или адресная эскалация разрешены в рамках общего бюджета. Стоимость этих исправлений входит в оценку эффективности пресета.

## 8. Оценщик и переходы между стадиями

Assessor получает связанное предложение, обязательства, затронутые зависимости, существенные цитаты и доступ к остальным доказательствам. Он не обязан перечитывать весь проект для каждого поля, но и не ограничивается пересказом автора, лишённым проверяемых оснований.

Приёмка технически переносимых данных — работа движка. Семантическая оценка остаётся там, где нужно установить релевантность, достаточность или непротиворечивость. Проверка целостности ссылки не заменяет оценку смысла.

Переход стадии передаёт следующему потребителю адресуемый результат, необходимые значения и обязательства. Полный документ сохраняется для просмотра/экспорта, но не становится обязательным приложением ко всем последующим запросам.

Противоречие возвращается к производителю соответствующего поля. Изменение основания затрагивает зависимые будущие результаты; история сохраняется. Отсутствие сведений не закрывается переписанным статусом `ready`.

## 9. Применение идеи h-proto

Использовать h-proto как основу происхождения, связывания и повторного использования результатов внутри существующего канона OMG:

- утверждение связано с конкретными байтами, версией и селектором;
- обязательство связано с результатом, проверками, вердиктом и областью применения;
- повторное использование учитывает зависимости, среду, версии правил и условия действительности;
- изменение основания адресно делает зависимые результаты непригодными для новой работы;
- подробности доступны по ссылкам, а модели выдаётся содержательное утверждение с необходимыми основаниями.

Дополнительно различать проектное предложение/вывод модели, наблюдение и решение владельца. Пересказ или вывод reader не получает статус факта автоматически.

Хеш доказывает идентичность байтов, а не истинность утверждения. Хешовая ссылка на обязательство не доказывает время его предварительной фиксации. Для доказуемого порядка и независимости нужны доверенная регистрация исполнения и реально действующие ограничения доступа. Разные имена ролей и одинаковые байты до/после не дают такой гарантии сами по себе.

Модель не восстанавливает смысл из хеша. Экономию обеспечивают адресное получение содержания и допустимое повторное использование доказанного результата. Протокол не заменяет сборщик контекста.

in-toto/DSSE могут служить форматом подписанного экспорта при внешнем обмене. Выбор этих форматов не создаёт автоматически управление ключами и доверенную среду. Подписи и внешняя инфраструктура не являются обязательной предпосылкой первой реализации экономии токенов.

Не создавать семь новых процедур на каждое чтение. Использовать существующие события, наблюдения, решения, исполнения и результаты проверок OMG, дополняя их необходимыми связями. Уровни профилей h-proto не смешивать с L1/L2/L3 операционной карты.

## 10. Учёт расхода и бюджет

Для каждой попытки сохранять роль, стадию, цель обращения, версию пресета, точную модель/режим, основания пакета и следующие показатели:

- символы/байты сформированного запроса и полученного ответа;
- входные и выходные токены, если их сообщает адаптер/провайдер;
- cached/reasoning и иные доступные составляющие с учётом того, что они могут входить в общие суммы;
- статус измерения: данные провайдера, оценка совместимым токенизатором или неизвестно;
- длительность, причину повтора/эскалации, получение нового полезного результата;
- доступные сведения о цене или расходе квоты с источником и датой.

Отсутствующее значение не равно нулю. Символы не объявляются токенами. Передача по короткому транспортному указателю не означает, что провайдер не учитывает развёрнутую историю. Кэшированные токены не прибавляются повторно к полному input.

Бюджеты задаются конфигурацией для запроса, ответа, чтения, стадии и полного прохода. Параллельные reader разделяют общий лимит; перед запуском учитывается уже зарезервированный расход. Учитываются все дочерние вызовы и неудачные попытки, а не только analyst.

Потолок запроса не обрезает обязательный контекст. Движок выбирает связное разделение, адресную загрузку или сохраняет объяснимую паузу. Слишком мелкие пакеты, повторные чтения и многократные коррекции также считаются расходом.

Критерий выбора пресета — пригодность и суммарная стоимость правильного результата. Низкая цена одного reader-вызова не доказывает экономию всей стадии. Сокращение количества токенов и снижение денежной/квотной стоимости показываются раздельно.

## 11. Кэширование как дополнительная оптимизация

Полезные неизменные инструкции и материалы можно располагать стабильно, а изменяемую часть отделять. Применимость кэширования, поддерживаемые настройки и реальный эффект определяет адаптер и подтверждает измерение.

Движок сохраняет способность сокращать исходные токены без кэша. Кэширование не делает лишнюю информацию необходимой, не уменьшает размер полезного ответа и не заменяет проектирование стадий. Возможности OpenAI не считаются возможностями всех провайдеров.

## 12. Восстановление и совместимость

После таймаута, потери связи или остановки сохраняются принятые ответы, извлечения reader, исходные источники, незавершённое действие и его основания. Возобновление не начинает исследование заново и не повторяет завершённые чтения без содержательной причины.

Новый пресет или формат пакета фиксируется для новой попытки. Старые журналы и принятые результаты сохраняют исходные версии правил. Пригодные результаты переиспользуются после проверки применимости к текущему потребителю; смена упаковки запроса сама по себе не стирает знания.

Повтор незавершённой оценки использует сохранённый предмет этой оценки. Изменение его оснований требует адресного пересмотра, а не выдачи старого вердикта за оценку новых данных.

Разрешённые области записи и полномочия не расширяются вследствие бюджетной ошибки, недоступности reader или смены модели. Нет автоматического обхода паузы через другую роль, другой провайдер или возобновляемый фоновый запуск.

## 13. Модульные изменения в OMG

| Ответственность | Направление изменения |
|---|---|
| Контракты стадий | Зависимости полей и связанные группы исследования, формат адресных изменений |
| Сборщик контекста | Общий контекст, рабочий набор, каталог, правила отдельных стадий; без скрытого полного приложения |
| Источники и чтение | Индексы, пакетное получение, точные селекторы, явная полнота и продолжение |
| Маршрутизация ролей | Версионируемые пресеты, актуальный каталог, reader/analyst/assessor, ограниченные резервные варианты |
| Адаптеры | Доступные модели/режимы, реальные ограничения инструментов, поддерживаемые счётчики расхода |
| Исследовательский цикл | Повторное использование, адресные пробелы, контролируемая эскалация и возобновление |
| Построители карты и документов | Применение изменений к точной базе; наследование неизменившихся частей |
| Доказательства | Область применимости, происхождение, зависимости и адресное устаревание по идее h-proto |
| Учёт | Все роли и повторы, расход стадии/прохода, общий бюджет параллельных обращений |
| Настройки CLI/API | Просмотр и выбор пресета, моделей, ограничений и фактических причин маршрутизации |

Сейчас конфигурация среды содержит implementer/reviewer; этого недостаточно, чтобы объявить reader-пресет реализованным. Также недостаточно только уменьшить выдержки источников или заменить модель в одном вызове.

Это развитие модулей того же продукта. Конкретные имена моделей, пути OMG и идентификаторы его текущего прохода не встраиваются в алгоритмы.

### 13.1. Реализовывать правила только для следующей запускаемой стадии

Дополнение владельца: таблица методов не должна превращаться в «правила для правил». **Правило отбора — это работающий код с тестом, названным риском и измерением эффекта. Сейчас реализуются только R1 и L2.** Реализация начинается после снятия владельцем текущей паузы.

| Ближайшая стадия | Какой риск закрывает код | Что должен показывать результат |
|---|---|---|
| R1 | На каждое чтение повторяется большой общий пакет; при сокращении могут потеряться сквозные ограничения, факты и противоречия | Размеры и совокупные токены запросов/ответов всех ролей, число повторных чтений и коррекций; сохранённые исходники и доказательства; полнота применимых технических выводов. Пригодные принятые ответы текущего R1 не исследуются заново. |
| L2 | Модель повторно генерирует верхние уровни и весь граф; локальные изменения могут разорвать межблочные связи | Доля и объём действительно новых данных в ответе; сохранность неизменившейся L1; полнота затронутых входов, выходов, границ и потребителей; совокупный расход построения и исправлений слоя. До первого запуска L2 её экономия считается неизвестной. |

Общие модули реализуются в объёме, необходимом R1/L2: адресное и пакетное чтение, рабочий набор, применимое назначение reader, учёт и изменение точной версии графа. Не требуется заранее строить полный каталог политик для всех стадий, универсальный язык правил, отдельный проект h-proto или инфраструктуру подписанного экспорта.

Ранние стадии, уже пройденные в текущем проекте, не запускаются заново только ради внедрения оптимизации. Их будущие изменения используют соответствующие строки таблицы, когда возникает реальная работа на этих стадиях. Методы для R2/L3 и последующих стадий реализуются, когда к ним подходит проход; строка в документе сама по себе не становится задачей немедленной реализации.

Риск и результат выражаются в предметном тесте и измерении работающего механизма. Для этого не создаются дополнительные реестры, процедуры принятия или инженерные ворота. Сокращение текста одного пакета не считается успехом, если оно увеличило суммарный расход или потеряло необходимое содержание.

## 14. Продуктовые критерии результата

Реализация должна демонстрировать следующие сценарии; это критерии функций продукта, а не дополнительные процедуры разработки:

Сейчас реализуются и проверяются сценарии, применимые к R1/L2 и их общим механизмам. Остальные критерии остаются требованиями будущих стадий; весь перечень не является предварительным условием возобновления ближайшего участка.

| Сценарий | Требуемое наблюдаемое поведение |
|---|---|
| Перенос известного результата | R0, наследование идентификаторов и компиляция не вызывают модель без необходимости |
| Два различных продукта | Общие механизмы и пресеты работают без специальных ID и переделки ядра |
| Узкий вопрос с удалённой зависимостью | В пакет попадает существенное ограничение из другого блока либо обнаруживается необходимость дочитать его; результат не принимается с потерянной зависимостью |
| Раннее неопределённое Discovery | Сохраняются широкий обзор, противоречия и неизвестное; дешёвое извлечение не подменяет формирование концепции |
| Набор связанных файлов | Чтения объединяются; общий проектный пакет не повторяется на каждый файл |
| Простой запрос к данным | Работает скрипт, лишнего reader-вызова нет |
| Смысловое чтение | Движок выбирает допустимый быстрый экономичный reader; analyst получает проверяемый результат |
| Попытка обойти назначение | В принудительном режиме основная модель не запускает запрещённую роль или дорогой резервный вариант |
| Неподдерживаемый адаптер | Ограничение явно отражено; принудительность не выдаётся за реализованную |
| Недоступность модели/неизвестная цена | Нет выдуманной доступности или нулевой стоимости; работает разрешённая альтернатива либо сохраняется техническая пауза |
| Недостоверный reader | Неверный селектор, неподтверждённый факт, потерянное исключение или противоречие не становятся принятыми знаниями |
| Исправление одного узла | Модель возвращает адресное изменение; неизменившиеся уровни и история сохраняются |
| Изменение источника | Пересматриваются зависимые будущие результаты; старые доказательства не приписываются новым данным |
| Исчерпание бюджета | Сохраняется продолжение; нет скрытой обрезки контекста и запуска дорогого fallback |
| Пауза и восстановление | Работа не возобновляется без разрешения; после разрешённого продолжения пригодные сведения используются повторно |
| Полный учёт | Видны расходы reader, analyst, assessor, исполнителей, повторов и дочерних вызовов; неизвестное обозначено |
| Сравнение методов | На сопоставимых сценариях оцениваются полнота результата, потерянные зависимости, число коррекций, совокупные токены и время; улучшение только одного счётчика не объявляется победой |

Точный процент экономии пока не установлен. Корректность обещания «контекст сохранён» подтверждается сохранностью исходных данных, покрытием существенных обязательств и результатами сценариев, а не одним коротким запросом или совпадением хеша.

## 15. Граница текущего поручения

Подготовлен только проект решения. Пресет, новые адаптеры, выбор конкретных моделей, перенос текущего R1 на иной алгоритм, модельные прогоны и HTML/UI этим поручением не запускаются. Решение о продолжении принимается после обсуждения этого проекта с владельцем.
