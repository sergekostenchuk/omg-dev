### 3.2. Сначала прочитан построитель, затем найден настоящий писатель

T60 включает graph/builder.ts, но `buildL1` только строит/проверяет Graph ивозвращает его. Предметная запись находится в `GraphRepository.#write`. В engine уже видны отдельные импорты GraphRepository/buildL1, тип поля graphs ивызов `graphs.saveDerived` после построения (`cb60d84 product/engine.ts:7,14,32,231–232`). Поэтому реальное место записи доступно статически, а не требует нового смыслового предположения по названию файла.

T62 добавляет graph/repository.ts: фрагменты `[1274,4039)` и`[7060,9678)` раскрывают группы graph/binding/layers, expected revisions, guards ипроизводный слой. Это новое необходимое основание, которого в builder нет.

**Что изначально неправильно:** запрос о записи/транзакции был направлен к модулю построения данных без реализации писателя. Первоначальная подготовка должна разрешать реальный символ/тип/вызов писателя иотбирать его тело. Для данного пути связь статически определена. Полную автоматическую замкнутость для любых динамических callbacks это не доказывает.

### 3.3. Caller получен без тела соседнего callee

В T60 reader имел весь execution/worktree.ts, но доставил только ensureWorktree `[1618,3185)` — сохранение creating, вызов materializeWorktree, затем ready. Для поведения повтора этого недостаточно.

T62 запрашивает тот же source `[0,1618)` идоставляет `[461,1618)`: requireWorktree/materializeWorktree проверяют репозиторий, ветку/HEAD исоздают либо проверяют существующую рабочую копию. Диапазоны T60/T62 не перекрываются: это не петля чтения одинакового текста. Но helper расположен втом же файле непосредственно перед caller (`worktree.ts:10–25,26–44`), поэтому связанное исходное чтение могло его включить.

**Первоначальный вариант:** при задаче «проверить повтор/восстановление» передавать связанную реализацию ensureWorktree→materializeWorktree→requireWorktree сразу. Изготовить такое source-задание помогает статическое разрешение известных вызовов; семантика внешнего Git/SQLite-эффекта остаётся предметом исследования. Не приписывать всему поведению helper один факт его вызова — CASE-2.3-CALLEE-EVIDENCE.
