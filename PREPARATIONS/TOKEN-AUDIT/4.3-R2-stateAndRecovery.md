## 3. Как предотвратить неправильную первую попытку

Отказов этого вопроса не было. Из прежнего исследования уже известны основания, которые нужно применить к новому результату:

| Установленное | Требование к первому ответу |
|---|---|
| Store.writeMany атомарно сохраняет свою группу SQLite с expected revisions и read guards | Назвать точную группу; не объявлять её общей транзакцией SQLite/Git/файлов |
| Assessment, принятый answer и завершение research-turn могут сохраняться отдельно | Проекция должна показывать промежуточное состояние без ложного «всё принято» |
| Pipeline, Discovery/Researcher, GraphRepository/Refinement, Compiler, Executor и PlanRepairs являются непосредственными producers | Не ограничивать подключение только ProductEngine.execute; учесть внутренние и восстановительные записи |
| Канонический результат, намерение внешнего эффекта и подтверждённый внешний результат различаются | Повторять действие по его собственному состоянию, а не по отсутствию Markdown-файла |
| A/B и существующий Git recovery имеют свои контракты | Не выдавать их за готовое восстановление нового файлового проектора |

**Предлагаемый исходный контракт публикации:** поколение связано с project/database identity, exact Ref исходных записей и версией формата. Подготавливается целый набор файлов, затем переключается публикация. Запоздалая попытка не вытесняет более новое опубликованное состояние. Принадлежащая область и защита посторонних файлов определены явно; гарантии переключения и сохранности требуют подходящих подтверждённых условий файловой системы.

**Предлагаемый контракт восстановления:** публикация следует за успешной канонической записью; открытие базы восполняет потерянное уведомление или отсутствующий документ. Незавершённые/удалённые проекции восстанавливаются из сохранённого канона. Ошибка файлов показывается отдельно от успешного сохранения стадии; предыдущая пригодная публикация сохраняется.

**Граница повторов:** файловый сбой сам по себе не запускает Researcher, model assessment, реализацию, проверки, ревью, принятие stage или Git-публикацию. Повторяется восстановление представления. Предметная работа продолжается только по собственному незавершённому каноническому состоянию.

Эти пункты — проект нового механизма, не утверждение о его готовности. Неподтверждённые fsync/rename/lock и аварийные исходы нельзя заменить формулировкой design; однако требовать уже созданный projector до постановки его реализации также неправильно.
