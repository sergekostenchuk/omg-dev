В текущей SQLite нет plan, current-plan, compilation-stage и принятого om-g2. Компиляция в аудите не запускалась. Из отсутствия записей не выводится полный список возможных незафиксированных неуспешных команд.

## 1. Входы, вывод задач и потребители

`Compiler.compile` проверяет current accepted om-g2 и feasibility, получает проверенный graph и environment, затем вызывает deriveTasks с разрешением внешних входов и ownership.

| Поле карты / основание | Результат в задаче |
|---|---|
| Узлы horizon | Набор tasks; ID вычисляется из project/graphHash/node |
| Outcome, title, purpose, benefit, beneficiary, implements | Результат, назначение, польза, получатель и связанные requirements |
| Boundary и code refs | Ответственность, отсортированные readPaths/writePaths |
| L3 connectors и управляющие предшественники | Inputs и зависимости; внутренний producer становится producerTask |
| Внешний producer/source | Exact source либо committed receipt, добавляемые в guards |
| Transfers и предыдущий writer | Ownership/write grants и соответствующие зависимости |
| Tests и requiredTests | Конкретные tests и обязательства проверки |
| Outcome и выходящие connectors | Produces — заявленные артефакты результата |

Задачи сортируются топологически. Машинный план version2 сохраняет graph/environment/stage/feasibility refs, repository base, guards, tasks, graphSnapshot и hash тела. GraphSnapshot проверяется на соответствие точной graph revision; это связанная копия для воспроизводимости, а не самостоятельно редактируемая вторая карта.

Plan и указатель current-plan записываются одной writeMany-группой. При наличии плана с тем же вычисленным ID Compiler.compile возвращает существующую запись.

**Обычная команда ProductEngine `compile` также вызывает compiler.publish и Pipeline.accept**, то есть принимает compilation-стадию в том же командном пути. Отдельно существует `draft-plan`, создающий черновик. Эти маршруты нужно различать; отдельное ручное принятие после обычного compile не следует из кода.

План затем потребляют выдача task-context/detail и исполнитель. Сама компиляция не реализует задачи и не публикует изменение продукта в Git.

## 3. Что предотвратить в первом L3 до компиляции

### Внешние входы

Для artifact.external нужен проверенный source с соответствующим artifact ID и содержимым, проходящим его contract.schema. Для producer вне текущего горизонта требуется совместимая committed receipt: producer signature, contract hash, plan/run/commit/tree и актуальный file manifest.

Недостаточность даёт external_input_missing, artifact_contract_mismatch, producer_not_ready и связанные типизированные отказы. Будущий результат нельзя заменить выдуманной receipt или бизнес-значением, сочинённым моделью. У implementation receipt проверяется manifest файлов, включая удаления.

**Исходный вариант:** активные входы L3 сразу имеют доступное подтверждённое основание либо производителя-задачу внутри горизонта. Если необходимый producer ещё не готов, его работа и зависимость должны быть отражены в допустимой декомпозиции; формальный ready не создаёт входа.

### Запись и передача владения

Продолжающий writer сохраняет boundary. Смена принятого writer требует явного transfer; предшественник внутри горизонта становится producerTask, внешний — подтверждённым предыдущим писателем. Отказы: ownership_boundary_changed, ownership_transfer_required, ownership_predecessor_missing.

**Исходный вариант:** L3 задаёт передачу записи и её основание вместе с путями, а не узнаёт об отсутствующем transfer после большой генерации. Отсутствие прежнего WriterProof само по себе не является универсальным доказательством авторизации.

### Проверки и порядок

deriveTasks требует покрыть обязательные tests каждого узла и строит dependencies из данных, управления и ownership. Непустой horizon и ацикличный порядок — машинные условия. Модель проектирует содержательный результат и нужные отношения; код вычисляет идентификаторы, сортировку и обратные ссылки.

Зарегистрированных отказов фактического compile здесь нет. Перечисленные классы — реальные условия кода, которые нужно дать исходному проектированию для предотвращения будущей переделки.

## 4. Ручные изменения и состав контекста

`Compiler.read` проверяет basis, hash тела, соответствие graphSnapshot точной graph revision и повторно вычисляет tasks. Несовпадение задач даёт plan_derivation_mismatch. Пересчитать только checksum после ручной правки недостаточно.

Исправление должно происходить в исходной карте/основании с последующим детерминированным выводом, сохраняя применимые результаты, а не через отдельный модельный план поверх канона. Task-context/detail формируются из exact плана и его допустимых доказательств.

Модельного request в compile нет; размер и побайтная доля повторов неприменимы. Повторный вывод при read — проверка машинной производности, а не повторный вызов модели. Его IO/CPU-стоимость в этом аудите не измерялась.

Кодовые основания на d88: `compiler/compiler.ts`, `derive.ts`, `inputs.ts`, `ownership.ts`, `model.ts`; ProductEngine command compile. Продуктовые команды не исполнялись.

## 5. Резервы

| Механизм | Основание | Экономия | Правильное исходное изменение | Риск | Цена правки |
|---|---|---|---|---|---|
| Механическая производность tasks | deriveTasks и проверка plan_derivation_mismatch | Собственного токенного резерва нет | Сохранить карту источником проектной структуры, не добавлять LLM-сочинение плана | Несвязанный ручной план потеряет трассировку | Уже реализовано |
| Пригодные внешние входы | Source/receipt и contract validation | Будущая экономия не измерена | До первого L3 определить реальные основания или producerTask | Нельзя придумать готовый будущий артефакт | Подготовка карты/входов |
| Явные write grants | Проверки границы и передачи writer | Не измерена | Передача владения включена в первичную декомпозицию | Незаконное расширение записи или потеря прежнего владельца | Контракт графа |
| Автоматический обычный путь принятия | ProductEngine.compile вызывает publish+accept | Не измерена | Не добавлять лишний обязательный ручной этап после успешного compile | Нельзя путать его с отдельным draft-plan | Уже реализовано |

Новые сокращения IO/проверок без измерения не заявляются. Убирать проверки внешних входов или вручную чинить производный plan не предлагается.

## 6. Неизвестное и сохранённый случай

Неизвестны фактический план, runtime-стоимость его вывода и конкретные отказы будущего L3. План в аудитируемом состоянии не создан; никаких compile/publish/accept, записей или исполнения не выполнялось.

**CASE-6.3-GRAPH-DERIVATION:** карта задаёт структуру задач, а R3, внешние входы и права записи обеспечивают пригодность этой структуры. Эти данные нельзя заменять модельными обещаниями. Исправляется источник плана; задачи выводит код.

## Обсуждение

Запись подготовлена для Fable. Уточнено значение «единственного входа»: карта — источник содержания задач, но операция использует дополнительные точные основания. Обычный compile автоматически принимает compilation; существующий отдельный draft-plan не делает ручную приёмку обязательной для всех путей.
