## 1. Вход, машинный результат и потребители

`Refinement.assess` получает текущую цепочку до L3, graph и effective environment. После graph gate и inspectRepository он сохраняет **feasibility**, а не отдельную запись phase:R3.

| Поле feasibility | Потребитель |
|---|---|
| contractVersion/projectId | Проверка принадлежности и применимого контракта |
| graph/environment Ref | Связь готовности с конкретным графом и конфигурацией |
| repository: root/head/tree/files | Снимок Git-основания и хэшей объявленных файлов; последующая проверка актуальности |
| inputs | Точные зависимости, которые проверяет feasibilityGate |
| findings/ready | Машинная диагностика и разрешение дальнейшего перехода; ready=true только при отсутствии findings |

Публикация om-g2 и компилятор потребляют точную feasibility-привязку, а не произвольное поле ready. Если необходимые предыдущие phases отсутствуют, `#inputs` отказывает **до** создания feasibility. Если предпосылки есть, но проверки графа/репозитория дают findings, результат может быть сохранён как ready=false.

В SQLite для omg-live: feasibility revisions=0, `feasibility:omg-live` отсутствует; phase:R2 и phase:L3 отсутствуют; R3-вопросов нет. Отсутствие результата не является полным журналом всех возможных незафиксированных CLI-попыток.

## 3. Что проверяется и как избежать первой переделки

`inspectRepository` выполняет Git/файловые проверки, а не запускает implementer, reviewer, fullCheck или продуктовые tests:

| Проверка по коду | Что дать предыдущему L3 заранее |
|---|---|
| Настоящий Git root, HEAD/tree и отсутствие незакоммиченных изменений | Точное репозиторное основание и условия его использования |
| Доступность executable implementer/reviewer/fullCheck | Конкретные команды и конфигурацию среды |
| Различие actor implementer/reviewer | Явные роли без смешения их назначения |
| У каждого work горизонта есть write code ref | Точную область записи результата |
| Безопасные относительные пути, обычные файлы; missing existing даёт finding | Честные existing/planned refs и допустимые пути |
| Доступность executable команды каждого теста | Связанный тестовый контракт и необходимые инструменты |

Существующий файл получает hash; отсутствующий planned-путь может быть представлен с hash=null. Planned не подменяется фиктивным existing. Соответствие структурных связей дополнительно проверяет graph gate.

**Пределы:** X_OK не доказывает корректность аргументов команды, наличие всех используемых ею модулей или успешный прогон. Разные actor-строки не доказывают фактическую независимость полномочий. R3 не подтверждает живой provider, sandbox или бизнес-результат новой реализации одним фактом доступности executable.

Следовательно, исходный L3 должен получить машинные требования R3 до большой генерации, а не узнавать о них через очередной отказ. Настоящие свойства среды и будущего результата имеют отдельные доказательства/этапы. Добавление модельного «одобрения» поверх этих машинных условий не заменяет их.

## 4. Актуальность и повторяемость

Модельного request нет; размер/доля повторов здесь неприменимы. `feasibilityGate` проверяет точную ready-запись, версии её inputs и состояние репозитория. Снимок относится к моменту проверки; существенное изменение основания не оставляет автоматически действительным старый ready.

При этом R3 не является обещанием, что внешние файлы никогда не изменятся после проверки. Последующие эффекты должны использовать свою точную привязку и допустимость действия. Показ исторических результатов сам по себе не требует превращать их в новую проверку готовности по правилам другой эпохи.

Кодовые основания: `graph/refinement.ts` — assess/feasibilityGate; `runtime/environment.ts` — inspectRepository, executablePath, workspacePath; версия d88b89c. Проверки будущего реального прохода при аудите не выполнялись.

## 6. Неизвестное и сохранённый случай

Неизвестны результат и runtime-стоимость будущего R3, а также все незафиксированные ранние неуспешные команды. Из текущего состояния следует отсутствие принятого основания, а не набор воображаемых findings готового L3. Feasibility/phase не создавались.

**CASE-6.1-READINESS-BOUNDARY:** детерминированная готовность конкретного графа/среды/репозитория не равна успешному исполнению продукта. Известные машинные ограничения поступают в первый проектный запрос; их выполнение фиксирует код, а будущую работу подтверждают её реальные результаты.
