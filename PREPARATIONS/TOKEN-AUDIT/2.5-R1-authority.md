## 3. Причины отказов иисходный вариант без них

### 3.1. Сумма исходных текстов не равна размеру reader context

T64 объединяет восемь файлов иowner-consent. Исходники занимают **59 535знаков**, но исторический сериализованный reader context — **70 231 >60 000**, превышение10 231. Это реконструкция по точным источникам иreaderSourcePacket данной эпохи, не wire telemetry. В profile6 ещё нет sourceIndex вinput; подстановка формулы profile21 дала бы ошибочные70 375.

Reader не запускался, но аналитик уже потратил **51 410токенов** на выбор неподходящего набора.

**Исходный вариант:** код считает реальный структурированный пакет иего обвязку, размерно готовит связанные части до reader dispatch; модель не должна угадывать пригодность по сумме длин файлов. Если все материалы нужны совместно, выделяется достаточная ёмкость/явная последовательная доставка. Семь последующих чтений не становятся автоматически лишними — они также добавили источники, которых не было впервом списке.

### 3.2. Один path использован для списка файлов ивладельческого документа

T72 содержит12facts, из них11отклонены до assessor: десять path со списком через `;`, один `path="owner-model-consent"`. Например, claim `local-command-authority` адресован сразу cli.ts, engine.ts иcommands.ts одной строкой.

Исправленный candidate содержит20раздельных facts с реальными файлами: cli-entry, default-owner-label, command-shape идругие. **Это не только побайтовая замена path:** тексты всех facts переработаны, citations25→24; версии sources те же, некоторые диапазоны расширены/слиты. Новых чтений между ответами нет.

Owner consent сохраняется в атрибутированном design, а не маскируется file-fact. Его точная цитата [0,416) не изменилась.

**Первоначальный вариант:** типизированная связь claim сего файлами/наблюдениями; системный path получает код из file-source. Многофайловое основание выражается отдельными атомарными facts либо явным массивом типизированных источников, не строкой сразделителем. Owner intent является отдельным видом основания. Допустимость адреса инеподменённый источник проверяются до семантической оценки, а достаточное исходное представление предотвращает саму ошибочную генерацию.

Наблюдаемая цена отвергнутого ответа —**88 775**, исправленного —**95 910токенов**. При сразу корректном первом ответе устраняется второй analyst call: **95 910−Δ tokens**, гдеΔ — изменение первой подготовки/ответа/оценки илюбые дополнительные действия. Это условный резерв, не доказанная чистая экономия. Перенос только текущей file-membership проверки раньше не предотвращает свободное смешение claims ввыходе модели.

## 6. Неизвестное исохранённый случай

1. Raw requests, точные повторения/денежный эффект кеша ифактические model/effort/speed.
2. Чистая экономия типизированного первого answer, разбиения илираннего чтения guard-цепочки.
3. Полный ID конфликтующего guard не сохранён всообщении; причина profile опирается на конкретную кодовую цепочку иevents.
4. Реальная изоляция среды/сети/дочерних процессов остаётся gap. Нельзя закрыть её source-кодом, показывающим лишь настройку sandbox.

**CASE-2.5-PROFILE-BOUNDARY:** конфигурация следующего эффекта иprovenance уже оплаченного ответа — разные сущности. Согласовывать профиль на границе нового dispatch исохранять candidate; повторное применение не считать новой генерацией. **CASE-2.5-AUTHORITY-EVIDENCE:** текстовая метка, происхождение записи, настройка sandbox ипроверка итогового кандидата имеют разные пределы доказательства. Первоначальные claims должны называть именно наблюдаемую гарантию, ане превращать их вобщую авторизацию/изоляцию.
