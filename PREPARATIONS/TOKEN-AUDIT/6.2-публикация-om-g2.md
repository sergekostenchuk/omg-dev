# 6.2. Публикация om-g2

Автор: Codex, ARCHITECTOR OMG. Дата: 07.09.2026. Блок6.1 принят Fable, 9/10.

**Вывод:** этот переход выполняется кодом, **без модели**. Команда draft-om создаёт черновик стадии со ссылкой на R3; принятие om-g2 выполняется отдельным accept-stage. В текущем проходе ни feasibility, ни stage:omg-live:om-g2 не сохранены.

Правильный вариант — передать уже полученную exact feasibility дальше по конвейеру. Заново сочинять описание карты, копировать весь граф в стадию или просить модель подтвердить машинный ready не требуется.

## 1. Вход, результат и потребитель

На d88b89c цепочка выглядит так:

| Переход | Результат |
|---|---|
| ProductEngine, command=draft-om | Вызывает Refinement.publish с project, feasibility Ref и expected |
| Refinement.publish | Проверяет текущую feasibilityGate; передаёт `{feasibility: ref}` в Pipeline.draft |
| Pipeline.draft | Записывает stage om-g2 со status=draft, точным predecessor features и пустым начальным proofs |
| accept-stage → Pipeline.accept | Проверяет текущую stage и её валидатор; записывает accepted с proofs/guards |
| Следующая компиляция | Потребляет current accepted om-g2, связанную exact feasibility и пригодный repository snapshot |

`ready` — свойство результата R3; `draft/accepted` — состояние stage. Они не взаимозаменяемы. `expected` — ожидаемая ревизия изменяемой записи, защищающая от конкурентного обновления, а не поле разрешения владельца.

Под публикацией в этом блоке понимается запись связки стадии в SQLite. Её content содержит ссылку на R3, а не вторую независимую копию карты или плана.

## 3. Предотвращение ненужного повторения

Зарегистрированного отказа этого блока нет. Для первого корректного перехода нужны:

- точная актуальная feasibility, а не произвольный ready=true;
- принятый и текущий predecessor;
- корректная expected revision;
- различение созданного draft и принятой стадии.

Приёмка проверяет собственный content om-g2 через валидатор и сохраняет доказательные зависимости. Если стадия уже принята на проверяемой текущей ревизии, Pipeline.accept возвращает её; stale expected даёт revision_conflict. Это причина обновить сведения о каноническом состоянии, а не автоматически повторить модельное исследование.

Первое действие не должно собирать R3-заключение заново словами модели. Изменившееся существенное основание требует соответствующего нового результата по продуктовым правилам; неизменный результат используется по ссылке. Наличие отдельного accept-stage само по себе не вводит новый обязательный запрос владельцу на каждую обычную операцию.

Существующий draft не гарантирует, что основания останутся актуальными до приёмки. Поэтому потребитель использует принятую и проверяемую связку, а не факт появления записи.

## 4. Состав пакета и повторяемость

Модельного request здесь нет; размер и доля повторов неприменимы. Машинный content — `{feasibility: Ref}`; идентичность графа, среды и репозитория остаётся в связанном R3-результате.

Это уже реализованная экономная передача основания. Копирование полной карты/исследований либо дополнительный LLM-verdict создали бы другую операцию без установленной необходимости.

Кодовые основания: ProductEngine cases draft-om/accept-stage, Refinement.publish/feasibilityGate, Pipeline.draft/inspect/accept, версия d88b89c. Валидность реального будущего R3 в этом аудите не проверялась.

## 6. Неизвестное и сохранённый случай

Неизвестны runtime-стоимость и исход будущей публикации/приёмки, а также незафиксированные неуспешные попытки. Из текущего журнала установлен только факт отсутствия сохранённых результатов этих шагов.

**CASE-6.2-BOUND-STAGE:** ready-результат, черновик stage и принятое основание потребителя — разные объекты/состояния. Код передаёт exact ссылку и фиксирует принятие; новое модельное описание не заменяет эту привязку.
