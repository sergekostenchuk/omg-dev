# 6.4. Принятие плана

Автор: Codex, ARCHITECTOR OMG. Дата: 07.09.2026. Блок6.3 принят Fable, 9/10.

**Вывод:** принятие машинного плана выполняется кодом, **без модели**. В обычной команде compile публикация и Pipeline.accept вызываются автоматически. Отдельный путь draft-plan создаёт черновик, который принимается через accept-stage. Поэтому эта стадия не является обязательным дополнительным ручным одобрением после каждого успешного compile.

В проверенном состоянии из6.3 нет plan/current-plan/compilation records; принятого плана нет. В аудите эти переходы не выполнялись.

## 1. Вход, результат и настоящий потребитель

| Путь / объект | Значение |
|---|---|
| Обычный compile | Compiler.compile → compiler.publish → Pipeline.accept; при подходящей уже принятой ссылке возвращается существующий план |
| draft-plan | Проверяет план и создаёт compilation draft; принятие выполняется отдельным accept-stage |
| Accepted compilation | Содержит exact plan Ref и доказательные зависимости стадии |
| Current-plan | Указатель на сохранённый план; сам по себе не доказывает его принятие |
| Executor.run | Производственный потребитель точного плана и accepted compilation с совпадающим Ref |
| consumePlan | Preview-потребитель, проверяющий порядок/идентичность возвращённых outcomes; не является исполнением продукта |

План и current-plan записываются одной группой, но публикация compilation draft и её принятие — последующие записи. Одна команда не означает одну общую транзакцию всех этих состояний. Частично сохранённый результат требуется различать при продолжении.

## 2. Реестр обращений и фактическое состояние

| Показатель | Наблюдение |
|---|---|
| Прямые model-call принятия | 0 по коду |
| Сохранённый план / accepted compilation в проверенном наборе | Нет |
| Полезный / переделка / справка / петля модели | 0 / 0 / 0 / 0 |

Это не выполненный переход за нулевую стоимость. Отсутствие records не даёт полного журнала возможных неуспешных команд. Будущие implement/review-вызовы относятся к исполнению, а не начисляются как уже состоявшиеся при принятии плана.

## 3. Как предотвратить ненужное повторение

**Первый корректный переход** использует план, построенный из принятых exact оснований. Compiler.read проверяет basis, hash, graphSnapshot и повторно выведенные tasks; Compiler.gate и валидатор compilation проверяют принадлежность/актуальность. Pipeline.accept сохраняет accepted с proofs/guards.

При конфликте или частичном завершении нужно установить, какой план и какая стадия уже сохранены. Наличие plan/current-plan не заменяет accepted compilation; при этом пригодный сохранённый план не требуется заново сочинять моделью. Повторный детерминированный вывод по тем же основаниям возвращает существующий plan ID.

`expected` на отдельном пути — ревизия для конкурентной записи. Из этого параметра не следует новое обязательное согласие владельца. Само принятие не выполняет задачи и не доказывает продуктовый outcome.

**Граница производственного admission:** Executor.run сначала получает блокировку проекта и вызывает recoverCommits, затем проверяет запрошенный exact plan и accepted compilation. Поэтому нельзя утверждать, что проверка нового плана предшествует вообще всем эффектам восстановления. Завершение ранее сохранённого commit_pending не означает принятия нового плана.

Для существующего execution-root применяется currentBasis, учитывающий допустимый прогресс собственных коммитов относительно исходного плана; для нового root — compiler.gate. Иначе каждый собственный commit делал бы исходный HEAD формально устаревшим и провоцировал ненужную переподготовку. Это не разрешение игнорировать произвольные внешние изменения.

Модель появляется позже, при исполнении задач ролями implement/review; проверки выполняются командами. Принятие compilation не является ещё одним LLM-verdict поверх уже исследованной карты.

## 4. Передаваемые данные и повторяемость

Модельного request нет; размер и доля повторов неприменимы. Передаются exact Ref плана и связанные основания, а не новая копия текстового плана, вручную отредактированная ради приёмки.

Настоящий потребитель сверяет project, revision, hash и связь с accepted compilation. Он не выбирает произвольный документ с тем же названием. Preview-результат consumePlan также не заменяет эту производственную привязку или выполненный продукт.

Кодовые основания d88: ProductEngine compile/draft-plan/accept-stage; Pipeline.accept; Compiler.read/gate/publish и requireBasis; Executor.run; compiler/consumer.ts. Execution, recovery и команды при подготовке записи не запускались.
