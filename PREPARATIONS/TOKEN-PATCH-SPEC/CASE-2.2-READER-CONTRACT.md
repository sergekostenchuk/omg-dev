## Дефект
Аналитик формулирует purpose читателя со ссылками на идентификаторы собственных выводов («проверить основания actors-f1 и actors-f2»), а читатель получает только роль, purpose и нумерованные источники. Текст утверждений ему не виден; он отвечает unresolved «нет сведений», и аналитик позже тратит текст запросов на пояснение, что искать эти id не нужно.

## Место в коде (d88b89c)

- `src/discovery/reader.ts:115` — инструкция читателя: только выбор диапазонов по purpose.

## Свидетельства
- 2.2: T193 и T194 — читатель отвечает unresolved о actors-f1…f5 при шести выборках каждый; T198 и T199 уже содержат пояснение аналитика, что actors-f6…f9 — идентификаторы выводов, а не строки исходников. Отдельные лишние вызовы только из-за этого не доказаны.

## Смежный дефект: локальное unresolved читателя (2.4)
Читатель отвечает unresolved относительно поданного пакета («реализация Store.writeMany не предоставлена») в четырёх результатах подряд после того, как store.ts прочитан в T56. Сборщик обязан различать: отсутствует в этом пакете; уже покрыто другим точным reader-result; действительно неизвестно потребителю. Иначе локальное ограничение читателя превращается в новый запрос или в глобальный пробел. В 2.4 аналитик свёл сам и повторного чтения не купил; механизм риска подтверждён, цена не измерена.

## Изменение до первого вызова
Задание читателю либо самодостаточно (какие обработчики, условия, исключения отобрать), либо несёт структурированное поле `claims: [{id}]` у действия read_bundle (`research-protocol.ts:40`); код разворачивает id в `{id, text}` из сохранённых выводов вопроса (checkpoint / proposal / history, те же `conclusions`, что собирает `working-context.ts:107`) и передаёт читателю. Неизвестный id → типизированный отказ до вызова читателя. Purpose остаётся свободным текстом и кодом не разбирается (решение 2026-09-07, п.7 обсуждения: сканирование текста на id это эвристика, отвергнута).

Дополнительно (2.4): unresolved читателя становится структурированным `{about: {sourceIndex?, symbol?}, note}` (сейчас `[string]`, `reader.ts:34–37`; старые reader-result читать в обоих форматах). Код устанавливает только **наличие**: у того же источника той же версии есть сохранённые наблюдения, и доставляет их список аналитику вместе с unresolved (CASE-2.3-OBSERVED-REUSE). Пометку «разрешено» код не ставит: разрешено ли содержательное unresolved, решает аналитик. Символ в `about` только подсказка, не ключ сопоставления.

Вид изменения: контракт действия read_bundle + промпт аналитика + проверка кодом.

## Тест
- read_bundle с `claims` по сохранённому id: читатель получает текст утверждения; мутация «не разворачивать» — тест обязан упасть. read_bundle с неизвестным id отклоняется до вызова.
- unresolved с `about.sourceIndex`, у которого есть сохранённое наблюдение той же версии: аналитик получает unresolved как есть плюс список наблюдений, без пометки «разрешено»; мутация «пометить разрешённым» — тест обязан упасть.
