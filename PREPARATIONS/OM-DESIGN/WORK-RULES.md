# Правила работы над кодом блока OM (редакция 21.09.2026, фаза кода; прежняя редакция — фаза правил — в истории git)

Назначение файла: записанная цель, с которой сверяются действия оркестратора, воркера и ревьюера (в том числе сигнализатором). Это памятка, а не ворота: она ничего не блокирует.

## Главное правило (слова владельца 21.09.2026)
«Каждый твой шаг должен вести тебя к цели. А цель эту нужно изначально определить». Есть продвижение к цели — работа продолжается; нет — остановка и доклад владельцу,
почему стоим. Формальные лимиты работу не регулируют. Три попытки подряд без продвижения по одной задаче — стоп и владелец.

## Текущая цель
Рабочий код блока OM по принятой план-схеме (уровни 0–1–2, вердикт ревьюера №146): блок готовит всё для компилятора, чтобы тот выводил атомарные задачи.
Первый сквозной рубеж — живой проход малого горизонта omg-live: состав выводит M2, ответы модели не подменяются заготовками.
Порядок: план задач → один общий проход с ревьюером → подпись владельца → задачи по плану без промежуточных остановок.
НЕ цель: улучшать карту ради карты; полировать пробный код `proto/`; чинить прежний процесс R0–R3; трогать UI.

## Кто что делает (утверждено владельцем 21.09.2026)
- Оркестратор (Claude, ведущая сессия): формирует задачи из карты, выдаёт их, проверяет сданное — пять проходов, полный прогон на финальных байтах, тесты соседей; говорит с владельцем. Рабочий код сам НЕ пишет.
- Воркер (Opus): на каждую задачу новый, с чистым контекстом и узким пакетом задачи. Рабочая копия `~/OMG/.omg/worktrees/om-module`, ветка `om/module`. Пишет только в пути, объявленные в задаче.
- Ревьюер (Codex, место `codex-omg`): одно независимое ревью на задачу; получает только то, что прошло проверку оркестратора.
- Jev (скилл `typesafe-agent-router`): совет перед запуском субагента — делегировать ли, роль, ступень модели, объём контекста. Совет, не полномочие; хук в режиме «тень».

## На чём основана задача
Источник один — принятая карта: `LEVEL2-RULES.md` (16 карточек правил и две передачи), карточки записей хранилища и ворот с кодами отказов, перечень того, что в движке берётся как есть.
Карточка задачи: цель одной фразой; id правил; входные и выходные записи; соседи (от кого получает, кому отдаёт); разрешённые пути записи; что из движка берётся как есть;
обязательные тесты — успех, КАЖДЫЙ код отказа, отсутствие поля → типизированный отказ, подделка входа, окно между проверкой и записью.
Тексты правил в пакет задачи подставляет скрипт дословно из `level2-rules.mjs` — не пересказ оркестратора.

## Ворота (их три, по правилам владельца)
1. Полный прогон на финальных байтах: `npm run check:backend` в рабочей копии модуля (точка отсчёта 21.09.2026: 415 тестов, все зелёные, 62 с).
2. Одно независимое ревью задачи.
3. Подпись владельца — один раз под планом задач; дальше принятый план действует как постоянное разрешение.
Владельца зовём: отход от плана; три попытки без продвижения; слияние в основную ветку; пройден рубеж; расходы, доступы, данные, необратимые внешние действия.

## Правила
1. Если правило карты оказалось неверным или неполным — сначала правка карточки на карте и подтверждение ревьюера, потом код. Заплатка в коде в обход карты запрещена.
2. После второго «вернуть» по одной задаче пересматривается конструкция задачи, а не латается код.
3. Статус — по вердикту: «принято» только при «принять».
4. Отсутствующая возможность — типизированный отказ, не заглушка. Выбор поведения продукта в коде не делается: это карточка решения владельцу.
5. Прежние записи читаются по правилам своей эры; новые проверки прошлое не перепроверяют.
6. Состояние `.omg/state.sqlite` и `live-source` — только чтение. Тесты — без настоящих вендоров, сети и ключей. push, теги, слияния — только по слову владельца.

## Сигналы ухода от цели
Считаются без модели (`channel-check.mjs --code`):
- правка вне путей, объявленных в задаче;
- правка кода движка вне каталога модуля, не объявленная в задаче;
- кода прибавилось, а тестов нет (вторая граница канала: работа без проверки);
- в ветке модуля изменён текст правил (`level2-rules.mjs`) — правила меняются через карту и ревью, а не попутно;
- правка в `ui/`.
Требуют понимания текста:
- в задаче или отчёте воркера поведение продукта выбрано исполнителем;
- слово «закрыто» или «сдано» без вердикта «принять».
Сигнал идёт владельцу и в отчёт, а не останавливает работу сам.
