## Как работать

- Ты воркер блока OM движка OMG. Рабочая копия — `/Users/kostenchuksergey/OMG/.omg/worktrees/om-module`, ветка `om/module`. Работай ТОЛЬКО в ней. Основную копию `~/OMG`, базу `.omg/state.sqlite` и `live-source` не трогай и не читай на запись.

Факты о движке: `PREPARATIONS/OM-DESIGN/code/engine-facts-infra.md` и `engine-facts-reuse.md` — сверяй с кодом перед использованием.
- УРОКИ РЕВЬЮ СДЕЛАННЫХ ЗАДАЧ (классы дефектов, за которые код уже возвращали): (1) экспортируемая функция проверяет форму ВСЕХ аргументов до первого обращения к полям и до хранилища — отсутствует, null, не тот тип → `EngineError` с кодом дефекта единицы; обычный `TypeError` — дефект. Отсутствующий набор и явно пустой набор — разные случаи, отсутствующий на `[]` не подменяется. (2) JSON-содержимое копируется и отдаётся только через `sealed()` / `delivered()` из `src/om/refusal.ts`; своё копирование присваиванием по чужим ключам запрещено — ключ `__proto__` теряется и подменяет прототип; объект из чужих ключей строится через `Object.defineProperty` либо `Map`. Инвариант для теста: хэш выданного равен хэшу записи. (3) Точная ссылка доказывает, КАКУЮ запись прочитали, но не её принятие: основание принятия и связь с исходом ворот проверяет та единица, чья это обязанность. (4) Т3 буквально: производная запись сверяется с ЗАФИКСИРОВАННЫМ ИСТОЧНИКОМ — источник перечитывается по точной ссылке, производное выводится из него заново той же функцией и сравнивается; пересчёт хэша собственных полей записи — это самосогласованность, а не вывод заново (так вернули A2). Тест подделки меняет содержимое И пересчитывает id либо хэш; проверяется историческая ревизия источника по точной ссылке — новая голова источника старую запись ложной не делает. (5) Т5 буквально: запрос на переход НАЗЫВАЕТ состояние, из которого идёт (номер попытки, номер остановки, точную ревизию) — запоздавший повтор того же запроса после любых последующих событий распознаётся как уже применённый и на более позднее состояние не действует (так вернули A3: повтор продолжения снимал НОВУЮ остановку). Тест: запоздавший повтор после следующего события и после перезапуска базы. (6) Т6 буквально: НЕупорядоченные наборы (достижения, отмены, отказы, вопросы пакета, основания) нормализуются одной функцией перед записью И перед сравнением, сортировка не зависит от локали, кратность сохраняется; хранимая запись с неканоничным порядком — отказ. Тест: перестановка элементов — тот же исход без ревизии. (7) Передача соседу несёт ОДНОЗНАЧНУЮ сохранённую связь с конкретной записью или строкой соседа (id либо точная ссылка), а не пару «название + цель»: два законных события с одинаковыми названием и целью обязаны оставаться различимыми. (8) Изменяющая операция отделяет ПОДГОТОВКУ (все проверки → готовые записи и охраны, без записи) от ЗАПИСИ: соседняя единица, которой по правилам нужна ОДНА транзакция на несколько записей, включает подготовленное в свой writeGuarded, а не вызывает операции по очереди (частичный результат) и не переписывает твою логику. (9) Каждый исход, который правило называет (например «разбор завершён без пригодного изменения — ступень 2»), — это ПРИМЕНЯЕМЫЙ переход, сохранённый в истории записи, а не только отказ: отказ ничего не сохраняет, и следующий запрос проходит так, будто исхода не было (так вернули A3.1). Проверь по правилам своей единицы: у каждого названного исхода есть операция, которая его записывает, и тест, что после него запрещённое остаётся запрещённым — в том числе после перезапуска и у преемника. (10) Если сосед по правилам пишет свою запись В ТОЙ ЖЕ транзакции, что твой переход (основание, разбор, решение, подтверждение), подготовка принимает основание в двух видах — уже записанное (точная ссылка) и готовящееся в этой транзакции (предлагаемая запись: подготовка сама вычисляет её точную ссылку, проверяет её ТОЙ ЖЕ функцией содержания и включает в возвращаемый набор записей). Подготовка, которая умеет только читать основание из хранилища, вынуждает соседа коммитить его отдельно — и открывает окно (так второй раз вернули A3.1). (11) Ничто, от чего зависит продвижение, класс или маршрут, не принимается со слов вызывающего: достижение, отмену, принятость выводит ПОСТАВЩИК из своей записи по точной ссылке (таблица поставщиков принятия `src/om/achievements.ts`); вида, которого нет в таблице, — отказ, а не «поверим». (12) Положительный вывод требует ДОСТАТОЧНЫХ РАЗЛИЧАЮЩИХ оснований: не хватает обязательной роли либо кандидатов несколько без различающего основания — «неизвестно», а не первый по порядку и не «последняя ветка по умолчанию»; устойчивая сортировка выбор первого не обосновывает (так вернули A4). (13) Перед сдачей убедись, что новые тесты ЛОВЯТ дефект: временно верни ошибочное поведение в `dist/` (не в исходниках), увидь падение теста, затем пересобери. (14) ОДИН класс — ОДИН механизм установления: если обычный путь ВЫВОДИТ класс, маршрут или статус из источников (таблица решений над прочитанными записями), то любой второй путь к тому же результату (снятие преграды, разбор, повтор, восстановление) обязан звать ТУ ЖЕ выводящую функцию над теми же прочитанными источниками; поле `class` чужой записи — заявление, которое сверяется с выводом, а не заменяет его: противоречие или недостаточность → отказ без записи (так второй раз вернули A4: `weighLift` принимал класс из разбора по форме ссылок, не читая содержимое). Тест: основания, из которых таблица выводит другой класс либо «неизвестно», преграду не снимают — ни сохранённым, ни готовящимся разбором; ни снятия, ни записи разбора в базе после отказа нет. (15) ИСТОРИЯ и ГОЛОВЫ — разные вещи: историческое основание (запись, по точной ссылке на которую серия уже перешла) проверяется по точной ссылке и новой ревизией не отменяется; в охраны транзакции (guards) идут ТОЛЬКО изменяемые головы, от которых зависит актуальность результата, — зато ВСЕ фактически прочитанные, включая те, что читает вызванный сосед (например, снятые преграды в stopContext): нет сведений о прочитанном у соседа — расширь его интерфейс, а не охраняй меньше (так вернули A5). Тест: законная новая ревизия исторического источника — отчёт стоит; изменение любой прочитанной головы между проверкой и записью — отказ записи. (16) Позднейшее событие само по себе НЕ доказывает неудачу прежнего средства: «следующая остановка после продолжения» не значит «продолжение не помогло», если между ними записан принятый результат или граница окна; вывод о неудаче — только из сохранённых результатов и границ окон, с тестом на историю с наследованием (так вернули A5). (17) Точная ссылка НЕ заменяет ни проверку ПРИНАДЛЕЖНОСТИ, ни СОДЕРЖАНИЕ: читая чужую запись как источник объяснения или основания, сверяй ВСЕ поля адреса, включая цели/предмет (подделка с верными пространством имён, видом, ревизией и хэшем, но другими целями — отказ), и передавай получателю содержание относящихся строк (код, цель, предмет, происхождение, записанный способ исправления, класс, адресат) с однозначной связью с источником, а не только хэш и ссылку (так вернули A5). (18) СОСТОЯНИЕ ≠ ИСТОРИЯ: текущее состояние соседа (лестница, окна, цели стоящей остановки) — не полная история его событий; сведения, которых в состоянии нет (цели уже отвеченной остановки, границы прежних окон после сброса), НЕ заменяются приближённой проверкой («все цели когда-то встречались») и не пересчитываются вторым алгоритмом — их отдаёт ОДИН точный источник: сосед выводит историю тем же выводом, которым строит и проверяет состояние, и отдаёт её интерфейсом (расширение интерфейса соседа — стык реализации, не правило продукта). Тест: потерянная цель, лишняя цель из другого окна, чужая цель — отказ; перестановка — успех; после сброса лестницы промежуточная остановка не теряется и результат приписывается своему окну (так второй раз вернули A5). (19) ПОЛНОТА НАБОРА проверяется по сохранённым ИСТОЧНИКАМ, а не по перечислению самого набора: реестр/ведомость/список, который выводит каждую свою строку из записей, обязан также доказать, что в нём есть строка для КАЖДОЙ записи-источника (перечисление источников по пространству имён или по хранимому индексу), иначе строку можно удалить новой ревизией и все пути пройдут (так вернули E1). Тест: частичная и полная потеря набора, включая уже закрытую запись, на КАЖДОМ пути, обращающемся к другой записи, а не к потерянной. (20) ЗАЯВЛЕННЫЙ ПОТРЕБИТЕЛЬ — ПРОВЕРЕННЫЙ ПУТЬ: если пакет называет соседа потребителем твоего интерфейса, напиши тест, который проходит ЕГО путь через законные операции (например, обращение к ревьюеру при сохранённой остановке, когда следующая попытка запрещена), а не только «обычный» путь; интерфейс, до которого потребитель не может дойти, — дефект (так вернули E1). (21) ДОПУСК ТЕКУЩЕЙ ПОДГОТОВКИ ≠ ИСТОРИЧЕСКОЕ ЧТЕНИЕ: перечитывание уже сохранённой записи проверяет источники по точным ссылкам как историю; подготовка НОВОЙ записи или её использование в транзакции соседа обязаны проверить ТЕКУЩУЮ актуальность оснований по семантике движка (например, принятость стадии: Pipeline.inspect считает стадию stale при сдвиге головы доказательства) и вернуть полное замыкание охран на эти изменяемые зависимости — в том числе когда запись уже существует и writes пуст. Это два разных пути; общий путь нельзя ни ослабить, ни ужесточить для обоих. Тест: сдвиг зависимости до подготовки, после подготовки перед общей записью, при повторном использовании; историческое чтение после сдвига и перезапуска остаётся успешным (так вернули B1). (22) ОТРИЦАТЕЛЬНЫЙ РЕЗУЛЬТАТ ПРОВЕРКИ ≠ ИСКЛЮЧЕНИЕ ЕЁ ИСПОЛНЕНИЯ: «данные не прошли» приходит из результата проверки (state/findings) и становится типизированным отказом; исключение при исполнении проверки (TypeError, EngineError чужого кода, сбой хранилища) передаётся выше без подмены — общий catch с запасной веткой «отказ производителю» запрещён. Предусмотренное исключение-дефект-данных преобразуется только по явному договору с его кодом. Тест: сбой в чтении посреди проверки сохраняет исходное исключение на всех публичных путях и не оставляет записей (так второй раз вернули B1). (23) САМОСОГЛАСОВАННОЕ ДОКАЗАТЕЛЬСТВО ≠ ПРИНЯТИЕ: proof, хэш которого совпадает с проекцией и который ссылается на верный верх, записать может любой — принятие слоя подтверждается по его НАСТОЯЩИМ сохранённым основаниям (источники исследования и вывод слоя у движка; точный принятый кандидат и исход своих ворот у OM) ОДНИМ общим механизмом для всех читателей. Тест: новая ревизия слоя с пересчитанной проекцией, хэшем и proof, но без исследования и принятия — отказ на всех публичных путях и уровнях (так вернули C2). (24) ПОЛНОТА КОНЦОВ ≠ СОХРАНЕНИЕ ПОТОКОВ: соответствие верхних и нижних связей проверяется ПОТОКАМИ целиком (производитель, порт, якорь, потребители) и взаимно однозначно — два верхних потока не сливаются в одну нижнюю привязку; законная кратность потребителей и произвольные имена нижних портов по записанному соответствию сохраняются. Тест меняет И нижний граф, И записанное соответствие с пересчётом хэшей (так вернули C2). (25) ИСПРАВЛЕНИЕ КЛАССА ОХВАТЫВАЕТ СОСЕДА: если твой механизм уже реализован у принятого соседа (та же проверка другой реализацией), класс закрывается ОДНИМ общим модулем, на который переводятся оба, — а не второй, «правильной» копией у себя; иначе два читателя расходятся на одном входе (так второй раз вернули C2). Тест: один и тот же изменённый вход через обоих читателей даёт одинаковый исход. (26) ПЕРВЫЙ ПРОХОД — ЗАКОННЫЙ ПУТЬ: сохраняемый интерфейс обязан работать от начального состояния (принятые стадии и L1, без L2/L3), а не только на полностью раскрытой фикстуре; если обязательный источник ещё не может существовать, он явно сообщает ПРОВЕРЯЕМЫЙ исход «ещё не возможен», выведенный из точных оснований текущей стадии, — не пустоту по умолчанию и не перехват любого отказа соседа; после появления основания этот исход не может скрыть настоящие данные. Тест — настоящий путь от начального состояния, затем появление источника (так вернули D1). (27) ГРАНИЦА ПОЛНОМОЧИЙ — ПО ИЗМЕНЕНИЮ, А НЕ ПО НАЛИЧИЮ: «эта задача не трогает уровень N» проверяется сравнением итога с ПРИНЯТЫМ определением (что изменилось, что исчезло), а не по тому, встречается ли уровень N во входящем объекте: неизменённое принятое содержимое другого уровня законно присутствует, а его отсутствие во входящем определении не должно его удалять. Учитывать и исчезнувшие ссылки, а не только новые (так вернули C4). (28) ЗАЩИЩАЕМОЕ = ЗАМЫКАНИЕ ЗАВИСИМОСТЕЙ: защищая объект, защищай и всё, во что его типизированные ссылки разрешаются (порт → контракт; результат/связь → артефакт → контракт и т. д.), по типизированным связям графа, а не поиском строк; равенство самого объекта ничего не доказывает, если его ссылки ведут в изменённые определения. Не замораживать при этом весь граф — законные изменения вне замыкания должны проходить (так второй раз вернули C4). (29) СОВПАДЕНИЕ ID ≠ СОХРАННОСТЬ СОДЕРЖАНИЯ; ЗАПИСАННОЕ ДОЛЖНО ЧИТАТЬСЯ: переносить прежнее (заполнение, привязку, ответ) по совпадению идентификатора нельзя — пригодность проверяется по правилам той единицы, что будет это читать (роль, контракт, артефакт, поток); непригодное уходит в историю, требование остаётся открытым. Результат подготовки обязан проходить те же проверки, что его последующее чтение: успешная запись, которую её собственные потребители отвергают, — дефект. Тест: запись → чтение всеми потребителями → повтор → перезапуск (так вернули C5). (30) СОВМЕСТНОСТЬ ОСНОВАНИЙ: несколько источников одного вывода должны принадлежать ОДНОЙ сборке/объекту — каждый сопоставляется с сохранёнными входами отказного объекта (точные предложения, база, уровень, контекст), а не проверяется только по отдельности; по отдельности верная запись другой сборки не годится. Связи отдаёт общий наблюдающий читатель, не восстановление по головам или совпадению содержимого. Тест: подмена одного источника точной записью другой сборки — отказ на всех путях (так вернули C5.2). (31) СТАНДАРТНЫЙ ПРОГОН — БЕЗ ФЛАГОВ: полный `npm run check:backend` обязан проходить стандартной командой, без NODE_OPTIONS и прочих поправок среды; тест, которому нужна увеличенная куча, ломает общий прогон всем следующим задачам. Каждый тест закрывает свои базы и не удерживает данные между случаями; тяжёлые таблицы случаев строятся так, чтобы память не росла с числом случаев. В отчёте — длительность прогона и, для тяжёлых наборов, пик памяти (так до ревью вернули C5.2). (32) ПРИЗНАК «ТЕКУЩИЙ РЕЖИМ» ВКЛЮЧАЕТ ТОЛЬКО АКТУАЛЬНОСТЬ: флаг current/historical переключает лишь проверку сегодняшних голов и выдачу охран; проверки связности и совместности точных оснований (с сохранённым контекстом своего прохода/сборки) действуют ВСЕГДА, одной функцией — на подготовке, историческом чтении, повторе и у поставщика. Тест: запись, которую подготовка отвергает, вписанная напрямую с согласованными хэшами, отвергается и историческим читателем, и после перезапуска (так вернули D2). (33) ИДЕНТИЧНОСТЬ — У ОБЪЕКТА В СОСТОЯНИИ, А НЕ У СТРОКИ ИМЕНИ: соответствие переименования связывает объект конкретной ревизии (узел или пара «узел, порт» в ревизии N) с объектом ревизии N+1; одинаковые строки имён сквозь историю безусловно не объединяются. Взаимные и циклические перестановки имён (a↔b, a→b→c→a) при однозначном соответствии сохраняют различимость объектов и прежние ключи; настоящие split/merge — отказ. Тест: перестановка имён узлов и портов одной заменой, затем содержательное изменение и возврат, с перезапуском (так второй раз вернули D2). (34) ОБНОВЛЕНИЕ НЕЗАВИСИМОГО ИСТОЧНИКА НЕ СБРАСЫВАЕТ ПРОИЗВОДНОЕ: если запись выводится цепочкой (корень → принятые решения → версия), обновление одного источника (например, инвентаря) проходит через ТОТ ЖЕ общий вывод и сохраняет проверенные решения; если изменение основания требует нового разрешения — явный исход, а не молчаливая запись корня заново. Тест: принятое решение → обновление независимого источника → решение на месте, историческое чтение (так вернули D3). (35) У ПРИНЯТОГО СОСТОЯНИЯ, КОТОРОЕ МОЖЕТ УСТАРЕТЬ, ЕСТЬ ПРОВЕРЯЕМЫЙ ВЫХОД: если применённое значение перестаёт быть применимым (изменились источники), должен существовать законный переход, возвращающий задачу в исходное открытое состояние (с историей и защитой от использования устаревшего значения), — иначе блокировка всего объекта становится тупиком. Тест проходит весь жизненный цикл: применение → устаревание → возврат → новое подтверждение → повторное применение, с перезапуском (так вернули D3.1). (36) СТОИМОСТЬ ОПЕРАЦИИ С ОБЩИМИ ИСТОРИЧЕСКИМИ ОСНОВАНИЯМИ — ИНВАРИАНТ, А НЕ СКОРОСТЬ: в пределах одной верхнеуровневой операции (подготовка/запись/чтение истории) каждое неизменяемое историческое основание подтверждается один раз на ключ (читатель, представление Store/Proxy, проект, точная ссылка, влияющие параметры); число разворачиваний зависит от числа уникальных оснований и связей, а не от числа путей к ним; следующий внешний вызов читает заново, текущие головы и охраны не кэшируются; закрепляется счётчиком чтений/выводов на масштабе в обычном тесте, миллисекунды — только диагностика (так вернули D3.1 третий раз).

Если правило уже запрещает такое поведение, а черновик его нарушает — это замечание к черновику, схему оно не возвращает.

```text
ОБЩИЕ ТРЕБОВАНИЯ — каждое с местами, где обязано действовать

Т0 · ГЛАВНОЕ ПРАВИЛО (слова владельца 21.09.2026: «каждый твой шаг должен вести тебя к цели, а цель эту нужно изначально определить»). Цель определена заранее и записана. Работу — и модели внутри OM, и исполнителей, которые OM строят, — регулирует ПРОДВИЖЕНИЕ К ЦЕЛИ, а не формальные лимиты: число попыток, потолки токенов и бюджеты сами по себе ничего не останавливают и не урезают. Есть продвижение — работа продолжается; нет продвижения — остановка и ЛЕСТНИЦА ПОСЛЕ ОСТАНОВКИ (решение владельца 21.09.2026, ночь): сначала причина хождения по кругу разбирается с независимым ревьюером и вырабатывается изменение — после него снова до трёх попыток; не помогло и это — вызов владельца с объяснением, почему стоим. «Нет продвижения» понимается по правилу ЗАВЕРШЁННЫХ ПОПЫТОК (правила вызовов модели): остановка — после третьей подряд завершённой попытки без продвижения, а не после первого промежуточного шага без результата. Отмена потолков не отменяет остальных требований к корректности данных, допустимости действий и проверке результата.
  Места: вызовы модели MC1 и MC2 и серии исправлений; ворота повтора G7; правила работы исполнителей (WORK-RULES.md).

Т1. Принятое читается из записи, а не угадывается заново. Где записи нет — вывод по действующим отношениям движка; неоднозначность — типизированный отказ, «первый подходящий» не выбирается.
  Места: соответствие «обязательство → конец связи» в каркасах операций и работ; адрес соседа в пакете задачи; основание готовности блока (M2 → M7); адресация вопроса (M5).

Т2. Отношения между узлами — действующая семантика движка, а не приближение. Уточнение = вложенность ИЛИ явное «реализует» (RefinementRelations). Необходимые предшественники = связи данных + requires + передачи владения (controlPredecessors). Годность квитанции — формула компилятора. Владение путём — правила writeGrants.
  Места: замыкание горизонта; принадлежность заполнения верхнему узлу; зона работ; план исполнения; адрес соседа; сверка доставки.

Т3. Производная запись проверяется повторным выводом из зафиксированных источников, а не по собственным полям.
  Места: набор пробелов (G4, G4b); пакеты соседей (G5); кандидат слоя — принимается только граф из записи кандидата (G3, G5).

Т4. Отсутствие — типизированный отказ с адресом. Нет обязательного источника, поля или набора — отказ; значений по умолчанию у обязательного нет; «пусто» передаётся явно.
  Места: вход M1 (правило эры: в записи прежней эры отсутствие структурированного поля — адресный пробел, в новой — отказ производителю стадии); готовность блока в горизонте; источники M5; аргументы всех ворот.

Т5. Переход состояния проверяет, из какого состояния идёт. Повтор того же — без изменений; противоречащее — отказ; запоздавшее не отменяет более позднего.
  Места: принятие кандидата; переход каркаса на новую базу; адресация вопроса; закрытие линии пробела; переход серий; закрытие вызова модели; учёт исхода попытки.

Т6. Порядок записей ничего не решает, кратность доезжает до потребителя.
  Места: несколько привязок одной связи (потоки); несколько потребителей; работа, уточняющая несколько операций; адреса внешних входов; ровно один пакет на работу.

Т7. Проверка и запись — одна транзакция с охраной по точным ссылкам; окна между «проверил» и «записал» нет.
  Места: учёт вызова в ведомости (запись и однократное закрытие); принятие кандидата (граф + каркас + статусы предложений); переход серий; переход каркаса на новую базу.

Т8. Отказ адресный и с маршрутом: что именно, у какого узла, кому возвращается — производителю данных, в пробел M5, владельцу, на пересмотр готовности в M2. Сам отказ ничего не переключает: не разрешает повторное исполнение, не меняет готовность, не открывает новую попытку. Обратные пути идут через G7.

Т9. Каждый пробел заполняется (решение владельца 21.09.2026). Отложенное не теряется и не закрывается без основания; нужное текущей сборке не переносится строкой результата; вес блока — только очередь.
  Места: отсрочка и линии в M5; G4b; M3.

Т10. Продуктовый выбор в коде не делается. Если для исправления надо выбрать СМЫСЛ ограничения (что считать продвижением, что считать несоразмерным расходом, замена адресации, аварийная защита бюджета) — это карточка решения владельца; до решения действует названное осторожное умолчание.

Т11. Политика неизменяема, выданное — копия. Таблицы правил не меняются во время работы; запись, отданная потребителю, не делит изменяемых объектов ни с политикой, ни с источником, из которого ворота выводят эталон. Это требование к модулю; решений схемы оно не меняет.
```

### Уровень 2 · Правила · MC1 и MC2 · обращение к модели: пакет вопроса, форма ответа, проверка  `rules-mc`

```text
ЗАЧЕМ (слова владельца 21.09.2026): «Лечить нужно не потолком, а тем, что делает модель и как она это делает… чтобы было одно обращение к модели, и она спокойно на это ответила по делу, коротко, чётко — без мысли по древу».
ПРЕЖНЯЯ БОЛЕЗНЬ (по коду движка и аудиту 07.09.2026): вопрос охватывал целую область; каждый вызов получал «весь проект» — все требования, всю проекцию слоя, полные поля прежних стадий, историю восьми ходов (pilot-context.ts, research-context.ts, research-runner.ts); оценщик получал то же; цикл «план → до 16 чтений → сборка страницами → ответ → оценщик» крутился внутри одного хода. Действия «нужен источник», «нужно решение владельца», «пауза» в протоколе движка были, но в том сценарии R2 правила приёмки делали их бесполезными: записанный пробел давал отказ. Итог: 28 вызовов и 1 542 356 токенов на первый вопрос, принято 0.

ПАКЕТ ВОПРОСА — что уходит модели. Собирается КОДОМ под конкретный вопрос, по адресам, которые схема уже знает:
  · сам вопрос: цель, поле, вид знания, потребитель, что именно требуется в ответе и в какой форме;
  · для раскрытия узла (MC2): верхний узел (название, исход, граница, порты); его незаполненные обязательства; для каждого конца связи — связь, контракт и ВСЕ прочие концы этого потока (соседи) с узлами и портами; уже принятые нижние узлы этого узла; имена, занятые представителями;
  · для факта (MC1): известные адреса источников; требование к доказательству;
  · правила, по которым ответ будет проверяться, — названиями отказов;
  · при повторной попытке — отказы прошлой попытки ПО ЭТОМУ вопросу (коды и цели) и только они.
  В пакет НЕ входит: весь проект, все требования, полная проекция слоя, поля прежних стадий целиком, история ходов, чужие вопросы.
  ВМЕСТИМОСТЬ. Полный пакет проверяется строго до вызова, как контекст задачи у компилятора (boundedContext): обязательства молча не усекаются. Предел выражает ТЕХНИЧЕСКУЮ ВМЕСТИМОСТЬ одного запроса — сколько принимает модель и транспорт (в движке это физический предел запроса, physicalLimits.maxRequestChars) — и берётся из неё. Занижать его ради экономии нельзя: это был бы отменённый владельцем регулятор под другим именем.
  ЧАСТИ ВОПРОСА — когда узел целиком не помещается. Делит КОД, а не модель: по связям узла, в устойчивом порядке (по id связи); одна часть — обязательства одной или нескольких связей вместе с их соседями. В КАЖДУЮ часть входят: сам узел; перечень ВСЕХ его обязательств одной строкой каждое; нижние узлы, уже предложенные предыдущими частями (чтобы операции переиспользовались, а не дублировались). Ответ части — частичное предложение слоя на свои обязательства; оно может вводить узлы и ссылаться на узлы прежних частей. ТОЧКА ПРОВЕРКИ — одна: когда заполнены все обязательства узла, код собирает из частей ОДНО предложение узла; оно входит в общую сборку кандидата слоя, которую проверяют обычные ворота (правила M4); принимается только целое. Части, определившие один и тот же узел по-разному, — отказ «части противоречат», он возвращается в следующую попытку. Весь цикл по узлу — одна попытка (Т0).
  НАЗНАЧЕНИЕ ЧАСТЯМ (вердикт №486). Делится только после подтверждённого переполнения ПОЛНОГО пакета; делятся НЕЗАПОЛНЕННЫЕ обязательства связей в устойчивом порядке по id связи; все концы узла и отдельные потоки одной связи остаются в своей группе (совпадение id связи не сливает потоки). Незаполненное обязательство результата (block-outcome / operation-outcome) назначается ПОСЛЕДНЕЙ части вместе с её обязательствами связей: она получает узлы, предложенные прежними частями, и может использовать подходящий либо предложить новый; это порядок обращения, а не правило вывода результата — пригодность заполнения проверяет каркас; отдельного завершающего вызова нет. В каждой части различаются ПОЛНЫЙ перечень обязательств узла и обязательства, НАЗНАЧЕННЫЕ этой части: назначенные наборы не пересекаются, их объединение точно равно незаполненному набору проверенной базы; уже принятое заполнение видно в общем контексте со своим основанием и повторно не назначается. Открытых связей нет, а результат открыт — один неделимый пакет результата; открытых обязательств нет — обращения нет. Вместимость проверяется для ФАКТИЧЕСКИ сформированного пакета (общий перечень, узлы прежних частей, задание результата в последней части); переполнение не обходится удалением этого контекста, потерей результата или скрытым дополнительным вызовом. Прежняя часть — только из ЭТОЙ цепочки: тот же узел, уровень и точная база, соответствующее задание прежней части; произвольное читаемое предложение прежней частью не становится; наблюдение состава — не принятие слоя.
  Не помещается даже часть по ОДНОЙ связи либо неделимый пакет результата — адресная остановка «узел не раскрывается по частям»: это сигнал, что узел слишком крупен на уровне выше; маршрут — пересмотр верхнего слоя (проектное решение уровнем выше) либо владелец. Повторная сборка того же пакета не выполняется.
  ДОЧИТЫВАНИЕ. Дочитать модель может только КОНКРЕТНЫЙ адрес (действующие действия чтения и поиска по адресу); код отдаёт запрошенное, «дай всё» не выполняется. В каждом дозапросе форма ответа и обязательства повторяются. Дозапрос обязан назвать, КАКИХ сведений не хватает и по какому адресу они ожидаются; уже доставленное в этой попытке учитывается кодом. Повторный запрос того же неизменившегося источника без новых сведений завершает цикл адресным отказом (в движке — research_no_progress при повторном чтении): попытка завершена без результата. Это проверка СОДЕРЖАНИЯ действий, а не лимит чтений или токенов. Дозапросы — часть той же попытки; попытка оценивается по результату (Т0).

ФОРМА ОТВЕТА — задана заранее, проверяется по схеме вопроса (действующая проверка формы):
  · MC2, задание РАСКРЫТИЕ УЗЛА: предложение слоя на ЭТОТ узел (или его часть) — узлы, заполнения его обязательств (для работ — с портом и местом в коде), локальные связи, зависимые определения, явные замены с точной базой. Всё, что код умеет досчитать сам, модель не присылает (действующий досчёт: тесты работы по владельцу, реализуемые требования, входы объединений).
  · MC2, задание РЕШЕНИЕ О НЕДОСТАЮЩЕМ ПОЛЕ ВХОДА: на КАЖДЫЙ вопрос пакета отдельный результат {цель, поле, значение, основание}. Значение — только то, чего не хватает: для адресации вопроса — узел-потребитель и вид знания; для привязки контракта — id блоков; для границы — id узлов и участников; для критерия — вид проверки. Верхнего узла у такого задания может не быть вовсе — предложением слоя оно не является. Код проверяет: вопрос существует, id есть в карте, значение из допустимого перечня, ссылка строгая. Применение — принятый переход M5: заполняется только недостающее, уже известные поля производителя сохраняются, получается новая версия входа. Для АДРЕСАЦИИ сам содержательный вопрос остаётся открытым обязательством своего вида; заполненная привязка контракта, граница или вид проверки закрывают именно пробел ЭТОГО поля. Обязательное поле записи новой эры, отвергнутое воротами входа G1, этим маршрутом не обходится — оно возвращается производителю стадии.
  · MC1: значение поля и цитаты по адресам. ОСНОВАНИЕ вычисляет КОД из цитат (действующий расчёт с пределами доказательности: наблюдение репозитория / цитата намерения требует атрибуции / сообщённое — не доказательство исполнения).
  · Законные управляющие ответы (действующие действия протокола) — не провал формы, и у каждого свой определённый исход:
      «нужен такой-то источник» (адресно) → код доставляет адрес в ЭТУ ЖЕ попытку по правилу дочитывания; режим планирования, в который это действие переключало прежний обработчик, не используется;
      «нужно решение владельца» → попытка завершается исходом «ожидает владельца»: вопрос с причиной записывается владельцу с адресатом и потребителем; серия по этому вопросу ждёт ответа. Это сохранённое ожидание, а не остановка по Т0 и не попытка без продвижения; но и НЕ продвижение: накопленный счёт попыток без продвижения оно не обнуляет. Причина обращения и недостающее решение видны владельцу. Ответ владельца возвращает вопрос в работу, но утверждение о репозитории доказанным фактом не делает — проверка по виду знания сохраняется;
      «ответить не могу — почему» или пауза → попытка завершена без результата (Т0); названная причина входит в пакет следующей попытки и в объяснение владельцу при остановке.
    Выдумывать модели незачем.
  · Рассуждение вне формы результатом не считается и никуда не сохраняется как основание.

КУДА ИДЁТ ПРИНЯТЫЙ ОТВЕТ-ФАКТ (MC1)

Способ вычисления отпечатка — детализация модуля. Образец в движке — принятие исследованного ответа (Discovery.researched и связывание ответа с вопросом и полем).
  Находит M6 при следующем проходе — по обязательству, с проверкой применимости: тот же договор вопроса И те же текущие источники (правила M6).
  Получает и использует тот механизм, который породил пробел: пробел входа — сборка входа F1.1 подставляет значение в НЕДОСТАЮЩЕЕ поле (известные поля не трогает) и даёт новую версию входа; факт, нужный проектному вопросу, — входит в пакет вопроса MC2 как известный факт со ссылкой на основание; факт для проверки реализуемости — M8.
  Основание закрытия линии M5 «заполнено» выдаёт тот же шаг принятия: ссылка на принятый ответ, связанная с линией и полем. Неприменимый ответ линию не закрывает.

ЧТО ХРАНИТСЯ: запись вызова (действующая: отпечаток запроса, ответ, расход четырьмя полями, статус, время) с привязкой к попытке, серии и пробелам; ответ MC1 (значение, основания, вердикт оценщика); предложение слоя MC2. Модель сама ничего не меняет: все режимы, кроме исполнения задач, только читают.
ОТКАЗ И ПРОДОЛЖЕНИЕ: ответ не по форме, не на вопрос, с неразрешимыми адресами или отклонённый проверкой — попытка завершена без результата (Т0); отказы возвращаются модели в следующей попытке по этому вопросу; автоматического повтора того же запроса нет. Вердикт не supported — ответ не принят, пробел открыт. Остановка — по Т0: третья подряд попытка без продвижения; дальше — лестница после остановки (правила вызовов модели): разбор с независимым ревьюером, затем владелец.
ОТКРЫТОЕ: значение предела пакета — настройка среды; для режима исследования провайдерская схема ответа не выставляется — форма держится инструкцией и проверкой после ответа (детализация модуля); способ обращения один — codex-stdio; отказ от ролей планировщика и читателя следует из слов владельца — если на живом проходе чтения по адресам окажется мало, вопрос возвращается владельцу, роли молча не возвращаются.
```

### Уровень 2 · Правила · M6 · маршрут пробела и ответ кодом  `rules-m6`

```text
Получает: набор пробелов M5 (цель, поле, вид знания, маршруты, потребители, признак «блокирует»); вход; инвентарь репозитория, если он есть; принятые записи.
Достоверное основание: вид знания и допустимые маршруты — из таблицы M5, а не из самого пробела (Т3); ответ кодом — только по АДРЕСУ: принятая запись или место в инвентаре с точной ссылкой.
Выдаёт и хранит: результат маршрутизации на каждый пробел {пробел, маршрут, версия входа, ссылка на ответ} и вопросы для обращений к модели.
Правила:
  · Вопрос модели — только на невыводимый пробел: сначала код, потом модель (принцип «механически, модель по обоснованию»).
  · Факт репозитория: код ищет ответ по адресу; нашёл — ответ кодом с точным основанием. Не нашёл — вопрос в MC1 вместе с адресами, которые уже известны (из пробела, от производителя стадии), и с правом модели назвать недостающий адрес. Отсутствие инвентаря не означает, что вопрос невыводим: доступные механические ответы по известным адресам сохраняются.
  · ПРИНЯТЫЙ РАНЕЕ ОТВЕТ — тоже ответ кодом. Прежде чем задавать вопрос, M6 ищет принятый ответ на ЭТО обязательство (та же цель и то же поле) и проверяет его ПРИМЕНИМОСТЬ по двум условиям сразу:
      (а) ДОГОВОР ВОПРОСА тот же — что устанавливается, для какого потребителя, при каких существенных требованиях и в какой форме результата. Запись ответа хранит отпечаток этого договора; он сверяется с договором нынешнего вопроса. Совпадение цели и поля — идентичность линии для истории, тождества вопросов оно не доказывает (было «поддерживается JSON», стало «поддерживается потоковая выдача JSON» — поле и тип те же, вопрос другой);
      (б) ИСТОЧНИКИ, относящиеся к нынешнему заданию, в ТЕКУЩЕМ состоянии те же, что названы основаниями ответа. Сверяется действующее состояние источника: разрешимость исторической ссылки доказывает сохранность старой версии, а не её актуальность.
    Оба условия выполнены — результат маршрута «код» со ссылкой на принятый ответ, модель не вызывается. Изменился смысл требования, область применимости, форма результата либо источники — прежнего supported недостаточно: ответ проходит проверку для нового задания, вопрос задаётся заново. Правка входа, не затрагивающая договор вопроса, повторного исследования не требует.
  · Проектное решение → MC2. Решение владельца → владельцу: одна строка вопроса, варианты, потребитель. Подтверждение среды → наблюдение среды (M8, старт задачи). Доказательство после реализации → результат задачи. Ни одно из них не подменяется другим (Т2 передачи в M5).
  · У проектного решения ДВА разных задания с разными формами ответа (правила MC1 и MC2): РАСКРЫТИЕ УЗЛА — для незаполненных обязательств каркаса; РЕШЕНИЕ О НЕДОСТАЮЩЕМ ПОЛЕ ВХОДА — адресация вопроса предшественника, привязка контракта ТЗ к блокам по id, граница узлами вместо прозы, вид проверки критерия.
  · РАСКРЫТИЕ УЗЛА: единица ПРИЁМКИ — один верхний узел зоны (блок или операция) со ВСЕМИ его незаполненными обязательствами: кандидат собирается и проверяется целиком. Единица ОБРАЩЕНИЯ — весь узел, если его пакет помещается в техническую вместимость вызова; иначе — части (правило частей — в правилах MC1 и MC2). «Единица приёмки — узел» означает целостность ЕГО предложения, а не проверку изолированного узла: обычные ворота проверяют собранный граф слоя со всеми необходимыми заполнениями (правила M4). Если для общей сборки ещё нужны предложения других узлов, готовое предложение этого узла сохраняется до неё; ожидание остальных не делает его ошибочным ответом модели. Значимость вопроса — число обязательств и потребителей, которые он закрывает.
  · Мелкие однотипные вопросы одного вида знания объединяются в один вызов с отдельным проверяемым результатом на каждый (пример: адресация десяти исторических вопросов omg-live).
  · Ничего не запускается и не ожидается без пробела; пробел вне горизонта в модель не идёт.
Разрешённые изменения: M6 ничего не меняет в графе и входе — только записывает маршрут и результат.
Отказ и продолжение: маршрут, не разрешённый видом знания, — отказ (G4b: answer_route_foreign). Нет ни адреса, ни инвентаря для факта репозитория — вопрос уходит в MC1 с каталогом адресов (перечень путей) и адресным чтением; перечень путей сам факта не доказывает — основание даёт только прочитанный точный источник.
Открытое: инвентарь репозитория кодом (решение владельца 12.09.2026) не построен — до него большая часть фактов репозитория пойдёт в MC1 по адресному пути; этот путь инвентарь не заменяет. Потребители инвентаря — сам M6 (ответ кодом) и пакет проектного вопроса; проверке реализуемости M8 он не нужен.
```

### Уровень 2 · Правила · Вызовы модели · вопрос по делу, учёт, продвижение и остановка  `rules-g8`

```text
РЕШЕНИЕ ВЛАДЕЛЬЦА 21.09.2026 (вечер), его словами: «Проблема не в потолке. Лечить нужно не потолком, а тем, что делает модель и как она это делает». «Не должно урезаться количеством токенов успешное прохождение вопроса». «Если продвигаешься к цели — хоть десять проходов; если три раза прошёлся и ноль продвижений — нужно что-то менять, и это главная причина вызова меня».
Потолки токенов (на вызов, на блок), выделения бюджета горизонта и лимит числа попыток как РЕГУЛЯТОР работы ОТМЕНЕНЫ. Прежние карточки G8 (допуск по потолкам, предохранители, выделения) — история.

ЧТО РЕГУЛИРУЕТ ВЫЗОВ МОДЕЛИ
  1. Вопрос. Один вызов — один адресный вопрос: пробел с целью, полем и потребителем (M5). Нет потребителя — нет вопроса, нет и вызова. Мелкие однотипные вопросы (например, адресация десяти исторических вопросов omg-live) объединяются в один вызов с отдельным проверяемым результатом на каждый.
  2. Что уходит модели. Только нужное для этого вопроса: сам пробел, соседи по связи, относящиеся к нему правила и контракты — не весь проект и не «всё, что может пригодиться».
  3. Ответ. В заданной форме и по делу: проектное решение — предложение слоя на ЭТОТ пробел (узлы, заполнения, зависимые определения); исследование — ответ с основаниями и вердиктом. Ответ не по форме или не на заданный вопрос результатом не считается; код проверяет ответ, а не верит ему.
  4. Значимость вопроса схеме известна заранее: сколько обязательств, потребителей и блоков он закрывает.

УЧЁТ — остаётся
  Расход каждого вызова записывается в одну ведомость проекта с адресом: блок, пробелы, серия, вид вызова. Закрытие вызова — один раз, по фактическому расходу; повтор той же записи ничего не удваивает (Т5, Т7). Назначение учёта — не отказ, а ответ на вопрос владельца: сколько потрачено на вопрос какой значимости и что за это получено.

ПРОДВИЖЕНИЕ И ОСТАНОВКА — вместо лимита попыток и потолков
  Цель попытки. ДО попытки названы цель — вопрос или согласованный пакет вопросов серии — и конкретный проверяемый результат, который к ней приблизит.
  Попытка — ЗАВЕРШЁННЫЙ ЦИКЛ решения этого вопроса (пакета) в серии: от постановки до проверенного результата либо конечного отказа этого цикла. В цикл входят работа кодом, вызов модели, подготовка кандидата и относящиеся к нему проверки; промежуточные шаги отдельных отметок «без продвижения» не получают. Исход цикла учитывается один раз; повтор доставки — не новая попытка. Ответ не по форме или не на вопрос завершает попытку без результата, а не исчезает из учёта. Пакетный вызов даёт результаты по своим вопросам; один цикл не умножает счёт серии на число вопросов.
  Продвижение — НОВЫЙ ПРИНЯТЫЙ РЕЗУЛЬТАТ с основанием относительно истории этой цели: заполненная линия пробела, проверенный ответ, принятое уточнение. Отправка ответа или изменение кандидата сами по себе продвижением не являются.
    · Повторное получение уже достигнутого после его потери новым продвижением не считается. Исправление одного, отменившее другое, — конфликт результатов, а не успех.
    · Принятое уточнение может породить новые обязательства — это продвижение: сохраняются его основание и связь с порождёнными обязательствами (решена адресация вопроса — остался сам вопрос: это разные результаты, M5 их различает). Рост числа пробелов сам по себе не означает отсутствия продвижения; уменьшение само по себе его не доказывает.
    · Уменьшение набора отказов ворот — полезный признак при сопоставимых проверках, но не самостоятельное основание: засчитывается только как новое подтверждённое достижение относительно истории цели. Чередование состояний A → B → A продвижением не является.
    · Идентичность цели переживает техническую смену ревизий, id и переоформление серии.
  Счёт. Подтверждённое продвижение обнуляет счёт подряд идущих попыток без продвижения; попытка без продвижения увеличивает его на один.
  · Продвижение есть → работа продолжается, сколько бы попыток ни было. Почти готовый ответ не обрывается.
  · Третья подряд попытка без продвижения → сохранённая остановка с точкой продолжения. Перезапуск остановку не снимает. Сама остановка ничего не переключает (Т8).
  ЛЕСТНИЦА ПОСЛЕ ОСТАНОВКИ — решение владельца 21.09.2026 (ночь), его словами: «мне нужно движение и прогресс к цели, а не церемонии. Можно три, но при этих условиях»; «нужно сначала дать контекст Кодексу и сначала с ним разобрать причину хождения кругами и выработать решение; если оно тоже не сработает — тогда меня».
  Область: лестница относится к остановке ИЗ-ЗА ОТСУТСТВИЯ ПРОДВИЖЕНИЯ. Прямой вопрос владельцу, неустановленное происхождение отказа, условия среды и ошибки производителя сохраняют свои маршруты (правила G7) — решение ревьюера их не отменяет. «Ожидает владельца» остаётся ожиданием и счёт не меняет; новое окно открывает только отдельное разрешённое продолжение.
  · Ступень 1 — РАЗБОР С НЕЗАВИСИМЫМ РЕВЬЮЕРОМ. Ревьюер — роль, не совпадающая с исполнителем (действующее правило независимости ролей). Он получает КОНТЕКСТ ОСТАНОВКИ, собранный кодом (правила G7): какие цели ставились, что принято, какие отказы повторяются, адрес препятствия и ответственный, причины завершения попыток. Результат — названная ПРИЧИНА хождения по кругу и выработанное ИЗМЕНЕНИЕ подхода или входов — записывается и служит основанием продолжения. Продолжение по записи разбора открывает НОВОЕ ОКНО: снова до трёх попыток. Ни разбор, ни разрешение продолжить продвижением к исходной цели не являются. Обращение к ревьюеру — вызов модели по общим правилам этой карточки: адресный вопрос (эта остановка), пакет собирает код, ответ по форме, запись вызова до отправки, учёт расхода.
  · ЗАПИСЬ РАЗБОРА — смысловой договор (поля и способ хранения — детализация модуля): точная остановка и цель, к которым разбор относится; зафиксированный контекст и его источники; независимость ревьюера; причина С ОСНОВАНИЯМИ либо явно названная ГИПОТЕЗА; предлагаемое изменение и его адреса. Сам разбор ничего не меняет — ни граф, ни входы, ни готовность, ни классификацию отказов (Т8). Продолжение применяется отдельно, к СВОЕЙ остановке и один раз: чужой, устаревший или повторно доставленный разбор новую остановку не снимает (Т5).

Ответ не по форме или сбой вызова — остановка сохраняется вместе с причиной неудачи, восстановление относится к ТОМУ ЖЕ обращению. Ревьюер не смог назвать причину либо разбор закончился без пригодного изменения — ступень 2: владельцу передаются известные факты, без выдуманной причины.
  · ИСПРАВЛЕННЫЙ ВХОД — продолжение маршрута G7 «производителю данных» и тоже основание ПЕРВОЙ ступени, но только при содержательных условиях: названы конкретный отказ и вход, с которым шли попытки; новая принятая запись исправляет именно те данные, к которым относится этот отказ; повторная адресная проверка это подтверждает. Новый id, ревизия, время или изменение постороннего поля исправлением не считаются. Установить исправление нельзя — разбор с ревьюером. На второй ступени исправленный вход решения владельца не заменяет. (Это уточнение схемы по маршруту G7, а не слова владельца; принято ревью, запись журнала №168.)
  · Ступень 2 — ВЛАДЕЛЕЦ. Серия снова остановилась, не дав после продолжения первой ступени НИ ОДНОГО нового принятого результата исходной цели, → продолжить можно ТОЛЬКО по решению владельца. Ему уходит объяснение: что пытались, что не сдвинулось, какой разбор был сделан и почему он не помог, что предлагается изменить. Разрешённое владельцем продолжение тоже открывает новое окно до трёх попыток; если и оно не дало нового принятого результата исходной цели, следующая остановка — СНОВА вторая ступень: к ревьюеру лестница не возвращается.
  · На начало лестницу возвращает только ПРОДВИЖЕНИЕ ЭТОЙ ЦЕЛИ — новый принятый результат. История окон, использованная первая ступень и требование решения владельца переживают преемника серии, смену среза и возврат к прежнему предмету: одна смена горизонта вторую ступень не снимает. Владелец вправе решить на любой ступени. Запись «подход изменён» рукой самого исполнителя — без разбора и без подтверждённого исправления входа — остановку НЕ снимает.
  Расход. Учёт расхода вместе со значимостью вопроса и достигнутым результатом — отчётность владельцу; оценку «несоразмерно» даёт владелец по этой отчётности. Автоматического распознавания несоразмерности и скрытого токенного порога нет; никакой сигнал ответ не обрывает.
  Серии: история попыток ведётся по блоку и его срезу. Срез не изменился — серия и счёт продолжаются (из горизонта убрали ДРУГОЙ блок — остановка не снимается). Срез изменился — преемник серии со ссылкой на предшественника и сохранённой историей; изменение входов — основание продолжить только на условиях лестницы после остановки (одна смена горизонта ступень лестницы не меняет) и само продвижением не является; при возврате к прежнему предмету его история действует снова. Переход применяется только после успешного G2 на этот проект, эту версию выбора, эту запись горизонта и этот подготовленный переход — одной транзакцией и один раз; отклонённый горизонт — переход отброшен, серии не тронуты.

ОТКРЫТОЕ РЕШЕНИЕ ВЛАДЕЛЬЦА — одно
  Аварийный выключатель недельного бюджета владельца: нужен ли и с каким порогом. Это НЕ регулятор работы и не условие допуска вопроса, а защита от сбоя (вызов не заканчивается, петля); он сохраняет точку продолжения и сделанного не теряет. До решения — выключен.
```

## Карточки единиц карты — дословно

#### MC1 · Исследовать невыводимый пробел  `model-research`
- **вопрос:** Один пробел = один вопрос с потребителем и требованием к доказательству. Уровень 2 карты (21.09.2026): раскрыт карточками правил «M6 · маршрут пробела и ответ кодом» и «MC1 и MC2 · обращение к модели: пакет вопроса, форма ответа, проверка».
- **почему невыводимо:** Ответа нет ни в принятых записях, ни в инвентаре: нужно чтение конкретных источников и оценка оснований независимым оценщиком.
- **вид источника:** repository_evidence / external_primary_docs / runtime_evidence
- **потребитель:** узел или задача горизонта из поля consumer пробела
- **очередь и учёт:** Вопросы берутся в порядке очереди блоков из M3. Один вызов — один адресный вопрос или согласованный пакет однотипных. Пакет вопроса собирает КОД под вопрос — не весь проект; дочитывание — только по конкретному адресу; ответ — значение и цитаты, основание считает код; законные ответы «нужен источник», «нужно решение владельца», «ответить не могу». Независимый оценщик — отдельной ролью и только после проверок кодом; принимается только supported. Потолков токенов и резервов нет: расход учитывается и ответ не обрывает. Правила — карточки «M6…» и «MC1 и MC2 · обращение к модели».

#### MC2 · Проектное решение: операции и работы  `model-design`
- **вопрос:** Как разбить блок на операции, если контракты допускают несколько разбиений? Какие новые пути, символы, точки входа тестов и условия соединений нужны работе, если их нет в инвентаре и контрактах? Уровень 2 карты (21.09.2026): раскрыт карточками правил «M6 · маршрут пробела и ответ кодом» и «MC1 и MC2 · обращение к модели: пакет вопроса, форма ответа, проверка».
- **почему невыводимо:** Проектное решение, а не факт репозитория: код проверяет предложение против контрактов, соединений, хлеба и атомарности, но не выбирает его. Объявлять такое решение фактом из репозитория запрещено.
- **вид источника:** design-decision (obligation-policy) с основаниями из om-input
- **потребитель:** M4 (операции) или M7 (работы) — по пробелу
- **очередь и учёт:** Для любого блока горизонта, у которого M6 признал пробел проектным решением; блоки — в порядке очереди M3. Два задания: РАСКРЫТИЕ УЗЛА (приёмка — узел целиком; обращение — целиком или частями, делит код) → предложение слоя; РЕШЕНИЕ О НЕДОСТАЮЩЕМ ПОЛЕ ВХОДА → отдельный результат на каждый вопрос. Проверяет код: предложение операций — G3; предложение работ допускается к сборке и принимается после M7 и G5; отклонённое предложение пробел не закрывает. Попытки и остановка — по правилу продвижения (G7); потолков и лимита числа попыток нет. Правила — карточки «MC1 и MC2 · обращение к модели» и «Вызовы модели…».

## Карточки записей-соседей — дословно

#### Серии исправлений (repair-series)  `store-repairs`
- **что хранит:** Серия принадлежит блоку и его срезу горизонта (срез = блок, замыкание его зависимостей в горизонте и его основания). В серии: история попыток — заранее названная цель, причина завершения, принятые результаты, набор отказов — связью со строками журнала отказов (класс и адресат хранит журнал, в серии они не дублируются); счёт подряд идущих попыток без продвижения; состояние остановки с причиной и точкой продолжения. Попытка — завершённый цикл, исход учитывается один раз; повтор доставки попыткой не считается. Лимита ЧИСЛА попыток нет: продвижение обнуляет счёт; третья подряд попытка без продвижения — остановка; перезапуск её не снимает. Продолжение — по лестнице: запись разбора с независимым ревьюером либо подтверждённое исправление входа (назван отказ, исправлены его данные, повторная проверка это подтвердила) — после них новое окно до трёх попыток; при повторной остановке без единого нового результата цели — только решение владельца, и оно тоже открывает окно до трёх попыток. На начало лестницу возвращает только новый принятый результат цели; состояние лестницы хранится в серии и переживает преемника и смену среза. Запись «подход изменён» рукой исполнителя остановку не снимает. Переход при смене горизонта: срез не изменился — та же серия и тот же счёт; изменился — преемник со ссылкой на предшественника и сохранённой историей; применяется только после успешного G2, одной транзакцией и один раз. Правила — карточки «Вызовы модели…» и «G7 · ворота повтора».

#### layer-proposal (предложение слоя)  `st-proposal`
- **что хранит:** { base{graph, frame} — головы на момент предложения, level, source: input | decision, status: proposed | accepted | rejected, verdict?{candidateHash, candidate ref, codes}, nodes[] — полные определения узлов, fills[{obligation, node, port?}], localConnectors[], и ВСЁ, что предложение вводит: artifacts, contracts, joins (соединения входов — без них join_missing), tests, edges, journeys, packets, transfers, anchors; для замены принятого: removes[id узлов], replaces[{obligation, base{node, graph ref}, with, basis}], redefines[id принятых определений, которые предложение переопределяет] }. Ссылка {node, port, contract} без определения узла предложением не является. Проверено тестом: предложение без joins → join_missing, без artifacts → artifact_missing. Исполняемая спецификация: proto/frame.mjs; тесты proto/frame.test.mjs.
