# Задача F1 · M7 · зона раскрытия работ (F7.1)

**Цель.** Определить зону: операции, которые уточняют блоки горизонта с execution needed; представители и готовые блоки в зону не входят.

## Как работать

- Ты воркер блока OM движка OMG. Рабочая копия — `/Users/kostenchuksergey/OMG/.omg/worktrees/om-module`, ветка `om/module`. Работай ТОЛЬКО в ней. Основную копию `~/OMG`, базу `.omg/state.sqlite` и `live-source` не трогай и не читай на запись.
- Писать разрешено ТОЛЬКО в эти файлы: `src/om/work-zone.ts`, `test/om-work-zone.test.ts`, `src/om/frame-obligations.ts`, `test/om-frame-obligations.test.ts`. Нужен другой файл — остановись и сообщи: это отход от задачи, а не твоё решение.
- Источник истины — правила ниже. Они приняты ревьюером. Если правило кажется неверным, неполным или противоречит движку — НЕ обходи его кодом: остановись и опиши противоречие с примером. Поведение продукта сам не выбирай.
- Отсутствующая возможность — типизированный отказ с адресом, не заглушка и не значение по умолчанию.

- Тесты: `node:test` + `node:assert/strict`, своя временная база на тест (образец — `test/storage.test.ts`), без настоящих вендоров, сети и ключей. `ui/` не трогать. push, слияния, теги — запрещены.
- Стиль движка: ESM, относительные импорты с суффиксом `.js`; `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noUnusedLocals`; файлы в kebab-case, без `index.ts`; типы экспортируются рядом с реализацией; комментарии редкие, на английском, объясняют «почему». Отказ движка — `EngineError(code, message, details)` из `src/errors.ts`. Факты о движке: `PREPARATIONS/OM-DESIGN/code/engine-facts-infra.md` и `engine-facts-reuse.md` — сверяй с кодом перед использованием.
- УРОКИ РЕВЬЮ СДЕЛАННЫХ ЗАДАЧ (классы дефектов, за которые код уже возвращали): (1) экспортируемая функция проверяет форму ВСЕХ аргументов до первого обращения к полям и до хранилища — отсутствует, null, не тот тип → `EngineError` с кодом дефекта единицы; обычный `TypeError` — дефект. Отсутствующий набор и явно пустой набор — разные случаи, отсутствующий на `[]` не подменяется. (2) JSON-содержимое копируется и отдаётся только через `sealed()` / `delivered()` из `src/om/refusal.ts`; своё копирование присваиванием по чужим ключам запрещено — ключ `__proto__` теряется и подменяет прототип; объект из чужих ключей строится через `Object.defineProperty` либо `Map`. Инвариант для теста: хэш выданного равен хэшу записи. (3) Точная ссылка доказывает, КАКУЮ запись прочитали, но не её принятие: основание принятия и связь с исходом ворот проверяет та единица, чья это обязанность. (4) Т3 буквально: производная запись сверяется с ЗАФИКСИРОВАННЫМ ИСТОЧНИКОМ — источник перечитывается по точной ссылке, производное выводится из него заново той же функцией и сравнивается; пересчёт хэша собственных полей записи — это самосогласованность, а не вывод заново (так вернули A2). Тест подделки меняет содержимое И пересчитывает id либо хэш; проверяется историческая ревизия источника по точной ссылке — новая голова источника старую запись ложной не делает. (5) Т5 буквально: запрос на переход НАЗЫВАЕТ состояние, из которого идёт (номер попытки, номер остановки, точную ревизию) — запоздавший повтор того же запроса после любых последующих событий распознаётся как уже применённый и на более позднее состояние не действует (так вернули A3: повтор продолжения снимал НОВУЮ остановку). Тест: запоздавший повтор после следующего события и после перезапуска базы. (6) Т6 буквально: НЕупорядоченные наборы (достижения, отмены, отказы, вопросы пакета, основания) нормализуются одной функцией перед записью И перед сравнением, сортировка не зависит от локали, кратность сохраняется; хранимая запись с неканоничным порядком — отказ. Тест: перестановка элементов — тот же исход без ревизии. (7) Передача соседу несёт ОДНОЗНАЧНУЮ сохранённую связь с конкретной записью или строкой соседа (id либо точная ссылка), а не пару «название + цель»: два законных события с одинаковыми названием и целью обязаны оставаться различимыми. (8) Изменяющая операция отделяет ПОДГОТОВКУ (все проверки → готовые записи и охраны, без записи) от ЗАПИСИ: соседняя единица, которой по правилам нужна ОДНА транзакция на несколько записей, включает подготовленное в свой writeGuarded, а не вызывает операции по очереди (частичный результат) и не переписывает твою логику. (9) Каждый исход, который правило называет (например «разбор завершён без пригодного изменения — ступень 2»), — это ПРИМЕНЯЕМЫЙ переход, сохранённый в истории записи, а не только отказ: отказ ничего не сохраняет, и следующий запрос проходит так, будто исхода не было (так вернули A3.1). Проверь по правилам своей единицы: у каждого названного исхода есть операция, которая его записывает, и тест, что после него запрещённое остаётся запрещённым — в том числе после перезапуска и у преемника. (10) Если сосед по правилам пишет свою запись В ТОЙ ЖЕ транзакции, что твой переход (основание, разбор, решение, подтверждение), подготовка принимает основание в двух видах — уже записанное (точная ссылка) и готовящееся в этой транзакции (предлагаемая запись: подготовка сама вычисляет её точную ссылку, проверяет её ТОЙ ЖЕ функцией содержания и включает в возвращаемый набор записей). Подготовка, которая умеет только читать основание из хранилища, вынуждает соседа коммитить его отдельно — и открывает окно (так второй раз вернули A3.1). (11) Ничто, от чего зависит продвижение, класс или маршрут, не принимается со слов вызывающего: достижение, отмену, принятость выводит ПОСТАВЩИК из своей записи по точной ссылке (таблица поставщиков принятия `src/om/achievements.ts`); вида, которого нет в таблице, — отказ, а не «поверим». (12) Положительный вывод требует ДОСТАТОЧНЫХ РАЗЛИЧАЮЩИХ оснований: не хватает обязательной роли либо кандидатов несколько без различающего основания — «неизвестно», а не первый по порядку и не «последняя ветка по умолчанию»; устойчивая сортировка выбор первого не обосновывает (так вернули A4). (13) Перед сдачей убедись, что новые тесты ЛОВЯТ дефект: временно верни ошибочное поведение в `dist/` (не в исходниках), увидь падение теста, затем пересобери. (14) ОДИН класс — ОДИН механизм установления: если обычный путь ВЫВОДИТ класс, маршрут или статус из источников (таблица решений над прочитанными записями), то любой второй путь к тому же результату (снятие преграды, разбор, повтор, восстановление) обязан звать ТУ ЖЕ выводящую функцию над теми же прочитанными источниками; поле `class` чужой записи — заявление, которое сверяется с выводом, а не заменяет его: противоречие или недостаточность → отказ без записи (так второй раз вернули A4: `weighLift` принимал класс из разбора по форме ссылок, не читая содержимое). Тест: основания, из которых таблица выводит другой класс либо «неизвестно», преграду не снимают — ни сохранённым, ни готовящимся разбором; ни снятия, ни записи разбора в базе после отказа нет. (15) ИСТОРИЯ и ГОЛОВЫ — разные вещи: историческое основание (запись, по точной ссылке на которую серия уже перешла) проверяется по точной ссылке и новой ревизией не отменяется; в охраны транзакции (guards) идут ТОЛЬКО изменяемые головы, от которых зависит актуальность результата, — зато ВСЕ фактически прочитанные, включая те, что читает вызванный сосед (например, снятые преграды в stopContext): нет сведений о прочитанном у соседа — расширь его интерфейс, а не охраняй меньше (так вернули A5). Тест: законная новая ревизия исторического источника — отчёт стоит; изменение любой прочитанной головы между проверкой и записью — отказ записи. (16) Позднейшее событие само по себе НЕ доказывает неудачу прежнего средства: «следующая остановка после продолжения» не значит «продолжение не помогло», если между ними записан принятый результат или граница окна; вывод о неудаче — только из сохранённых результатов и границ окон, с тестом на историю с наследованием (так вернули A5). (17) Точная ссылка НЕ заменяет ни проверку ПРИНАДЛЕЖНОСТИ, ни СОДЕРЖАНИЕ: читая чужую запись как источник объяснения или основания, сверяй ВСЕ поля адреса, включая цели/предмет (подделка с верными пространством имён, видом, ревизией и хэшем, но другими целями — отказ), и передавай получателю содержание относящихся строк (код, цель, предмет, происхождение, записанный способ исправления, класс, адресат) с однозначной связью с источником, а не только хэш и ссылку (так вернули A5). (18) СОСТОЯНИЕ ≠ ИСТОРИЯ: текущее состояние соседа (лестница, окна, цели стоящей остановки) — не полная история его событий; сведения, которых в состоянии нет (цели уже отвеченной остановки, границы прежних окон после сброса), НЕ заменяются приближённой проверкой («все цели когда-то встречались») и не пересчитываются вторым алгоритмом — их отдаёт ОДИН точный источник: сосед выводит историю тем же выводом, которым строит и проверяет состояние, и отдаёт её интерфейсом (расширение интерфейса соседа — стык реализации, не правило продукта). Тест: потерянная цель, лишняя цель из другого окна, чужая цель — отказ; перестановка — успех; после сброса лестницы промежуточная остановка не теряется и результат приписывается своему окну (так второй раз вернули A5). (19) ПОЛНОТА НАБОРА проверяется по сохранённым ИСТОЧНИКАМ, а не по перечислению самого набора: реестр/ведомость/список, который выводит каждую свою строку из записей, обязан также доказать, что в нём есть строка для КАЖДОЙ записи-источника (перечисление источников по пространству имён или по хранимому индексу), иначе строку можно удалить новой ревизией и все пути пройдут (так вернули E1). Тест: частичная и полная потеря набора, включая уже закрытую запись, на КАЖДОМ пути, обращающемся к другой записи, а не к потерянной. (20) ЗАЯВЛЕННЫЙ ПОТРЕБИТЕЛЬ — ПРОВЕРЕННЫЙ ПУТЬ: если пакет называет соседа потребителем твоего интерфейса, напиши тест, который проходит ЕГО путь через законные операции (например, обращение к ревьюеру при сохранённой остановке, когда следующая попытка запрещена), а не только «обычный» путь; интерфейс, до которого потребитель не может дойти, — дефект (так вернули E1). (21) ДОПУСК ТЕКУЩЕЙ ПОДГОТОВКИ ≠ ИСТОРИЧЕСКОЕ ЧТЕНИЕ: перечитывание уже сохранённой записи проверяет источники по точным ссылкам как историю; подготовка НОВОЙ записи или её использование в транзакции соседа обязаны проверить ТЕКУЩУЮ актуальность оснований по семантике движка (например, принятость стадии: Pipeline.inspect считает стадию stale при сдвиге головы доказательства) и вернуть полное замыкание охран на эти изменяемые зависимости — в том числе когда запись уже существует и writes пуст. Это два разных пути; общий путь нельзя ни ослабить, ни ужесточить для обоих. Тест: сдвиг зависимости до подготовки, после подготовки перед общей записью, при повторном использовании; историческое чтение после сдвига и перезапуска остаётся успешным (так вернули B1). (22) ОТРИЦАТЕЛЬНЫЙ РЕЗУЛЬТАТ ПРОВЕРКИ ≠ ИСКЛЮЧЕНИЕ ЕЁ ИСПОЛНЕНИЯ: «данные не прошли» приходит из результата проверки (state/findings) и становится типизированным отказом; исключение при исполнении проверки (TypeError, EngineError чужого кода, сбой хранилища) передаётся выше без подмены — общий catch с запасной веткой «отказ производителю» запрещён. Предусмотренное исключение-дефект-данных преобразуется только по явному договору с его кодом. Тест: сбой в чтении посреди проверки сохраняет исходное исключение на всех публичных путях и не оставляет записей (так второй раз вернули B1). (23) САМОСОГЛАСОВАННОЕ ДОКАЗАТЕЛЬСТВО ≠ ПРИНЯТИЕ: proof, хэш которого совпадает с проекцией и который ссылается на верный верх, записать может любой — принятие слоя подтверждается по его НАСТОЯЩИМ сохранённым основаниям (источники исследования и вывод слоя у движка; точный принятый кандидат и исход своих ворот у OM) ОДНИМ общим механизмом для всех читателей. Тест: новая ревизия слоя с пересчитанной проекцией, хэшем и proof, но без исследования и принятия — отказ на всех публичных путях и уровнях (так вернули C2). (24) ПОЛНОТА КОНЦОВ ≠ СОХРАНЕНИЕ ПОТОКОВ: соответствие верхних и нижних связей проверяется ПОТОКАМИ целиком (производитель, порт, якорь, потребители) и взаимно однозначно — два верхних потока не сливаются в одну нижнюю привязку; законная кратность потребителей и произвольные имена нижних портов по записанному соответствию сохраняются. Тест меняет И нижний граф, И записанное соответствие с пересчётом хэшей (так вернули C2). (25) ИСПРАВЛЕНИЕ КЛАССА ОХВАТЫВАЕТ СОСЕДА: если твой механизм уже реализован у принятого соседа (та же проверка другой реализацией), класс закрывается ОДНИМ общим модулем, на который переводятся оба, — а не второй, «правильной» копией у себя; иначе два читателя расходятся на одном входе (так второй раз вернули C2). Тест: один и тот же изменённый вход через обоих читателей даёт одинаковый исход. (26) ПЕРВЫЙ ПРОХОД — ЗАКОННЫЙ ПУТЬ: сохраняемый интерфейс обязан работать от начального состояния (принятые стадии и L1, без L2/L3), а не только на полностью раскрытой фикстуре; если обязательный источник ещё не может существовать, он явно сообщает ПРОВЕРЯЕМЫЙ исход «ещё не возможен», выведенный из точных оснований текущей стадии, — не пустоту по умолчанию и не перехват любого отказа соседа; после появления основания этот исход не может скрыть настоящие данные. Тест — настоящий путь от начального состояния, затем появление источника (так вернули D1). (27) ГРАНИЦА ПОЛНОМОЧИЙ — ПО ИЗМЕНЕНИЮ, А НЕ ПО НАЛИЧИЮ: «эта задача не трогает уровень N» проверяется сравнением итога с ПРИНЯТЫМ определением (что изменилось, что исчезло), а не по тому, встречается ли уровень N во входящем объекте: неизменённое принятое содержимое другого уровня законно присутствует, а его отсутствие во входящем определении не должно его удалять. Учитывать и исчезнувшие ссылки, а не только новые (так вернули C4). (28) ЗАЩИЩАЕМОЕ = ЗАМЫКАНИЕ ЗАВИСИМОСТЕЙ: защищая объект, защищай и всё, во что его типизированные ссылки разрешаются (порт → контракт; результат/связь → артефакт → контракт и т. д.), по типизированным связям графа, а не поиском строк; равенство самого объекта ничего не доказывает, если его ссылки ведут в изменённые определения. Не замораживать при этом весь граф — законные изменения вне замыкания должны проходить (так второй раз вернули C4). (29) СОВПАДЕНИЕ ID ≠ СОХРАННОСТЬ СОДЕРЖАНИЯ; ЗАПИСАННОЕ ДОЛЖНО ЧИТАТЬСЯ: переносить прежнее (заполнение, привязку, ответ) по совпадению идентификатора нельзя — пригодность проверяется по правилам той единицы, что будет это читать (роль, контракт, артефакт, поток); непригодное уходит в историю, требование остаётся открытым. Результат подготовки обязан проходить те же проверки, что его последующее чтение: успешная запись, которую её собственные потребители отвергают, — дефект. Тест: запись → чтение всеми потребителями → повтор → перезапуск (так вернули C5). (30) СОВМЕСТНОСТЬ ОСНОВАНИЙ: несколько источников одного вывода должны принадлежать ОДНОЙ сборке/объекту — каждый сопоставляется с сохранёнными входами отказного объекта (точные предложения, база, уровень, контекст), а не проверяется только по отдельности; по отдельности верная запись другой сборки не годится. Связи отдаёт общий наблюдающий читатель, не восстановление по головам или совпадению содержимого. Тест: подмена одного источника точной записью другой сборки — отказ на всех путях (так вернули C5.2). (31) СТАНДАРТНЫЙ ПРОГОН — БЕЗ ФЛАГОВ: полный `npm run check:backend` обязан проходить стандартной командой, без NODE_OPTIONS и прочих поправок среды; тест, которому нужна увеличенная куча, ломает общий прогон всем следующим задачам. Каждый тест закрывает свои базы и не удерживает данные между случаями; тяжёлые таблицы случаев строятся так, чтобы память не росла с числом случаев. В отчёте — длительность прогона и, для тяжёлых наборов, пик памяти (так до ревью вернули C5.2). (32) ПРИЗНАК «ТЕКУЩИЙ РЕЖИМ» ВКЛЮЧАЕТ ТОЛЬКО АКТУАЛЬНОСТЬ: флаг current/historical переключает лишь проверку сегодняшних голов и выдачу охран; проверки связности и совместности точных оснований (с сохранённым контекстом своего прохода/сборки) действуют ВСЕГДА, одной функцией — на подготовке, историческом чтении, повторе и у поставщика. Тест: запись, которую подготовка отвергает, вписанная напрямую с согласованными хэшами, отвергается и историческим читателем, и после перезапуска (так вернули D2). (33) ИДЕНТИЧНОСТЬ — У ОБЪЕКТА В СОСТОЯНИИ, А НЕ У СТРОКИ ИМЕНИ: соответствие переименования связывает объект конкретной ревизии (узел или пара «узел, порт» в ревизии N) с объектом ревизии N+1; одинаковые строки имён сквозь историю безусловно не объединяются. Взаимные и циклические перестановки имён (a↔b, a→b→c→a) при однозначном соответствии сохраняют различимость объектов и прежние ключи; настоящие split/merge — отказ. Тест: перестановка имён узлов и портов одной заменой, затем содержательное изменение и возврат, с перезапуском (так второй раз вернули D2). (34) ОБНОВЛЕНИЕ НЕЗАВИСИМОГО ИСТОЧНИКА НЕ СБРАСЫВАЕТ ПРОИЗВОДНОЕ: если запись выводится цепочкой (корень → принятые решения → версия), обновление одного источника (например, инвентаря) проходит через ТОТ ЖЕ общий вывод и сохраняет проверенные решения; если изменение основания требует нового разрешения — явный исход, а не молчаливая запись корня заново. Тест: принятое решение → обновление независимого источника → решение на месте, историческое чтение (так вернули D3). (35) У ПРИНЯТОГО СОСТОЯНИЯ, КОТОРОЕ МОЖЕТ УСТАРЕТЬ, ЕСТЬ ПРОВЕРЯЕМЫЙ ВЫХОД: если применённое значение перестаёт быть применимым (изменились источники), должен существовать законный переход, возвращающий задачу в исходное открытое состояние (с историей и защитой от использования устаревшего значения), — иначе блокировка всего объекта становится тупиком. Тест проходит весь жизненный цикл: применение → устаревание → возврат → новое подтверждение → повторное применение, с перезапуском (так вернули D3.1). (36) СТОИМОСТЬ ОПЕРАЦИИ С ОБЩИМИ ИСТОРИЧЕСКИМИ ОСНОВАНИЯМИ — ИНВАРИАНТ, А НЕ СКОРОСТЬ: в пределах одной верхнеуровневой операции (подготовка/запись/чтение истории) каждое неизменяемое историческое основание подтверждается один раз на ключ (читатель, представление Store/Proxy, проект, точная ссылка, влияющие параметры); число разворачиваний зависит от числа уникальных оснований и связей, а не от числа путей к ним; следующий внешний вызов читает заново, текущие головы и охраны не кэшируются; закрепляется счётчиком чтений/выводов на масштабе в обычном тесте, миллисекунды — только диагностика (так вернули D3.1 третий раз). (37) ДЕЙСТВИЕ ПОД ПОПЫТКОЙ ПРИНАДЛЕЖИТ ЕЁ ЗАРАНЕЕ ОБЪЯВЛЕННОЙ ЦЕЛИ: наличие открытой попытки без остановки и свежая голова серии не доказывают, что вопрос, пакет, вызов или результат относятся к ЭТОЙ цели; принадлежность проверяется по проверяемым адресам и договору результата (для вопросов-фактов — ключ линии пробела в goal.questions и ожидаемый результат по договору D5/D2, потребитель серии), до выдачи вопросов и записи, и восстанавливается при историческом чтении; сравнения текста или одного ключа цели недостаточно. Тест: законная открытая попытка с ЧУЖОЙ целью и законные источники — отказ без записей (так вернули E2). (38) ТЕКУЩИЙ ДОПУСК ПРОВЕРЯЕТ ЛИНИЮ, А НЕ ГОЛОВУ ОДНОЙ ЗАПИСИ: если у объекта бывает преемник под другим id (серия → преемник, запись → новая эра), свежесть головы прежнего id не доказывает, что линия текущая; допуск нового действия читает текущую линию общим механизмом, а переход к преемнику защищается CAS предшественника в той же транзакции (проверка «следующего id нет» перед записью гонку не закрывает). Тест: законный преемник появился — новое действие по прежней линии отвергается, в том числе при появлении преемника между подготовкой и записью в обоих порядках; история и поздний повтор прежнего действия сохраняются (так нашли в E4 обход принятого A3.3/E1). (39) НЕОБРАТИМЫЙ ВНЕШНИЙ РЕЗУЛЬТАТ СОХРАНЯЕТСЯ ДО ПРИМЕНЕНИЯ И НЕЗАВИСИМО ОТ НЕГО: полученный ответ внешнего исполнителя, израсходованный ресурс, завершённый процесс записываются неизменяемо с читаемым терминальным исходом физического действия; отказ применения (смена оснований, конкурентное завершение попытки, конфликт) не теряет обмен, не оставляет действие «в работе» навсегда и не перезаписывает уже сохранённый законный исход; основания отказа выводятся из полного проверенного допуска. Тест: второй Store меняет состояние между отправкой и применением — ответ и расход сохранены, частичного результата нет, история и повтор после перезапуска читаются, повторной отправки нет (так вернули E4). (40) СОХРАНЁННОЕ ПРОМЕЖУТОЧНОЕ СОСТОЯНИЕ — НЕ ТЕРМИНАЛ, ВОЗОБНОВЛЕНИЕ — ТЕМ ЖЕ ПЕРЕХОДОМ: у многошаговой операции с внешним эффектом явный автомат состояний; одна функция перехода исполняется и при первом проходе, и при возобновлении из ЛЮБОГО сохранённого состояния (без нового внешнего действия, если оно уже выполнено); повтор завершённой операции и возобновление незавершённой различаются явно; конечными считаются только объявленные терминальные состояния, промежуточное читатели и соседи за завершение не принимают. Тест: остановка исполнения после каждой сохраняющей транзакции → перезапуск → предусмотренный результат, внешнее действие и расход не удваиваются (так вернули E4 второй раз). Для операций с ВНЕШНИМ ИСПОЛНИТЕЛЕМ — то же и при ПОТЕРЕ ИСПОЛНИТЕЛЯ (владельца или поставщика): каждый сохраняемый префикс либо законно продолжается, либо достигает проверяемого исхода; запрет дублирования без выхода — тупик; граница передачи запроса доказывается записью, зафиксированной ДО передачи; живое исполнение не объявляется потерянным; неизвестный расход не выдумывается; неопределённость факта отправки остаётся видимой (так вернули E4 третий раз, разбор №575). (41) ИЗМЕНЕНИЕ ФОРМУЛЫ ВЫВОДА — НОВАЯ ЭРА: если меняется функция, которой запись выводится заново из своих источников (фильтр, проекция, порядок, состав), новые записи несут доказуемый маркер договора производителя, а сохранённые — воспроизводятся формулой своей эры; без маркера старая история станет «подделкой». Граница эры доказывается сохранёнными основаниями, без перебора алгоритмов до успешного чтения; зелёные прежние тесты совместимость истории не доказывают. Тест: старый производитель (код базы) сохраняет записи → новый читатель читает их после перезапуска; новая подготовка применяет новую формулу (так вернули F1; стык разрешал оркестратор).

```text
  Места: отсрочка и линии в M5; G4b; M3.

Т10. Продуктовый выбор в коде не делается. Если для исправления надо выбрать СМЫСЛ ограничения (что считать продвижением, что считать несоразмерным расходом, замена адресации, аварийная защита бюджета) — это карточка решения владельца; до решения действует названное осторожное умолчание.

Т11. Политика неизменяема, выданное — копия. Таблицы правил не меняются во время работы; запись, отданная потребителю, не делит изменяемых объектов ни с политикой, ни с источником, из которого ворота выводят эталон. Это требование к модулю; решений схемы оно не меняет.
```

### Уровень 2 · Правила · M7 · работы и соседи  `rules-m7`

```text
Получает: принятый слой операций и запись каркаса операций; om-horizon; предложения слоя работ; квитанции артефактов; поставщика владельцев путей.
Достоверное основание: те же, что у M4 (Т1–Т3), плюс: готовность — только названное M2 основание этого результата; владение путём — подтверждённый прежний писатель с той же границей.
Выдаёт и хранит: каркас работ — ТЕ ЖЕ правила, что каркас операций, уровнем ниже (обязательства: исход каждой операции и каждый конец каждого потока уровня операций, включая локальные связи между подблоками одного блока); граф уровня работ; план исполнения; пакеты соседей.
Правила:
  · Конец связи у настоящей работы привязан к месту в коде — иначе действующая проверка движка откажет.
  · Две РАЗНЫЕ границы плана исполнения. ПОТРЕБИТЕЛЬ вне плана (производитель в плане) — действующий механизм «спящая связь»: отдельная привязка с якорем и тестом пробуждения. ПРОИЗВОДИТЕЛЬ вне плана поставляет готовый результат по названной квитанции (правило доставки из передачи M2 → M4 → M7); внешний источник обрабатывается как внешний. Само отсутствие производителя в плане спящей связи не создаёт и обязательства пробуждения не порождает: блок «результат уже есть» исключён из исполнения, его настоящая работа поставляет вход по квитанции. Якорь спящей связи выводится механически: работа-производитель с исходом = артефакт связи; тест — тест производителя, покрывающий связь. Вывести нельзя — отказ; классификатор возвратов превращает его в адресное проектное решение, если нужен выбор, либо в дефект вывода, если принятое определение потеряно.
  · Пакет соседей ВЫВОДИТСЯ из принятого графа, модель его не присылает. На каждый конец каждой связи работы — запись: связь, артефакт, контракт, направление (читаю / пишу / получаю владение / передаю владение / требую), свой порт и место в коде, порт и место в коде соседа, цепочка соседа работа → операция → блок, маршрут возврата, доставка: сосед в этом же плане / вход по квитанции со ссылкой / внешний источник / спящий потребитель.
  · Адрес подблока — не «где лежит работа», а тот конец верхней связи, который работа УТОЧНЯЕТ (Т2). Уточняет несколько концов — адресов столько, сколько принято и записано в каркасе (Т1, Т6); записи нет — отказ.
  · Представитель помечен честно: операция и контракт обмена известны, работа ещё не спроектирована. Исполнителю не обещается существующий код потребителя; при раскрытии нужны новые привязки и проверка совместимости.
  · Основание результата ищется одинаково для всех видов входа (данные и requires): среди блоков, которые производитель уточняет, — тот, у кого M2 назвал основание этого артефакта; два разных названных основания — отказ.
  · Ровно один пакет на работу; вход без источника задачу исполнителю не пускает.
Разрешённые изменения: как у M4; плюс явный переход каркаса работ на законно изменённый слой операций.
Отказ и продолжение: обратные маршруты — в передаче M2 → M4 → M7.
Открытое: проверки атомарности — в принятой карточке правил «G5 · атомарность работы и пакет задачи»; управляющий сосед (requires, владение путём) адресуется по расположению работы — у него нет конца связи, который можно уточнять.
```

### Уровень 2 · Передача · M2 → M4 → M7 · горизонт → операции → работы  `rules-handoff-horizon`

```text
ЧТО ПЕРЕДАЁТСЯ И ЧТО ПОЛУЧАТЕЛЬ СЧИТАЕТ ДОКАЗАННЫМ

M2 → M4. Запись om-horizon: блоки горизонта; по каждому — refinement (accepted | needed: есть ли принятое настоящее раскрытие) и execution (needed | available с основанием); граница — блоки вне горизонта, у которых есть И результат, И принятое раскрытие; адреса внешних входов; исключения владельца с причиной и условием возврата; хэш (в него входят версия выбора, исключения и основания).
  M4 считает доказанным: горизонт замкнут — каждый производитель, нужный блоку горизонта (по связям данных, requires и передачам владения), либо в горизонте, либо на границе.
  M4 НЕ считает доказанным: что принятое раскрытие означает готовый результат; что квитанции подлинны (это M8).
  Правило: «раскрыт на карте» ≠ «результат есть». Граница — только при обоих признаках. Блок с результатом, но без раскрытия добирается в горизонт РАДИ РАСКРЫТИЯ: исполнять его не нужно, но конкретный подблок-производитель должен быть известен.
  Основание готовности — блок → {артефакт: точная ссылка на квитанцию} на КАЖДЫЙ результат, который у блока берёт горизонт, включая исход выбранной фичи. Одна «квитанция на блок» основанием не считается. Непокрытый результат — адресный отказ (блок и артефакт).

M4 → M7. Принятый слой операций и запись каркаса операций: какой конец какого потока какой связи закрыт каким узлом и портом; какие узлы — представители; хэши слоя.
  M7 берёт ЗОНУ: операции, которые УТОЧНЯЮТ (Т2) блоки горизонта с execution needed. Представитель операции в зону не входит.
  Блок с execution available в зону не входит — повторное исполнение не выводится. Его производители обязаны быть НАСТОЯЩИМИ принятыми работами, а вход от них принимается только по квитанции, которую M2 назвал основанием именно этого результата: квитанция названа на эту работу, с её подписью и хэшем контракта, и она же — текущая квитанция артефакта (иначе компилятор прочтёт другую).
  M7 НЕ проверяет: подлинность коммита, дерева, плана и прогона квитанции — это действующий resolveArtifact на стыке с M8.

ОБРАТНЫЕ МАРШРУТЫ (Т8)
  · Результат «есть», а настоящей работы-производителя нет; либо основание не годится, устарело, названо на чужую работу или не названо вовсе → адресный отказ (связь или ребро, производитель, блок, артефакт) → через G7 пересмотр готовности в M2: исправить основание либо снять признак готовности решением. Автоматически готовность не меняется и повторное исполнение не запускается.
  · Слой операций законно изменён и принят тем же каркасом, когда слой работ уже принят → каркас работ ЯВНО переходит на новую базу: заполнения, чьё обязательство сохранилось, переносятся; остальные уходят в историю; новые обязательства обрабатываются обычным порядком. Правка слоя в обход каркаса — отказ, переход не выполняется.
  · Незаполненное обязательство зоны → адресный пробел в M5 вместе с соседями по связи.

M7 → M9 → компилятор. Граф уровня работ: работы с местом в коде и тестами; привязки уровня работ — действующие и спящие (якорь и тест пробуждения — только для ПОТРЕБИТЕЛЯ вне плана; вход от производителя вне плана идёт по названной квитанции, от внешнего источника — как внешний); план исполнения = настоящие работы, уточняющие операции зоны; пакет соседей каждой работы. Всё выводится из ОДНОГО зафиксированного снимка графа вместе с записью каркаса работ и основаниями доставки — не из текущих голов записей в момент выдачи задачи.
```

## Карточки единиц карты — дословно

#### M7 · Вывести атомарные работы  `mech-l3`
- **цель:** Задачи, которые исполнитель делает без загрузки всего проекта.
- **что делает:** Запускается после G4b. Зона работ — операции, УТОЧНЯЮЩИЕ блоки горизонта, которым нужно исполнение; блок «результат уже есть» повторно не исполняется. Каркас работ — те же правила, что каркас операций, уровнем ниже. Сосед-ПОТРЕБИТЕЛЬ вне плана исполнения — спящая связь с якорем и тестом пробуждения; ПРОИЗВОДИТЕЛЬ вне плана поставляет результат по названной квитанции. Для каждой работы КОДОМ выводится пакет соседей: связь, контракт, направление, порты, место в коде, цепочка работа → операция → блок, откуда придут данные. Кандидат слоя работ собирается (в том числе из предложений MC2 «к сборке») и проверяется G5; сборка всегда раньше проверки. Пакет задачи вместе с соседями проверяется против ТЕХНИЧЕСКОЙ ВМЕСТИМОСТИ запроса исполнителя. Правила — карточка «M7 · работы и соседи».
- **вход:** graph уровня операций и запись каркаса операций; horizon; ответы и предложения; квитанции артефактов
- **выход:** graph (уровень работ для горизонта, план исполнения); запись каркаса работ; пакеты соседей
- **ворота:** G5 «Ворота атомарности»

#### F7.1 · workZone — зона раскрытия работ  `f7-zone`
- **цель:** Работы выводятся только там, где нужно исполнение; готовый результат повторно не исполняется.
- **что делает:** workZone(graph, horizon, identityOps) → множество операций: операции блоков принятого горизонта, у которых horizon.execution[блок].state = needed. Блок с execution available (в том числе добранный в горизонт ради раскрытия) в зону НЕ входит: его производители обязаны быть настоящими принятыми работами с годной квитанцией (F7.4), иначе отказ horizon_producer_unrefined и пересмотр готовности в M2. Операция-представитель в зону не входит. ОТСУТСТВИЕ: горизонт без сведений о готовности блока (запись прежней редакции) — отказ horizon_execution_missing, а не молча пустая зона. Операция относится к блоку, если УТОЧНЯЕТ его — вложенностью или явным realizes (действующий RefinementRelations; вердикт №3 по M7, п.2), а не только лежит в нём: операции, структурно помещённые в чужой блок и реализующие нужный, в зону входят.
- **вход:** принятый граф уровня 2; запись om-horizon (nodes, execution с основаниями); признаки identity принятого каркаса уровня 2
- **выход:** зона — множество id операций → F7.2
- **ворота:** G5 «Ворота атомарности»

## Карточки записей-соседей — дословно

#### connection-frame (каркас обязательств уровня N)  `st-frame`
- **что хранит:** ПРИНЯТЫЙ каркас уровня N: { project, level, candidateHash, fills[{ obligation, node, port?, source: accepted | identity, basis }] }. Новая ревизия появляется только при принятии кандидата (F4.6); подготовка кандидата эту запись не трогает — поэтому охранная ссылка на неё остаётся действительной до принятия. Признак identity хранится ЗДЕСЬ, а не в узле (схема узла закрыта), и переживает принятие: принятый представитель остаётся представителем. Исторический слой без каркаса считается целиком настоящим. Обязательства не хранятся — они чистая функция верхнего слоя и горизонта (F4.1) и пересчитываются. Обязательство двух видов: connection-end { connector, artifact, role producer | consumer, upper{node, port} } и block-outcome { upper.node, artifact }; зона horizon | outside; у producer и block-outcome одно заполнение, у consumer — одно или несколько. Id обязательства = хэш(вид, connector, уровень, роль, upper.node, upper.port). При смене идентификаторов верха соответствие старое → новое — только по объявленному переименованию; иначе новая работа с основанием. Расход и попытки учитываются на блоке (серия, ведомость G8): смена id их не обнуляет, ответ на старое обязательство на новое не переносится. M7 и пакет контекста читают только принятую ревизию по точной ссылке. Исполняемая спецификация: proto/frame.mjs; тесты proto/frame.test.mjs. Редакция 3: запись каркаса несёт layerHash — хэш проекции принятого слоя; по нему проверяется, что записанное соответствие относится к действующему слою.

#### horizon (кандидат горизонта) и om-horizon (исход G2)  `st-horizon`
- **что хранит:** horizon { choiceVersion, features[исходы], nodes[блоки], refinement{блок: accepted | needed} — переиспользуется ли принятое раскрытие, execution{блок: {state: available, basis} | {state: needed}} — доступен ли уже результат блока; у доступного хранится ТОЧНАЯ ссылка на основание (квитанция: id, revision, hash), она входит в хэш горизонта — смена квитанции даёт другой горизонт, даже если блок внутри горизонта, а не на границе, boundary[{block, basis}] — только блоки, у которых есть И подтверждённо доступный результат, И принятое настоящее раскрытие (иначе каркас не найдёт конкретного подблока-производителя), externalInputs[{consumer, connector, source}] — адреса связей с внешними источниками, собранные по ОКОНЧАТЕЛЬНОМУ горизонту и всем его привязкам: не зависят от порядка обхода, от перестановки фич и от того, каким путём источник вошёл в горизонт, excluded[{block, reason, returnCondition}], hash } — хэш включает версию выбора и исключения: другая версия выбора — другой горизонт даже при тех же узлах. om-horizon { project, choiceVersion, horizonHash, state: accepted | refused } — на неё ссылается исход G2 при применении перехода серий (F2.2). Принятая запись обязана ссылаться на фактически проверенный горизонт; кандидат слоя и исход G3 сохраняют ссылку на этот же принятый горизонт (стык с F4.5/F4.6 — требование к модулю). Исполняемая спецификация: proto/horizon.mjs; тесты proto/horizon.test.mjs. Основание готовности блока (в execution и boundary) — не одна ссылка на блок, а { артефакт: ссылка на квитанцию } на КАЖДЫЙ результат блока, который берёт у него горизонт (вердикт №1 по M7, п.3).

#### Записи OM в SQLite  `store-records`
- **что хранит:** om-input, horizon и om-horizon, series-transition, block-weight, call-record, gaps, answers, graph и graph-layer, feasibility — все с id/revision/hash; проекции только читают (инвариант). Состав каждой записи — в её карточке уровня 2; серии исправлений, ведомость расхода и журнал отказов — отдельные карточки.
