Отсутствующий набор и явно пустой набор — разные случаи, отсутствующий на `[]` не подменяется. (2) JSON-содержимое копируется и отдаётся только через `sealed()` / `delivered()` из `src/om/refusal.ts`; своё копирование присваиванием по чужим ключам запрещено — ключ `__proto__` теряется и подменяет прототип; объект из чужих ключей строится через `Object.defineProperty` либо `Map`. Инвариант для теста: хэш выданного равен хэшу записи. (3) Точная ссылка доказывает, КАКУЮ запись прочитали, но не её принятие: основание принятия и связь с исходом ворот проверяет та единица, чья это обязанность. (4) Т3 буквально: производная запись сверяется с ЗАФИКСИРОВАННЫМ ИСТОЧНИКОМ — источник перечитывается по точной ссылке, производное выводится из него заново той же функцией и сравнивается; пересчёт хэша собственных полей записи — это самосогласованность, а не вывод заново (так вернули A2). Тест подделки меняет содержимое И пересчитывает id либо хэш; проверяется историческая ревизия источника по точной ссылке — новая голова источника старую запись ложной не делает. (5) Т5 буквально: запрос на переход НАЗЫВАЕТ состояние, из которого идёт (номер попытки, номер остановки, точную ревизию) — запоздавший повтор того же запроса после любых последующих событий распознаётся как уже применённый и на более позднее состояние не действует (так вернули A3: повтор продолжения снимал НОВУЮ остановку). Тест: запоздавший повтор после следующего события и после перезапуска базы. (6) Т6 буквально: НЕупорядоченные наборы (достижения, отмены, отказы, вопросы пакета, основания) нормализуются одной функцией перед записью И перед сравнением, сортировка не зависит от локали, кратность сохраняется; хранимая запись с неканоничным порядком — отказ. Тест: перестановка элементов — тот же исход без ревизии. (7) Передача соседу несёт ОДНОЗНАЧНУЮ сохранённую связь с конкретной записью или строкой соседа (id либо точная ссылка), а не пару «название + цель»: два законных события с одинаковыми названием и целью обязаны оставаться различимыми. (8) Изменяющая операция отделяет ПОДГОТОВКУ (все проверки → готовые записи и охраны, без записи) от ЗАПИСИ: соседняя единица, которой по правилам нужна ОДНА транзакция на несколько записей, включает подготовленное в свой writeGuarded, а не вызывает операции по очереди (частичный результат) и не переписывает твою логику. (9) Каждый исход, который правило называет (например «разбор завершён без пригодного изменения — ступень 2»), — это ПРИМЕНЯЕМЫЙ переход, сохранённый в истории записи, а не только отказ: отказ ничего не сохраняет, и следующий запрос проходит так, будто исхода не было (так вернули A3.1). Проверь по правилам своей единицы: у каждого названного исхода есть операция, которая его записывает, и тест, что после него запрещённое остаётся запрещённым — в том числе после перезапуска и у преемника. (10) Если сосед по правилам пишет свою запись В ТОЙ ЖЕ транзакции, что твой переход (основание, разбор, решение, подтверждение), подготовка принимает основание в двух видах — уже записанное (точная ссылка) и готовящееся в этой транзакции (предлагаемая запись: подготовка сама вычисляет её точную ссылку, проверяет её ТОЙ ЖЕ функцией содержания и включает в возвращаемый набор записей). Подготовка, которая умеет только читать основание из хранилища, вынуждает соседа коммитить его отдельно — и открывает окно (так второй раз вернули A3.1). (11) Ничто, от чего зависит продвижение, класс или маршрут, не принимается со слов вызывающего: достижение, отмену, принятость выводит ПОСТАВЩИК из своей записи по точной ссылке (таблица поставщиков принятия `src/om/achievements.ts`); вида, которого нет в таблице, — отказ, а не «поверим». (12) Положительный вывод требует ДОСТАТОЧНЫХ РАЗЛИЧАЮЩИХ оснований: не хватает обязательной роли либо кандидатов несколько без различающего основания — «неизвестно», а не первый по порядку и не «последняя ветка по умолчанию»; устойчивая сортировка выбор первого не обосновывает (так вернули A4). (13) Перед сдачей убедись, что новые тесты ЛОВЯТ дефект: временно верни ошибочное поведение в `dist/` (не в исходниках), увидь падение теста, затем пересобери. (14) ОДИН класс — ОДИН механизм установления: если обычный путь ВЫВОДИТ класс, маршрут или статус из источников (таблица решений над прочитанными записями), то любой второй путь к тому же результату (снятие преграды, разбор, повтор, восстановление) обязан звать ТУ ЖЕ выводящую функцию над теми же прочитанными источниками; поле `class` чужой записи — заявление, которое сверяется с выводом, а не заменяет его: противоречие или недостаточность → отказ без записи (так второй раз вернули A4: `weighLift` принимал класс из разбора по форме ссылок, не читая содержимое). Тест: основания, из которых таблица выводит другой класс либо «неизвестно», преграду не снимают — ни сохранённым, ни готовящимся разбором; ни снятия, ни записи разбора в базе после отказа нет. (15) ИСТОРИЯ и ГОЛОВЫ — разные вещи: историческое основание (запись, по точной ссылке на которую серия уже перешла) проверяется по точной ссылке и новой ревизией не отменяется; в охраны транзакции (guards) идут ТОЛЬКО изменяемые головы, от которых зависит актуальность результата, — зато ВСЕ фактически прочитанные, включая те, что читает вызванный сосед (например, снятые преграды в stopContext): нет сведений о прочитанном у соседа — расширь его интерфейс, а не охраняй меньше (так вернули A5). Тест: законная новая ревизия исторического источника — отчёт стоит; изменение любой прочитанной головы между проверкой и записью — отказ записи. (16) Позднейшее событие само по себе НЕ доказывает неудачу прежнего средства: «следующая остановка после продолжения» не значит «продолжение не помогло», если между ними записан принятый результат или граница окна; вывод о неудаче — только из сохранённых результатов и границ окон, с тестом на историю с наследованием (так вернули A5). (17) Точная ссылка НЕ заменяет ни проверку ПРИНАДЛЕЖНОСТИ, ни СОДЕРЖАНИЕ: читая чужую запись как источник объяснения или основания, сверяй ВСЕ поля адреса, включая цели/предмет (подделка с верными пространством имён, видом, ревизией и хэшем, но другими целями — отказ), и передавай получателю содержание относящихся строк (код, цель, предмет, происхождение, записанный способ исправления, класс, адресат) с однозначной связью с источником, а не только хэш и ссылку (так вернули A5). (18) СОСТОЯНИЕ ≠ ИСТОРИЯ: текущее состояние соседа (лестница, окна, цели стоящей остановки) — не полная история его событий; сведения, которых в состоянии нет (цели уже отвеченной остановки, границы прежних окон после сброса), НЕ заменяются приближённой проверкой («все цели когда-то встречались») и не пересчитываются вторым алгоритмом — их отдаёт ОДИН точный источник: сосед выводит историю тем же выводом, которым строит и проверяет состояние, и отдаёт её интерфейсом (расширение интерфейса соседа — стык реализации, не правило продукта). Тест: потерянная цель, лишняя цель из другого окна, чужая цель — отказ; перестановка — успех; после сброса лестницы промежуточная остановка не теряется и результат приписывается своему окну (так второй раз вернули A5). (19) ПОЛНОТА НАБОРА проверяется по сохранённым ИСТОЧНИКАМ, а не по перечислению самого набора: реестр/ведомость/список, который выводит каждую свою строку из записей, обязан также доказать, что в нём есть строка для КАЖДОЙ записи-источника (перечисление источников по пространству имён или по хранимому индексу), иначе строку можно удалить новой ревизией и все пути пройдут (так вернули E1). Тест: частичная и полная потеря набора, включая уже закрытую запись, на КАЖДОМ пути, обращающемся к другой записи, а не к потерянной. (20) ЗАЯВЛЕННЫЙ ПОТРЕБИТЕЛЬ — ПРОВЕРЕННЫЙ ПУТЬ: если пакет называет соседа потребителем твоего интерфейса, напиши тест, который проходит ЕГО путь через законные операции (например, обращение к ревьюеру при сохранённой остановке, когда следующая попытка запрещена), а не только «обычный» путь; интерфейс, до которого потребитель не может дойти, — дефект (так вернули E1). (21) ДОПУСК ТЕКУЩЕЙ ПОДГОТОВКИ ≠ ИСТОРИЧЕСКОЕ ЧТЕНИЕ: перечитывание уже сохранённой записи проверяет источники по точным ссылкам как историю; подготовка НОВОЙ записи или её использование в транзакции соседа обязаны проверить ТЕКУЩУЮ актуальность оснований по семантике движка (например, принятость стадии: Pipeline.inspect считает стадию stale при сдвиге головы доказательства) и вернуть полное замыкание охран на эти изменяемые зависимости — в том числе когда запись уже существует и writes пуст. Это два разных пути; общий путь нельзя ни ослабить, ни ужесточить для обоих. Тест: сдвиг зависимости до подготовки, после подготовки перед общей записью, при повторном использовании; историческое чтение после сдвига и перезапуска остаётся успешным (так вернули B1). (22) ОТРИЦАТЕЛЬНЫЙ РЕЗУЛЬТАТ ПРОВЕРКИ ≠ ИСКЛЮЧЕНИЕ ЕЁ ИСПОЛНЕНИЯ: «данные не прошли» приходит из результата проверки (state/findings) и становится типизированным отказом; исключение при исполнении проверки (TypeError, EngineError чужого кода, сбой хранилища) передаётся выше без подмены — общий catch с запасной веткой «отказ производителю» запрещён. Предусмотренное исключение-дефект-данных преобразуется только по явному договору с его кодом. Тест: сбой в чтении посреди проверки сохраняет исходное исключение на всех публичных путях и не оставляет записей (так второй раз вернули B1). (23) САМОСОГЛАСОВАННОЕ ДОКАЗАТЕЛЬСТВО ≠ ПРИНЯТИЕ: proof, хэш которого совпадает с проекцией и который ссылается на верный верх, записать может любой — принятие слоя подтверждается по его НАСТОЯЩИМ сохранённым основаниям (источники исследования и вывод слоя у движка; точный принятый кандидат и исход своих ворот у OM) ОДНИМ общим механизмом для всех читателей. Тест: новая ревизия слоя с пересчитанной проекцией, хэшем и proof, но без исследования и принятия — отказ на всех публичных путях и уровнях (так вернули C2). (24) ПОЛНОТА КОНЦОВ ≠ СОХРАНЕНИЕ ПОТОКОВ: соответствие верхних и нижних связей проверяется ПОТОКАМИ целиком (производитель, порт, якорь, потребители) и взаимно однозначно — два верхних потока не сливаются в одну нижнюю привязку; законная кратность потребителей и произвольные имена нижних портов по записанному соответствию сохраняются. Тест меняет И нижний граф, И записанное соответствие с пересчётом хэшей (так вернули C2). (25) ИСПРАВЛЕНИЕ КЛАССА ОХВАТЫВАЕТ СОСЕДА: если твой механизм уже реализован у принятого соседа (та же проверка другой реализацией), класс закрывается ОДНИМ общим модулем, на который переводятся оба, — а не второй, «правильной» копией у себя; иначе два читателя расходятся на одном входе (так второй раз вернули C2). Тест: один и тот же изменённый вход через обоих читателей даёт одинаковый исход.
- Проверяй все предусмотренные отказы СВОЕЙ единицы и существенные стыки с соседями, а не внутренние отказы неизменённого движка. Правило отсутствия — для ОБЯЗАТЕЛЬНЫХ данных. Публичной команды у модуля ещё нет (до H2): граница — функции твоей единицы и записи, законно приходящие от соседей.

ЧТО M5 ДЕЛАЕТ С ПОЛУЧЕННЫМ
  Одна запись пробела: цель и поле (это её идентичность), вид знания, маршрут, момент разрешения, потребители-блоки, признак «блокирует сборку».
  Потребитель приводится к БЛОКУ горизонта: фича → блоки с её исходом; требование → его фичи; операция или работа → её блок; механизм OM — потребитель-механизм (инвентарь нужен ответу кодом в M6 и пакету проектного вопроса; такой пробел не откладывается никогда, но сборку не держит — у M6 есть адресный путь без инвентаря).
  Вид знания и маршрут — по таблице от кода источника; неизвестный код — отказ. Проектное решение нельзя объявить фактом репозитория, и наоборот.
  Потребитель вне горизонта → отсрочка «до входа блока в горизонт»: смена горизонта меняет статус пробела, а не состав.
  «Блокирует» = потребитель действует И вид знания разрешается в проходе OM. Подтверждение среды уходит на старт задачи, доказательство после реализации — на результат задачи: сборку они не держат изначально.
  Несколько источников на одно поле одной цели: одинаковая классификация — одна запись с объединёнными потребителями; противоречащая — отказ, первый источник молча не выигрывает.

КУДА УХОДИТ
  → G4: присланный набор сверяется с выведенным заново (Т3); отсутствие набора — отказ, а не успех (Т4).
  → M6: маршрут по виду знания. → MC2: соседи незаполненного конца связи.
  → G4b — ГОТОВНОСТЬ ОСНОВАНИЙ ДЛЯ СБОРКИ РАБОТ, а не принятие слоя. У каждого блокирующего пробела текущей версии входа — ровно один результат законным маршрутом с точной ссылкой, и результат этот допустимого вида:
      · ответ кодом — с проверенным основанием; ответ исследования (MC1) — с вердиктом supported; ответ владельца;
      · предложение ОПЕРАЦИЙ (MC2) — с результатом проверки G3, связанным с точным кандидатом и базовыми ссылками;
      · предложение РАБОТ (MC2) — допускается К СБОРКЕ, с учтённой попыткой; его принятие — позже: после сборки в M7 и проверки G5.
    Проход G4b не закрывает линию проектного пробела и не означает принятия работ: линию закрывает принятое заполнение (см. «Как ответ возвращается»). Подготовка кандидата, нужная для проверки ответа, собственного принятия не ждёт: взаимного ожидания нет, сборка всегда раньше проверки.
    Отложить блокирующий пробел результат маршрута НЕ может: нужное сборке переносит только смена горизонта владельцем.
  → G7: состояние линий. Счётчик проходов линии — не счётчик попыток серии; тот ведётся в серии по правилам вызовов модели и G7.

КАК ОТВЕТ ВОЗВРАЩАЕТСЯ
  · Проектное решение по операциям или работам → предложение слоя в каркас → принятие кандидата → основание закрытия «заполнено».
  · Принятый ответ-факт (MC1, вердикт supported) → запись принятого ответа → M6 находит его по обязательству и проверяет применимость (тот же договор вопроса и те же текущие источники) → значение получает механизм, породивший пробел (сборка входа, пакет проектного вопроса, M8) → основание закрытия «заполнено» = ссылка на принятый ответ. Изменились источники или сам вопрос (смысл требования, потребитель, форма результата) — ответ неприменим, вопрос задаётся заново; правка входа, не затрагивающая договор вопроса, ответ не отменяет.
  · Решение о недостающем поле входа — адресация вопроса, привязка контракта к блокам, граница узлами, вид проверки — проверяется кодом и применяется как новая версия входа: заполняется только недостающее.
  · Решение об адресации вопроса (кому он нужен и какого он вида) → новая версия входа → в следующем проходе вопрос становится обязательством СВОЕГО вида. Это не ответ на вопрос. Адресация заполняет только НЕДОСТАЮЩЕЕ: каждое поле, уже данное производителем (вид знания, узел-потребитель), сохраняется; повтор того же решения ничего не меняет; другое решение — отказ. Замена принятой адресации не предусмотрена.
  · Линия пробела закрывается ТОЛЬКО с основанием: «заполнено» (принятое заполнение или адресация, в том числе вычисленное кодом) либо «отменено» (решение владельца). Связать основание с конкретной линией и проверить полномочие отмены обязан поставщик закрытия. Запоздавший проход не отменяет более позднего закрытия или отсрочки.

## Карточки единиц карты — дословно

#### F4.3 · applyProposals — положить предложения  `f4-input`
- **цель:** Предложения слоя ложатся в обязательства кодом до проверки; принятия для этого не требуется — взаимного ожидания нет.
- **что делает:** applyProposals внутри fillObligations. Допускаются ТОЛЬКО предложения status proposed — иначе отказ proposal_not_proposed: отклонённое предложение повторно не подаётся, нужно новое (тест 11); этот проверенный набор идёт во все шаги. Предложения для ЭТОЙ базы (base = головы принятых графа и каркаса; иначе proposal_base_stale). Заполнение подходит, если узел определён в том же предложении или принят и является потомком upper.node (иначе slot_fill_foreign). producer и block-outcome — ровно одно заполнение, два разных предложения → slot_fill_conflict; consumer — одно или несколько. Принятое настоящее заполнение меняется только явной заменой: replaces с точной базой {node, graph ref}; база сверяется с принятым ДО удаления заменяемого узла; устаревшая база → proposal_base_stale; предложение на занятое обязательство без replaces либо две разные замены одной базы → slot_fill_conflict. Результат — fills и перечень незаполненных обязательств горизонта; каркас при этом НЕ переписывается; кандидата сохраняет сборщик F4.5. Тест: «принятое заполнение меняется только явной заменой…».
- **вход:** connection-frame; layer-proposal[] (source input | decision)
- **выход:** fills[]; незаполненные обязательства горизонта
- **ворота:** G3 (proposal_base_stale, slot_fill_conflict, slot_fill_foreign, identity_in_horizon)

#### F4.4 · openObligationsToGaps — незаполненное в адресные пробелы  `f4-open`
- **цель:** Каждая неуловленная связь подблоков и каждый блок без производителя исхода видны поимённо, с тем, кого это блокирует.
- **что делает:** openObligationsToGaps(frame) → gaps[]. На каждое обязательство зоны horizon без заполнения: пробел { target: id обязательства, field: fill, kind: design-decision, consumer: upper.node — узел, чьё раскрытие заблокировано, neighbors[]: все остальные концы той же привязки (у 14 связей omg-live потребителей несколько — адресаты не теряются), blocking: true }. Вопрос к MC2 закрытый: «какой узел уровня N внутри <upper.node> производит / потребляет <artifact> по контракту <portContract>: один из существующих [перечень] либо новый — тогда с полным определением узла». Ответ MC2 — запись layer-proposal со status proposed, она возвращается в F4.3. Линия пробела — по id обязательства.
- **вход:** connection-frame, кандидатная ревизия
- **выход:** gaps[] → M5 → MC2 → layer-proposal
- **ворота:** G4 (через M5)

#### layer-proposal (предложение слоя)  `st-proposal`
- **что хранит:** { base{graph, frame} — головы на момент предложения, level, source: input | decision, status: proposed | accepted | rejected, verdict?{candidateHash, candidate ref, codes}, nodes[] — полные определения узлов, fills[{obligation, node, port?}], localConnectors[], и ВСЁ, что предложение вводит: artifacts, contracts, joins (соединения входов — без них join_missing), tests, edges, journeys, packets, transfers, anchors; для замены принятого: removes[id узлов], replaces[{obligation, base{node, graph ref}, with, basis}], redefines[id принятых определений, которые предложение переопределяет] }. Ссылка {node, port, contract} без определения узла предложением не является. Проверено тестом: предложение без joins → join_missing, без artifacts → artifact_missing. Исполняемая спецификация: proto/frame.mjs; тесты proto/frame.test.mjs.
