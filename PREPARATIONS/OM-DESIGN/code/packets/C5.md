# Задача C5 · Каркас: принятие кандидата и переход на новую базу (F4.6) — общий для уровней 2 и 3

**Цель.** Принимать ТОЧНЫЙ успешный исход ворот своего уровня (G3 — операции, G5 — работы) одной транзакцией — граф, слой, запись каркаса, статусы предложений — и явно переводить каркас на законно изменённую базу.

## Как работать

- Ты воркер блока OM движка OMG. Рабочая копия — `/Users/kostenchuksergey/OMG/.omg/worktrees/om-module`, ветка `om/module`. Работай ТОЛЬКО в ней. Основную копию `~/OMG`, базу `.omg/state.sqlite` и `live-source` не трогай и не читай на запись.
- Писать разрешено ТОЛЬКО в эти файлы: `src/om/frame-accept.ts`, `test/om-frame-accept.test.ts`, `src/om/layer-basis.ts`, `test/om-layer-basis.test.ts`, `src/om/frame-obligations.ts`, `test/om-frame-obligations.test.ts`, `src/om/horizon.ts`, `test/om-horizon.test.ts`, `src/om/gaps.ts`, `test/om-gaps.test.ts`. Нужен другой файл — остановись и сообщи: это отход от задачи, а не твоё решение.
- Источник истины — правила ниже. Они приняты ревьюером. Если правило кажется неверным, неполным или противоречит движку — НЕ обходи его кодом: остановись и опиши противоречие с примером. Поведение продукта сам не выбирай.

- Тесты: `node:test` + `node:assert/strict`, своя временная база на тест (образец — `test/storage.test.ts`), без настоящих вендоров, сети и ключей. `ui/` не трогать. push, слияния, теги — запрещены.
- Стиль движка: ESM, относительные импорты с суффиксом `.js`; `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noUnusedLocals`; файлы в kebab-case, без `index.ts`; типы экспортируются рядом с реализацией; комментарии редкие, на английском, объясняют «почему». Отказ движка — `EngineError(code, message, details)` из `src/errors.ts`. Факты о движке: `PREPARATIONS/OM-DESIGN/code/engine-facts-infra.md` и `engine-facts-reuse.md` — сверяй с кодом перед использованием.
- УРОКИ РЕВЬЮ СДЕЛАННЫХ ЗАДАЧ (классы дефектов, за которые код уже возвращали): (1) экспортируемая функция проверяет форму ВСЕХ аргументов до первого обращения к полям и до хранилища — отсутствует, null, не тот тип → `EngineError` с кодом дефекта единицы; обычный `TypeError` — дефект. Отсутствующий набор и явно пустой набор — разные случаи, отсутствующий на `[]` не подменяется. (2) JSON-содержимое копируется и отдаётся только через `sealed()` / `delivered()` из `src/om/refusal.ts`; своё копирование присваиванием по чужим ключам запрещено — ключ `__proto__` теряется и подменяет прототип; объект из чужих ключей строится через `Object.defineProperty` либо `Map`. Инвариант для теста: хэш выданного равен хэшу записи. (3) Точная ссылка доказывает, КАКУЮ запись прочитали, но не её принятие: основание принятия и связь с исходом ворот проверяет та единица, чья это обязанность. (4) Т3 буквально: производная запись сверяется с ЗАФИКСИРОВАННЫМ ИСТОЧНИКОМ — источник перечитывается по точной ссылке, производное выводится из него заново той же функцией и сравнивается; пересчёт хэша собственных полей записи — это самосогласованность, а не вывод заново (так вернули A2). Тест подделки меняет содержимое И пересчитывает id либо хэш; проверяется историческая ревизия источника по точной ссылке — новая голова источника старую запись ложной не делает. (5) Т5 буквально: запрос на переход НАЗЫВАЕТ состояние, из которого идёт (номер попытки, номер остановки, точную ревизию) — запоздавший повтор того же запроса после любых последующих событий распознаётся как уже применённый и на более позднее состояние не действует (так вернули A3: повтор продолжения снимал НОВУЮ остановку). Тест: запоздавший повтор после следующего события и после перезапуска базы. (6) Т6 буквально: НЕупорядоченные наборы (достижения, отмены, отказы, вопросы пакета, основания) нормализуются одной функцией перед записью И перед сравнением, сортировка не зависит от локали, кратность сохраняется; хранимая запись с неканоничным порядком — отказ. Тест: перестановка элементов — тот же исход без ревизии. (7) Передача соседу несёт ОДНОЗНАЧНУЮ сохранённую связь с конкретной записью или строкой соседа (id либо точная ссылка), а не пару «название + цель»: два законных события с одинаковыми названием и целью обязаны оставаться различимыми. (8) Изменяющая операция отделяет ПОДГОТОВКУ (все проверки → готовые записи и охраны, без записи) от ЗАПИСИ: соседняя единица, которой по правилам нужна ОДНА транзакция на несколько записей, включает подготовленное в свой writeGuarded, а не вызывает операции по очереди (частичный результат) и не переписывает твою логику. (9) Каждый исход, который правило называет (например «разбор завершён без пригодного изменения — ступень 2»), — это ПРИМЕНЯЕМЫЙ переход, сохранённый в истории записи, а не только отказ: отказ ничего не сохраняет, и следующий запрос проходит так, будто исхода не было (так вернули A3.1). Проверь по правилам своей единицы: у каждого названного исхода есть операция, которая его записывает, и тест, что после него запрещённое остаётся запрещённым — в том числе после перезапуска и у преемника. (10) Если сосед по правилам пишет свою запись В ТОЙ ЖЕ транзакции, что твой переход (основание, разбор, решение, подтверждение), подготовка принимает основание в двух видах — уже записанное (точная ссылка) и готовящееся в этой транзакции (предлагаемая запись: подготовка сама вычисляет её точную ссылку, проверяет её ТОЙ ЖЕ функцией содержания и включает в возвращаемый набор записей). Подготовка, которая умеет только читать основание из хранилища, вынуждает соседа коммитить его отдельно — и открывает окно (так второй раз вернули A3.1). (11) Ничто, от чего зависит продвижение, класс или маршрут, не принимается со слов вызывающего: достижение, отмену, принятость выводит ПОСТАВЩИК из своей записи по точной ссылке (таблица поставщиков принятия `src/om/achievements.ts`); вида, которого нет в таблице, — отказ, а не «поверим». (12) Положительный вывод требует ДОСТАТОЧНЫХ РАЗЛИЧАЮЩИХ оснований: не хватает обязательной роли либо кандидатов несколько без различающего основания — «неизвестно», а не первый по порядку и не «последняя ветка по умолчанию»; устойчивая сортировка выбор первого не обосновывает (так вернули A4). (13) Перед сдачей убедись, что новые тесты ЛОВЯТ дефект: временно верни ошибочное поведение в `dist/` (не в исходниках), увидь падение теста, затем пересобери. (14) ОДИН класс — ОДИН механизм установления: если обычный путь ВЫВОДИТ класс, маршрут или статус из источников (таблица решений над прочитанными записями), то любой второй путь к тому же результату (снятие преграды, разбор, повтор, восстановление) обязан звать ТУ ЖЕ выводящую функцию над теми же прочитанными источниками; поле `class` чужой записи — заявление, которое сверяется с выводом, а не заменяет его: противоречие или недостаточность → отказ без записи (так второй раз вернули A4: `weighLift` принимал класс из разбора по форме ссылок, не читая содержимое). Тест: основания, из которых таблица выводит другой класс либо «неизвестно», преграду не снимают — ни сохранённым, ни готовящимся разбором; ни снятия, ни записи разбора в базе после отказа нет. (15) ИСТОРИЯ и ГОЛОВЫ — разные вещи: историческое основание (запись, по точной ссылке на которую серия уже перешла) проверяется по точной ссылке и новой ревизией не отменяется; в охраны транзакции (guards) идут ТОЛЬКО изменяемые головы, от которых зависит актуальность результата, — зато ВСЕ фактически прочитанные, включая те, что читает вызванный сосед (например, снятые преграды в stopContext): нет сведений о прочитанном у соседа — расширь его интерфейс, а не охраняй меньше (так вернули A5). Тест: законная новая ревизия исторического источника — отчёт стоит; изменение любой прочитанной головы между проверкой и записью — отказ записи. (16) Позднейшее событие само по себе НЕ доказывает неудачу прежнего средства: «следующая остановка после продолжения» не значит «продолжение не помогло», если между ними записан принятый результат или граница окна; вывод о неудаче — только из сохранённых результатов и границ окон, с тестом на историю с наследованием (так вернули A5). (17) Точная ссылка НЕ заменяет ни проверку ПРИНАДЛЕЖНОСТИ, ни СОДЕРЖАНИЕ: читая чужую запись как источник объяснения или основания, сверяй ВСЕ поля адреса, включая цели/предмет (подделка с верными пространством имён, видом, ревизией и хэшем, но другими целями — отказ), и передавай получателю содержание относящихся строк (код, цель, предмет, происхождение, записанный способ исправления, класс, адресат) с однозначной связью с источником, а не только хэш и ссылку (так вернули A5). (18) СОСТОЯНИЕ ≠ ИСТОРИЯ: текущее состояние соседа (лестница, окна, цели стоящей остановки) — не полная история его событий; сведения, которых в состоянии нет (цели уже отвеченной остановки, границы прежних окон после сброса), НЕ заменяются приближённой проверкой («все цели когда-то встречались») и не пересчитываются вторым алгоритмом — их отдаёт ОДИН точный источник: сосед выводит историю тем же выводом, которым строит и проверяет состояние, и отдаёт её интерфейсом (расширение интерфейса соседа — стык реализации, не правило продукта). Тест: потерянная цель, лишняя цель из другого окна, чужая цель — отказ; перестановка — успех; после сброса лестницы промежуточная остановка не теряется и результат приписывается своему окну (так второй раз вернули A5). (19) ПОЛНОТА НАБОРА проверяется по сохранённым ИСТОЧНИКАМ, а не по перечислению самого набора: реестр/ведомость/список, который выводит каждую свою строку из записей, обязан также доказать, что в нём есть строка для КАЖДОЙ записи-источника (перечисление источников по пространству имён или по хранимому индексу), иначе строку можно удалить новой ревизией и все пути пройдут (так вернули E1). Тест: частичная и полная потеря набора, включая уже закрытую запись, на КАЖДОМ пути, обращающемся к другой записи, а не к потерянной. (20) ЗАЯВЛЕННЫЙ ПОТРЕБИТЕЛЬ — ПРОВЕРЕННЫЙ ПУТЬ: если пакет называет соседа потребителем твоего интерфейса, напиши тест, который проходит ЕГО путь через законные операции (например, обращение к ревьюеру при сохранённой остановке, когда следующая попытка запрещена), а не только «обычный» путь; интерфейс, до которого потребитель не может дойти, — дефект (так вернули E1). (21) ДОПУСК ТЕКУЩЕЙ ПОДГОТОВКИ ≠ ИСТОРИЧЕСКОЕ ЧТЕНИЕ: перечитывание уже сохранённой записи проверяет источники по точным ссылкам как историю; подготовка НОВОЙ записи или её использование в транзакции соседа обязаны проверить ТЕКУЩУЮ актуальность оснований по семантике движка (например, принятость стадии: Pipeline.inspect считает стадию stale при сдвиге головы доказательства) и вернуть полное замыкание охран на эти изменяемые зависимости — в том числе когда запись уже существует и writes пуст. Это два разных пути; общий путь нельзя ни ослабить, ни ужесточить для обоих. Тест: сдвиг зависимости до подготовки, после подготовки перед общей записью, при повторном использовании; историческое чтение после сдвига и перезапуска остаётся успешным (так вернули B1). (22) ОТРИЦАТЕЛЬНЫЙ РЕЗУЛЬТАТ ПРОВЕРКИ ≠ ИСКЛЮЧЕНИЕ ЕЁ ИСПОЛНЕНИЯ: «данные не прошли» приходит из результата проверки (state/findings) и становится типизированным отказом; исключение при исполнении проверки (TypeError, EngineError чужого кода, сбой хранилища) передаётся выше без подмены — общий catch с запасной веткой «отказ производителю» запрещён. Предусмотренное исключение-дефект-данных преобразуется только по явному договору с его кодом. Тест: сбой в чтении посреди проверки сохраняет исходное исключение на всех публичных путях и не оставляет записей (так второй раз вернули B1). (23) САМОСОГЛАСОВАННОЕ ДОКАЗАТЕЛЬСТВО ≠ ПРИНЯТИЕ: proof, хэш которого совпадает с проекцией и который ссылается на верный верх, записать может любой — принятие слоя подтверждается по его НАСТОЯЩИМ сохранённым основаниям (источники исследования и вывод слоя у движка; точный принятый кандидат и исход своих ворот у OM) ОДНИМ общим механизмом для всех читателей. Тест: новая ревизия слоя с пересчитанной проекцией, хэшем и proof, но без исследования и принятия — отказ на всех публичных путях и уровнях (так вернули C2). (24) ПОЛНОТА КОНЦОВ ≠ СОХРАНЕНИЕ ПОТОКОВ: соответствие верхних и нижних связей проверяется ПОТОКАМИ целиком (производитель, порт, якорь, потребители) и взаимно однозначно — два верхних потока не сливаются в одну нижнюю привязку; законная кратность потребителей и произвольные имена нижних портов по записанному соответствию сохраняются. Тест меняет И нижний граф, И записанное соответствие с пересчётом хэшей (так вернули C2). (25) ИСПРАВЛЕНИЕ КЛАССА ОХВАТЫВАЕТ СОСЕДА: если твой механизм уже реализован у принятого соседа (та же проверка другой реализацией), класс закрывается ОДНИМ общим модулем, на который переводятся оба, — а не второй, «правильной» копией у себя; иначе два читателя расходятся на одном входе (так второй раз вернули C2). Тест: один и тот же изменённый вход через обоих читателей даёт одинаковый исход. (26) ПЕРВЫЙ ПРОХОД — ЗАКОННЫЙ ПУТЬ: сохраняемый интерфейс обязан работать от начального состояния (принятые стадии и L1, без L2/L3), а не только на полностью раскрытой фикстуре; если обязательный источник ещё не может существовать, он явно сообщает ПРОВЕРЯЕМЫЙ исход «ещё не возможен», выведенный из точных оснований текущей стадии, — не пустоту по умолчанию и не перехват любого отказа соседа; после появления основания этот исход не может скрыть настоящие данные. Тест — настоящий путь от начального состояния, затем появление источника (так вернули D1). (27) ГРАНИЦА ПОЛНОМОЧИЙ — ПО ИЗМЕНЕНИЮ, А НЕ ПО НАЛИЧИЮ: «эта задача не трогает уровень N» проверяется сравнением итога с ПРИНЯТЫМ определением (что изменилось, что исчезло), а не по тому, встречается ли уровень N во входящем объекте: неизменённое принятое содержимое другого уровня законно присутствует, а его отсутствие во входящем определении не должно его удалять. Учитывать и исчезнувшие ссылки, а не только новые (так вернули C4). (28) ЗАЩИЩАЕМОЕ = ЗАМЫКАНИЕ ЗАВИСИМОСТЕЙ: защищая объект, защищай и всё, во что его типизированные ссылки разрешаются (порт → контракт; результат/связь → артефакт → контракт и т. д.), по типизированным связям графа, а не поиском строк; равенство самого объекта ничего не доказывает, если его ссылки ведут в изменённые определения. Не замораживать при этом весь граф — законные изменения вне замыкания должны проходить (так второй раз вернули C4).
- Проверяй все предусмотренные отказы СВОЕЙ единицы и существенные стыки с соседями, а не внутренние отказы неизменённого движка. Правило отсутствия — для ОБЯЗАТЕЛЬНЫХ данных. Публичной команды у модуля ещё нет (до H2): граница — функции твоей единицы и записи, законно приходящие от соседей.

```text
Т2. Отношения между узлами — действующая семантика движка, а не приближение. Уточнение = вложенность ИЛИ явное «реализует» (RefinementRelations). Необходимые предшественники = связи данных + requires + передачи владения (controlPredecessors). Годность квитанции — формула компилятора. Владение путём — правила writeGrants.
  Места: замыкание горизонта; принадлежность заполнения верхнему узлу; зона работ; план исполнения; адрес соседа; сверка доставки.

Т3. Производная запись проверяется повторным выводом из зафиксированных источников, а не по собственным полям.
  Места: набор пробелов (G4, G4b); пакеты соседей (G5); кандидат слоя — принимается только граф из записи кандидата (G3, G5).

Т4. Отсутствие — типизированный отказ с адресом. Нет обязательного источника, поля или набора — отказ; значений по умолчанию у обязательного нет; «пусто» передаётся явно.
  Места: вход M1 (правило эры: в записи прежней эры отсутствие структурированного поля — адресный пробел, в новой — отказ производителю стадии); готовность блока в горизонте; источники M5; аргументы всех ворот.

Т5. Переход состояния проверяет, из какого состояния идёт. Повтор того же — без изменений; противоречащее — отказ; запоздавшее не отменяет более позднего.
  Места: принятие кандидата; переход каркаса на новую базу; адресация вопроса; закрытие линии пробела; переход серий; закрытие вызова модели; учёт исхода попытки.

Т6. Порядок записей ничего не решает, кратность доезжает до потребителя.
  Места: несколько привязок одной связи (потоки); несколько потребителей; работа, уточняющая несколько операций; адреса внешних входов; ровно один пакет на работу.

Т7. Проверка и запись — одна транзакция с охраной по точным ссылкам; окна между «проверил» и «записал» нет.
  Места: учёт вызова в ведомости (запись и однократное закрытие); принятие кандидата (граф + каркас + статусы предложений); переход серий; переход каркаса на новую базу.

Т8. Отказ адресный и с маршрутом: что именно, у какого узла, кому возвращается — производителю данных, в пробел M5, владельцу, на пересмотр готовности в M2. Сам отказ ничего не переключает: не разрешает повторное исполнение, не меняет готовность, не открывает новую попытку. Обратные пути идут через G7.

Т9. Каждый пробел заполняется (решение владельца 21.09.2026). Отложенное не теряется и не закрывается без основания; нужное текущей сборке не переносится строкой результата; вес блока — только очередь.
  Места: отсрочка и линии в M5; G4b; M3.

Т10. Продуктовый выбор в коде не делается. Если для исправления надо выбрать СМЫСЛ ограничения (что считать продвижением, что считать несоразмерным расходом, замена адресации, аварийная защита бюджета) — это карточка решения владельца; до решения действует названное осторожное умолчание.

Т11. Политика неизменяема, выданное — копия. Таблицы правил не меняются во время работы; запись, отданная потребителю, не делит изменяемых объектов ни с политикой, ни с источником, из которого ворота выводят эталон. Это требование к модулю; решений схемы оно не меняет.
```

### Уровень 2 · Правила · M4 · каркас связей операций  `rules-m4`

```text
Получает: принятый слой блоков; горизонт; принятый слой операций и запись каркаса, если они есть; предложения слоя (от MC2 или выведенные кодом) с указанием базы.
Достоверное основание: верхний слой — принятая запись; принятое соответствие — запись каркаса, привязанная к слою хэшем (Т1); предложение — только в статусе «предложено» и на текущей базе; кандидат — только граф из записи кандидата, прошедший ДЕЙСТВУЮЩИЕ проверки графа и сборки слоя без их правки.
Выдаёт и хранит:
  · обязательства — исход каждого блока и КАЖДЫЙ конец КАЖДОГО потока каждой связи по всему верхнему слою, включая связи внешних артефактов. Поток — привязка, различимая концом-производителем (узел и порт) и якорем; нижние привязки зеркалят верхние по одной (Т6);
  · заполнения с источником: принятое настоящее / предложенное / представитель;
  · кандидат — отдельная неизменяемая запись со ссылками на базу и предложения;
  · после принятия одной транзакцией (Т7) — граф, запись каркаса, статусы предложений.
Правила:
  · очерёдность заполнения: принятое настоящее → предложение → представитель;
  · представитель (тождественный узел 1:1) — только вне горизонта; обязательств горизонта не закрывает; имя зарезервировано — узел предложения не может выдать себя за представителя; несёт только те порты, концы которых закрывает сам; когда блок входит в горизонт, представитель уходит;
  · производитель вне горизонта, нужный узлу горизонта, обязан быть настоящим раскрытием (кроме внешнего источника);
  · предложение несёт полный состав: узлы, заполнения, локальные связи, зависимые определения; все потребители связи доезжают до нижней привязки.
Разрешённые изменения: заполнить пустое; принятое заполнение меняется только ЯВНОЙ заменой с точной базой; зависимое определение принятой части меняется, только если оно названо в предложении; замена не оставляет висящих ссылок; отклонённое предложение повторно не подаётся.
Отказ и продолжение: незаполненное в горизонте → адресный пробел в M5 → MC2 → новое предложение; отказ проверки → предложения отклонены, возврат через G7; база сменилась → новое предложение; запоздавший отказ принятого не меняет; слой изменён в обход каркаса → стоп, владельцу.
Открытое: нет.
```

### Уровень 2 · Передача · M2 → M4 → M7 · горизонт → операции → работы  `rules-handoff-horizon`

```text
ЧТО ПЕРЕДАЁТСЯ И ЧТО ПОЛУЧАТЕЛЬ СЧИТАЕТ ДОКАЗАННЫМ

M2 → M4. Запись om-horizon: блоки горизонта; по каждому — refinement (accepted | needed: есть ли принятое настоящее раскрытие) и execution (needed | available с основанием); граница — блоки вне горизонта, у которых есть И результат, И принятое раскрытие; адреса внешних входов; исключения владельца с причиной и условием возврата; хэш (в него входят версия выбора, исключения и основания).
  M4 считает доказанным: горизонт замкнут — каждый производитель, нужный блоку горизонта (по связям данных, requires и передачам владения), либо в горизонте, либо на границе.
  M4 НЕ считает доказанным: что принятое раскрытие означает готовый результат; что квитанции подлинны (это M8).
  Правило: «раскрыт на карте» ≠ «результат есть». Граница — только при обоих признаках. Блок с результатом, но без раскрытия добирается в горизонт РАДИ РАСКРЫТИЯ: исполнять его не нужно, но конкретный подблок-производитель должен быть известен.
  Основание готовности — блок → {артефакт: точная ссылка на квитанцию} на КАЖДЫЙ результат, который у блока берёт горизонт, включая исход выбранной фичи. Одна «квитанция на блок» основанием не считается. Непокрытый результат — адресный отказ (блок и артефакт).

M4 → M7. Принятый слой операций и запись каркаса операций: какой конец какого потока какой связи закрыт каким узлом и портом; какие узлы — представители; хэши слоя.
  M7 берёт ЗОНУ: операции, которые УТОЧНЯЮТ (Т2) блоки горизонта с execution needed. Представитель операции в зону не входит.
  Блок с execution available в зону не входит — повторное исполнение не выводится. Его производители обязаны быть НАСТОЯЩИМИ принятыми работами, а вход от них принимается только по квитанции, которую M2 назвал основанием именно этого результата: квитанция названа на эту работу, с её подписью и хэшем контракта, и она же — текущая квитанция артефакта (иначе компилятор прочтёт другую).
  M7 НЕ проверяет: подлинность коммита, дерева, плана и прогона квитанции — это действующий resolveArtifact на стыке с M8.

ОБРАТНЫЕ МАРШРУТЫ (Т8)
  · Результат «есть», а настоящей работы-производителя нет; либо основание не годится, устарело, названо на чужую работу или не названо вовсе → адресный отказ (связь или ребро, производитель, блок, артефакт) → через G7 пересмотр готовности в M2: исправить основание либо снять признак готовности решением. Автоматически готовность не меняется и повторное исполнение не запускается.
  · Слой операций законно изменён и принят тем же каркасом, когда слой работ уже принят → каркас работ ЯВНО переходит на новую базу: заполнения, чьё обязательство сохранилось, переносятся; остальные уходят в историю; новые обязательства обрабатываются обычным порядком. Правка слоя в обход каркаса — отказ, переход не выполняется.
  · Незаполненное обязательство зоны → адресный пробел в M5 вместе с соседями по связи.

M7 → M9 → компилятор. Граф уровня работ: работы с местом в коде и тестами; привязки уровня работ — действующие и спящие (якорь и тест пробуждения — только для ПОТРЕБИТЕЛЯ вне плана; вход от производителя вне плана идёт по названной квитанции, от внешнего источника — как внешний); план исполнения = настоящие работы, уточняющие операции зоны; пакет соседей каждой работы. Всё выводится из ОДНОГО зафиксированного снимка графа вместе с записью каркаса работ и основаниями доставки — не из текущих голов записей в момент выдачи задачи.
```

## Карточки единиц карты — дословно

#### F4.6 · settleCandidate — зафиксировать исход проверки  `f4-accept`
- **цель:** Кандидат и принятый результат различимы; принятие атомарно и однократно, отказ ничего принятого не меняет.
- **что делает:** settleCandidate(точная ссылка записи кандидата, исход G3). Исход G3 выдан на ТОЧНУЮ запись: нет такой ревизии или хэша → candidate_missing; хэш графа в записи не равен graphHash → candidate_graph_mismatch; принимается граф из записи, а не переданный объект. Предложения охраняются по ссылкам, сохранённым в кандидате, а не по текущим головам: изменённое после сборки предложение даёт input_stale, и ни одна запись транзакции не применяется (тест 10). Запоздавший отказ по предложениям, которые уже в другой ревизии или статусе, ничего не меняет (тест 11). Проход: база кандидата сверяется с текущими головами графа и каркаса — сменились → input_stale (принят другой кандидат той же базы); затем один store.writeMany с охраной [запись кандидата, текущий граф, текущий каркас, предложения]: новая ревизия graph, принятая ревизия каркаса (proposed → accepted, identity остаётся identity), предложения → accepted {candidateHash}. Отказ G3: предложения → rejected с кодами; граф и принятый каркас не меняются; дальше — ворота повтора G7. Прежние ревизии остаются в истории. Тест: два кандидата одной базы — первый принят, второй input_stale; отказ не меняет принятого. В прототипе граф пишется напрямую; в модуле — через копию GraphRepository с LayerProof уровня N. Исполняемая спецификация: proto/frame.mjs; тесты proto/frame.test.mjs. СМЕНА БАЗЫ: принятие слоя операций после принятого слоя работ не ломает каркас работ — F4.6 записывает layerHash, upperHash и lowerHash, по ним каркас уровня ниже отличает законную смену базы (rebaseFrame) от правки в обход.
- **вход:** candidate; исход G3 с хэшем кандидата
- **выход:** принятый слой N и принятая ревизия каркаса либо отклонённые предложения
- **ворота:** G7 на обратном пути (действующая связь G3 → G7)

## Карточки записей-соседей — дословно

#### frame-candidate (кандидат слоя)  `st-candidate`
- **что хранит:** Отдельная НЕИЗМЕНЯЕМАЯ запись, не ревизия каркаса: { project, level, graphHash, graph — САМ проверенный граф, fills[] (accepted | proposed | identity), base{ graph: ссылка головы принятого графа | null, frame: ссылка головы принятого каркаса | null }, proposals[ссылки] }. Имя записи = хэш(graphHash, base, proposals): одинаковый граф на другой базе — другой кандидат. Так различены неизменяемое основание предложения и точная ссылка на подготовленного кандидата; запись кандидата головы graph и каркаса не меняет, и принятие без конкурента не получает input_stale (проверено тестом). Сохраняет запись сборщик F4.5 после успешной проверки, когда известен хэш графа. Принимается только граф ИЗ ЭТОЙ записи: цепочка «граф → его хэш → запись кандидата → исход G3 для этой записи»; подмена объекта после проверки ничего не даёт (тест 9). proposals[] — точные ссылки {id, revision, hash} проверенных ревизий предложений. Исполняемая спецификация: proto/frame.mjs; тесты proto/frame.test.mjs.

#### connection-frame (каркас обязательств уровня N)  `st-frame`
- **что хранит:** ПРИНЯТЫЙ каркас уровня N: { project, level, candidateHash, fills[{ obligation, node, port?, source: accepted | identity, basis }] }. Новая ревизия появляется только при принятии кандидата (F4.6); подготовка кандидата эту запись не трогает — поэтому охранная ссылка на неё остаётся действительной до принятия. Признак identity хранится ЗДЕСЬ, а не в узле (схема узла закрыта), и переживает принятие: принятый представитель остаётся представителем. Исторический слой без каркаса считается целиком настоящим. Обязательства не хранятся — они чистая функция верхнего слоя и горизонта (F4.1) и пересчитываются. Обязательство двух видов: connection-end { connector, artifact, role producer | consumer, upper{node, port} } и block-outcome { upper.node, artifact }; зона horizon | outside; у producer и block-outcome одно заполнение, у consumer — одно или несколько. Id обязательства = хэш(вид, connector, уровень, роль, upper.node, upper.port). При смене идентификаторов верха соответствие старое → новое — только по объявленному переименованию; иначе новая работа с основанием. Расход и попытки учитываются на блоке (серия, ведомость G8): смена id их не обнуляет, ответ на старое обязательство на новое не переносится. M7 и пакет контекста читают только принятую ревизию по точной ссылке. Исполняемая спецификация: proto/frame.mjs; тесты proto/frame.test.mjs. Редакция 3: запись каркаса несёт layerHash — хэш проекции принятого слоя; по нему проверяется, что записанное соответствие относится к действующему слою.

#### layer-proposal (предложение слоя)  `st-proposal`
- **что хранит:** { base{graph, frame} — головы на момент предложения, level, source: input | decision, status: proposed | accepted | rejected, verdict?{candidateHash, candidate ref, codes}, nodes[] — полные определения узлов, fills[{obligation, node, port?}], localConnectors[], и ВСЁ, что предложение вводит: artifacts, contracts, joins (соединения входов — без них join_missing), tests, edges, journeys, packets, transfers, anchors; для замены принятого: removes[id узлов], replaces[{obligation, base{node, graph ref}, with, basis}], redefines[id принятых определений, которые предложение переопределяет] }. Ссылка {node, port, contract} без определения узла предложением не является. Проверено тестом: предложение без joins → join_missing, без artifacts → artifact_missing. Исполняемая спецификация: proto/frame.mjs; тесты proto/frame.test.mjs.

#### Записи OM в SQLite  `store-records`
- **что хранит:** om-input, horizon и om-horizon, series-transition, block-weight, call-record, gaps, answers, graph и graph-layer, feasibility — все с id/revision/hash; проекции только читают (инвариант). Состав каждой записи — в её карточке уровня 2; серии исправлений, ведомость расхода и журнал отказов — отдельные карточки.
