# Задача V1 · Единый источник технической вместимости запроса

**Цель.** Определить одну величину технической вместимости — для контекста задачи исполнителя и для запроса к модели — как настройку среды, с чтением через одну функцию и типизированным отказом при отсутствии.

## Как работать

- Ты воркер блока OM движка OMG. Рабочая копия — `/Users/kostenchuksergey/OMG/.omg/worktrees/om-module`, ветка `om/module`. Работай ТОЛЬКО в ней. Основную копию `~/OMG`, базу `.omg/state.sqlite` и `live-source` не трогай и не читай на запись.
- Писать разрешено ТОЛЬКО в эти файлы: `src/runtime/environment.ts`, `src/om/capacity.ts`, `test/om-capacity.test.ts`. Нужен другой файл — остановись и сообщи: это отход от задачи, а не твоё решение.
- Источник истины — правила ниже. Они приняты ревьюером. Если правило кажется неверным, неполным или противоречит движку — НЕ обходи его кодом: остановись и опиши противоречие с примером. Поведение продукта сам не выбирай.
- Отсутствующая возможность — типизированный отказ с адресом, не заглушка и не значение по умолчанию.
- Код движка, названный «как есть», не правится. Пробный код `PREPARATIONS/OM-DESIGN/proto/` — сценарии и контрпримеры ревью, а не код к переносу: он возвращался ревьюером 15 раз.
- Тесты: `node:test` + `node:assert/strict`, своя временная база на тест (образец — `test/storage.test.ts`), без настоящих вендоров, сети и ключей. `ui/` не трогать. push, слияния, теги — запрещены.
- Стиль движка: ESM, относительные импорты с суффиксом `.js`; `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noUnusedLocals`; файлы в kebab-case, без `index.ts`; типы экспортируются рядом с реализацией; комментарии редкие, на английском, объясняют «почему». Отказ движка — `EngineError(code, message, details)` из `src/errors.ts`. Факты о движке: `PREPARATIONS/OM-DESIGN/code/engine-facts-infra.md` и `engine-facts-reuse.md` — сверяй с кодом перед использованием.
- УРОКИ РЕВЬЮ СДЕЛАННЫХ ЗАДАЧ (классы дефектов, за которые код уже возвращали): (1) экспортируемая функция проверяет форму ВСЕХ аргументов до первого обращения к полям и до хранилища — отсутствует, null, не тот тип → `EngineError` с кодом дефекта единицы; обычный `TypeError` — дефект. Отсутствующий набор и явно пустой набор — разные случаи, отсутствующий на `[]` не подменяется. (2) JSON-содержимое копируется и отдаётся только через `sealed()` / `delivered()` из `src/om/refusal.ts`; своё копирование присваиванием по чужим ключам запрещено — ключ `__proto__` теряется и подменяет прототип; объект из чужих ключей строится через `Object.defineProperty` либо `Map`. Инвариант для теста: хэш выданного равен хэшу записи. (3) Точная ссылка доказывает, КАКУЮ запись прочитали, но не её принятие: основание принятия и связь с исходом ворот проверяет та единица, чья это обязанность. (4) Т3 буквально: производная запись сверяется с ЗАФИКСИРОВАННЫМ ИСТОЧНИКОМ — источник перечитывается по точной ссылке, производное выводится из него заново той же функцией и сравнивается; пересчёт хэша собственных полей записи — это самосогласованность, а не вывод заново (так вернули A2). Тест подделки меняет содержимое И пересчитывает id либо хэш; проверяется историческая ревизия источника по точной ссылке — новая голова источника старую запись ложной не делает. (5) Т5 буквально: запрос на переход НАЗЫВАЕТ состояние, из которого идёт (номер попытки, номер остановки, точную ревизию) — запоздавший повтор того же запроса после любых последующих событий распознаётся как уже применённый и на более позднее состояние не действует (так вернули A3: повтор продолжения снимал НОВУЮ остановку). Тест: запоздавший повтор после следующего события и после перезапуска базы. (6) Т6 буквально: НЕупорядоченные наборы (достижения, отмены, отказы, вопросы пакета, основания) нормализуются одной функцией перед записью И перед сравнением, сортировка не зависит от локали, кратность сохраняется; хранимая запись с неканоничным порядком — отказ. Тест: перестановка элементов — тот же исход без ревизии. (7) Передача соседу несёт ОДНОЗНАЧНУЮ сохранённую связь с конкретной записью или строкой соседа (id либо точная ссылка), а не пару «название + цель»: два законных события с одинаковыми названием и целью обязаны оставаться различимыми. (8) Изменяющая операция отделяет ПОДГОТОВКУ (все проверки → готовые записи и охраны, без записи) от ЗАПИСИ: соседняя единица, которой по правилам нужна ОДНА транзакция на несколько записей, включает подготовленное в свой writeGuarded, а не вызывает операции по очереди (частичный результат) и не переписывает твою логику. (9) Каждый исход, который правило называет (например «разбор завершён без пригодного изменения — ступень 2»), — это ПРИМЕНЯЕМЫЙ переход, сохранённый в истории записи, а не только отказ: отказ ничего не сохраняет, и следующий запрос проходит так, будто исхода не было (так вернули A3.1). Проверь по правилам своей единицы: у каждого названного исхода есть операция, которая его записывает, и тест, что после него запрещённое остаётся запрещённым — в том числе после перезапуска и у преемника. (10) Если сосед по правилам пишет свою запись В ТОЙ ЖЕ транзакции, что твой переход (основание, разбор, решение, подтверждение), подготовка принимает основание в двух видах — уже записанное (точная ссылка) и готовящееся в этой транзакции (предлагаемая запись: подготовка сама вычисляет её точную ссылку, проверяет её ТОЙ ЖЕ функцией содержания и включает в возвращаемый набор записей). Подготовка, которая умеет только читать основание из хранилища, вынуждает соседа коммитить его отдельно — и открывает окно (так второй раз вернули A3.1). (11) Ничто, от чего зависит продвижение, класс или маршрут, не принимается со слов вызывающего: достижение, отмену, принятость выводит ПОСТАВЩИК из своей записи по точной ссылке (таблица поставщиков принятия `src/om/achievements.ts`); вида, которого нет в таблице, — отказ, а не «поверим». (12) Положительный вывод требует ДОСТАТОЧНЫХ РАЗЛИЧАЮЩИХ оснований: не хватает обязательной роли либо кандидатов несколько без различающего основания — «неизвестно», а не первый по порядку и не «последняя ветка по умолчанию»; устойчивая сортировка выбор первого не обосновывает (так вернули A4). (13) Перед сдачей убедись, что новые тесты ЛОВЯТ дефект: временно верни ошибочное поведение в `dist/` (не в исходниках), увидь падение теста, затем пересобери. (14) ОДИН класс — ОДИН механизм установления: если обычный путь ВЫВОДИТ класс, маршрут или статус из источников (таблица решений над прочитанными записями), то любой второй путь к тому же результату (снятие преграды, разбор, повтор, восстановление) обязан звать ТУ ЖЕ выводящую функцию над теми же прочитанными источниками; поле `class` чужой записи — заявление, которое сверяется с выводом, а не заменяет его: противоречие или недостаточность → отказ без записи (так второй раз вернули A4: `weighLift` принимал класс из разбора по форме ссылок, не читая содержимое). Тест: основания, из которых таблица выводит другой класс либо «неизвестно», преграду не снимают — ни сохранённым, ни готовящимся разбором; ни снятия, ни записи разбора в базе после отказа нет. (15) ИСТОРИЯ и ГОЛОВЫ — разные вещи: историческое основание (запись, по точной ссылке на которую серия уже перешла) проверяется по точной ссылке и новой ревизией не отменяется; в охраны транзакции (guards) идут ТОЛЬКО изменяемые головы, от которых зависит актуальность результата, — зато ВСЕ фактически прочитанные, включая те, что читает вызванный сосед (например, снятые преграды в stopContext): нет сведений о прочитанном у соседа — расширь его интерфейс, а не охраняй меньше (так вернули A5). Тест: законная новая ревизия исторического источника — отчёт стоит; изменение любой прочитанной головы между проверкой и записью — отказ записи. (16) Позднейшее событие само по себе НЕ доказывает неудачу прежнего средства: «следующая остановка после продолжения» не значит «продолжение не помогло», если между ними записан принятый результат или граница окна; вывод о неудаче — только из сохранённых результатов и границ окон, с тестом на историю с наследованием (так вернули A5). (17) Точная ссылка НЕ заменяет ни проверку ПРИНАДЛЕЖНОСТИ, ни СОДЕРЖАНИЕ: читая чужую запись как источник объяснения или основания, сверяй ВСЕ поля адреса, включая цели/предмет (подделка с верными пространством имён, видом, ревизией и хэшем, но другими целями — отказ), и передавай получателю содержание относящихся строк (код, цель, предмет, происхождение, записанный способ исправления, класс, адресат) с однозначной связью с источником, а не только хэш и ссылку (так вернули A5). (18) СОСТОЯНИЕ ≠ ИСТОРИЯ: текущее состояние соседа (лестница, окна, цели стоящей остановки) — не полная история его событий; сведения, которых в состоянии нет (цели уже отвеченной остановки, границы прежних окон после сброса), НЕ заменяются приближённой проверкой («все цели когда-то встречались») и не пересчитываются вторым алгоритмом — их отдаёт ОДИН точный источник: сосед выводит историю тем же выводом, которым строит и проверяет состояние, и отдаёт её интерфейсом (расширение интерфейса соседа — стык реализации, не правило продукта). Тест: потерянная цель, лишняя цель из другого окна, чужая цель — отказ; перестановка — успех; после сброса лестницы промежуточная остановка не теряется и результат приписывается своему окну (так второй раз вернули A5). (19) ПОЛНОТА НАБОРА проверяется по сохранённым ИСТОЧНИКАМ, а не по перечислению самого набора: реестр/ведомость/список, который выводит каждую свою строку из записей, обязан также доказать, что в нём есть строка для КАЖДОЙ записи-источника (перечисление источников по пространству имён или по хранимому индексу), иначе строку можно удалить новой ревизией и все пути пройдут (так вернули E1). Тест: частичная и полная потеря набора, включая уже закрытую запись, на КАЖДОМ пути, обращающемся к другой записи, а не к потерянной. (20) ЗАЯВЛЕННЫЙ ПОТРЕБИТЕЛЬ — ПРОВЕРЕННЫЙ ПУТЬ: если пакет называет соседа потребителем твоего интерфейса, напиши тест, который проходит ЕГО путь через законные операции (например, обращение к ревьюеру при сохранённой остановке, когда следующая попытка запрещена), а не только «обычный» путь; интерфейс, до которого потребитель не может дойти, — дефект (так вернули E1). (21) ДОПУСК ТЕКУЩЕЙ ПОДГОТОВКИ ≠ ИСТОРИЧЕСКОЕ ЧТЕНИЕ: перечитывание уже сохранённой записи проверяет источники по точным ссылкам как историю; подготовка НОВОЙ записи или её использование в транзакции соседа обязаны проверить ТЕКУЩУЮ актуальность оснований по семантике движка (например, принятость стадии: Pipeline.inspect считает стадию stale при сдвиге головы доказательства) и вернуть полное замыкание охран на эти изменяемые зависимости — в том числе когда запись уже существует и writes пуст. Это два разных пути; общий путь нельзя ни ослабить, ни ужесточить для обоих. Тест: сдвиг зависимости до подготовки, после подготовки перед общей записью, при повторном использовании; историческое чтение после сдвига и перезапуска остаётся успешным (так вернули B1). (22) ОТРИЦАТЕЛЬНЫЙ РЕЗУЛЬТАТ ПРОВЕРКИ ≠ ИСКЛЮЧЕНИЕ ЕЁ ИСПОЛНЕНИЯ: «данные не прошли» приходит из результата проверки (state/findings) и становится типизированным отказом; исключение при исполнении проверки (TypeError, EngineError чужого кода, сбой хранилища) передаётся выше без подмены — общий catch с запасной веткой «отказ производителю» запрещён. Предусмотренное исключение-дефект-данных преобразуется только по явному договору с его кодом. Тест: сбой в чтении посреди проверки сохраняет исходное исключение на всех публичных путях и не оставляет записей (так второй раз вернули B1). (23) САМОСОГЛАСОВАННОЕ ДОКАЗАТЕЛЬСТВО ≠ ПРИНЯТИЕ: proof, хэш которого совпадает с проекцией и который ссылается на верный верх, записать может любой — принятие слоя подтверждается по его НАСТОЯЩИМ сохранённым основаниям (источники исследования и вывод слоя у движка; точный принятый кандидат и исход своих ворот у OM) ОДНИМ общим механизмом для всех читателей. Тест: новая ревизия слоя с пересчитанной проекцией, хэшем и proof, но без исследования и принятия — отказ на всех публичных путях и уровнях (так вернули C2). (24) ПОЛНОТА КОНЦОВ ≠ СОХРАНЕНИЕ ПОТОКОВ: соответствие верхних и нижних связей проверяется ПОТОКАМИ целиком (производитель, порт, якорь, потребители) и взаимно однозначно — два верхних потока не сливаются в одну нижнюю привязку; законная кратность потребителей и произвольные имена нижних портов по записанному соответствию сохраняются. Тест меняет И нижний граф, И записанное соответствие с пересчётом хэшей (так вернули C2). (25) ИСПРАВЛЕНИЕ КЛАССА ОХВАТЫВАЕТ СОСЕДА: если твой механизм уже реализован у принятого соседа (та же проверка другой реализацией), класс закрывается ОДНИМ общим модулем, на который переводятся оба, — а не второй, «правильной» копией у себя; иначе два читателя расходятся на одном входе (так второй раз вернули C2). Тест: один и тот же изменённый вход через обоих читателей даёт одинаковый исход. (26) ПЕРВЫЙ ПРОХОД — ЗАКОННЫЙ ПУТЬ: сохраняемый интерфейс обязан работать от начального состояния (принятые стадии и L1, без L2/L3), а не только на полностью раскрытой фикстуре; если обязательный источник ещё не может существовать, он явно сообщает ПРОВЕРЯЕМЫЙ исход «ещё не возможен», выведенный из точных оснований текущей стадии, — не пустоту по умолчанию и не перехват любого отказа соседа; после появления основания этот исход не может скрыть настоящие данные. Тест — настоящий путь от начального состояния, затем появление источника (так вернули D1). (27) ГРАНИЦА ПОЛНОМОЧИЙ — ПО ИЗМЕНЕНИЮ, А НЕ ПО НАЛИЧИЮ: «эта задача не трогает уровень N» проверяется сравнением итога с ПРИНЯТЫМ определением (что изменилось, что исчезло), а не по тому, встречается ли уровень N во входящем объекте: неизменённое принятое содержимое другого уровня законно присутствует, а его отсутствие во входящем определении не должно его удалять. Учитывать и исчезнувшие ссылки, а не только новые (так вернули C4). (28) ЗАЩИЩАЕМОЕ = ЗАМЫКАНИЕ ЗАВИСИМОСТЕЙ: защищая объект, защищай и всё, во что его типизированные ссылки разрешаются (порт → контракт; результат/связь → артефакт → контракт и т. д.), по типизированным связям графа, а не поиском строк; равенство самого объекта ничего не доказывает, если его ссылки ведут в изменённые определения. Не замораживать при этом весь граф — законные изменения вне замыкания должны проходить (так второй раз вернули C4). (29) СОВПАДЕНИЕ ID ≠ СОХРАННОСТЬ СОДЕРЖАНИЯ; ЗАПИСАННОЕ ДОЛЖНО ЧИТАТЬСЯ: переносить прежнее (заполнение, привязку, ответ) по совпадению идентификатора нельзя — пригодность проверяется по правилам той единицы, что будет это читать (роль, контракт, артефакт, поток); непригодное уходит в историю, требование остаётся открытым. Результат подготовки обязан проходить те же проверки, что его последующее чтение: успешная запись, которую её собственные потребители отвергают, — дефект. Тест: запись → чтение всеми потребителями → повтор → перезапуск (так вернули C5). (30) СОВМЕСТНОСТЬ ОСНОВАНИЙ: несколько источников одного вывода должны принадлежать ОДНОЙ сборке/объекту — каждый сопоставляется с сохранёнными входами отказного объекта (точные предложения, база, уровень, контекст), а не проверяется только по отдельности; по отдельности верная запись другой сборки не годится. ЧТО ПРОВЕРЯЕТСЯ ДЕЙСТВУЮЩИМИ ПРОВЕРКАМИ ДВИЖКА (как есть): у артефакта один производитель на уровне; у пути один писатель либо упорядоченная цепочка передач владения; граница работы равна границе её операции; одна работа не совмещает роли с разными границами; обязательные виды проверок по границе работы (исход; для долговременного состояния — холодное чтение и перезапуск; для провайдера — безопасность) покрыты тестами; тест привязан к точке входа в объявленном коде работы; у теста связи есть контрфактическая проверка; внутренний пакет записи не выходит за запись работы; конец связи настоящей работы привязан к месту в коде.
```text
НОВЫЕ ПРАВИЛА — в движке их нет, это объявленное изменение:
  · ОДИН АРТЕФАКТ. Работа производит ровно один артефакт — свой исход; все связи уровня работ, где она производитель, несут его же. Несколько исходящих связей с ОДНИМ артефактом допустимы. Два разных артефакта у одной работы — дефект карты: нужны разные работы, соответствия каркаса при этом сохраняются; операция с несколькими артефактами раскрывается в несколько работ. Исторические квитанции из-за введения этого правила негодными не объявляются.
  · ОДНА ПРОВЕРЯЕМАЯ ОБЯЗАННОСТЬ. Одна работа — один исход, который проверяют её тесты. Виды проверок ОДНОГО исхода (исход, холодное чтение, перезапуск, безопасность провайдера) — не разные обязанности. Тест работы вправе покрывать её ВХОДЯЩИЕ связи: «при входе A получается B» — проверка условий собственного исхода, а не вторая обязанность (действующий валидатор такого запрета не содержит). Вторая обязанность — это обязанность ПРОИЗВЕСТИ другой результат или изменить состояние за своей границей; её видимая коду часть уже закрыта правилом «один артефакт» и действующей проверкой границы работы. Смысловую неделимость текста обязанности код не доказывает — это граница механической проверки, а не разрешение: отдельный отказ по этому правилу не выдаётся, пока не назван признак без ложных срабатываний.
  · ОГРАНИЧЕННАЯ ОБЛАСТЬ ЗАПИСИ. Только точные пути файлов — не каталоги и не шаблоны; перечень непуст; при исполнении запись остаётся ВНУТРИ объявленных путей (действующая проверка исполнения); менять каждый объявленный файл необязательно. Предела на ЧИСЛО путей нет (Т0).
  · ПАКЕТ ЗАДАЧИ ПОМЕЩАЕТСЯ. Полный контекст задачи ВМЕСТЕ с пакетом соседей проверяется против технической вместимости запроса исполнителя — той же величины и из того же источника, что использует исполнение. Не помещается — отказ, а не усечение: работа слишком крупна, её раскрытие пересматривается проектным решением.
  · ПРОБЕЛЫ РАБОТЫ. Отказ даёт блокирующий пробел БЕЗ РЕШЕНИЯ, чей потребитель — эта работа, её операция или блок. Пробел, решение которого проверяется в ЭТОМ кандидате, отказом не является: G5 проверяет его заполнение по точной связи «обязательство → предложение → кандидат», и только успешный исход G5 даёт принятию основание закрыть линию. Ни наличие предложения само по себе, ни заранее закрытая линия успехом не считаются.
Пакеты соседей — по правилам M7: ровно один на работу, равен выведенному заново, вход без источника задачу не пускает.
Выдаёт и хранит: исход проверки с хэшем кандидата и базовыми ссылками; принятие — одной транзакцией по правилам каркаса: граф, запись каркаса работ, статусы предложений.
Разрешённые изменения: никаких — ворота только проверяют.
Отказ и продолжение: каждое нарушение — адресный отказ с узлом и названием; предложения кандидата отклоняются; возврат через G7 в M5 и MC2 с отказами ПО ЭТОМУ узлу в пакете следующей попытки; остановка — по Т0.
Открытое: у правила «одна обязанность» нет собственного механического признака сверх «одного артефакта» и границы состояния — заявленный на уровне 1 отдельный отказ не вводится, пока такой признак не назван; единый источник величины вместимости для G5 и исполнения — сегодня это параметр команды исполнения, а не настройка среды.
```

### Уровень 2 · Правила · MC1 и MC2 · обращение к модели: пакет вопроса, форма ответа, проверка  `rules-mc`

```text
ЗАЧЕМ (слова владельца 21.09.2026): «Лечить нужно не потолком, а тем, что делает модель и как она это делает… чтобы было одно обращение к модели, и она спокойно на это ответила по делу, коротко, чётко — без мысли по древу».
ПРЕЖНЯЯ БОЛЕЗНЬ (по коду движка и аудиту 07.09.2026): вопрос охватывал целую область; каждый вызов получал «весь проект» — все требования, всю проекцию слоя, полные поля прежних стадий, историю восьми ходов (pilot-context.ts, research-context.ts, research-runner.ts); оценщик получал то же; цикл «план → до 16 чтений → сборка страницами → ответ → оценщик» крутился внутри одного хода. Действия «нужен источник», «нужно решение владельца», «пауза» в протоколе движка были, но в том сценарии R2 правила приёмки делали их бесполезными: записанный пробел давал отказ. Итог: 28 вызовов и 1 542 356 токенов на первый вопрос, принято 0.

ПАКЕТ ВОПРОСА — что уходит модели. Собирается КОДОМ под конкретный вопрос, по адресам, которые схема уже знает:
  · сам вопрос: цель, поле, вид знания, потребитель, что именно требуется в ответе и в какой форме;
  · для раскрытия узла (MC2): верхний узел (название, исход, граница, порты); его незаполненные обязательства; для каждого конца связи — связь, контракт и ВСЕ прочие концы этого потока (соседи) с узлами и портами; уже принятые нижние узлы этого узла; имена, занятые представителями;
  · для факта (MC1): известные адреса источников; требование к доказательству;
  · правила, по которым ответ будет проверяться, — названиями отказов;
  · при повторной попытке — отказы прошлой попытки ПО ЭТОМУ вопросу (коды и цели) и только они.
  В пакет НЕ входит: весь проект, все требования, полная проекция слоя, поля прежних стадий целиком, история ходов, чужие вопросы.
  ВМЕСТИМОСТЬ. Полный пакет проверяется строго до вызова, как контекст задачи у компилятора (boundedContext): обязательства молча не усекаются. Предел выражает ТЕХНИЧЕСКУЮ ВМЕСТИМОСТЬ одного запроса — сколько принимает модель и транспорт (в движке это физический предел запроса, physicalLimits.maxRequestChars) — и берётся из неё. Занижать его ради экономии нельзя: это был бы отменённый владельцем регулятор под другим именем.
  ЧАСТИ ВОПРОСА — когда узел целиком не помещается. Делит КОД, а не модель: по связям узла, в устойчивом порядке (по id связи); одна часть — обязательства одной или нескольких связей вместе с их соседями. В КАЖДУЮ часть входят: сам узел; перечень ВСЕХ его обязательств одной строкой каждое; нижние узлы, уже предложенные предыдущими частями (чтобы операции переиспользовались, а не дублировались). Ответ части — частичное предложение слоя на свои обязательства; оно может вводить узлы и ссылаться на узлы прежних частей. ТОЧКА ПРОВЕРКИ — одна: когда заполнены все обязательства узла, код собирает из частей ОДНО предложение узла; оно входит в общую сборку кандидата слоя, которую проверяют обычные ворота (правила M4); принимается только целое. Части, определившие один и тот же узел по-разному, — отказ «части противоречат», он возвращается в следующую попытку. Весь цикл по узлу — одна попытка (Т0).
  Не помещается даже часть по ОДНОЙ связи — адресная остановка «узел не раскрывается по частям»: это сигнал, что узел слишком крупен на уровне выше; маршрут — пересмотр верхнего слоя (проектное решение уровнем выше) либо владелец. Повторная сборка того же пакета не выполняется.
  ДОЧИТЫВАНИЕ. Дочитать модель может только КОНКРЕТНЫЙ адрес (действующие действия чтения и поиска по адресу); код отдаёт запрошенное, «дай всё» не выполняется. В каждом дозапросе форма ответа и обязательства повторяются. Дозапрос обязан назвать, КАКИХ сведений не хватает и по какому адресу они ожидаются; уже доставленное в этой попытке учитывается кодом. Повторный запрос того же неизменившегося источника без новых сведений завершает цикл адресным отказом (в движке — research_no_progress при повторном чтении): попытка завершена без результата. Это проверка СОДЕРЖАНИЯ действий, а не лимит чтений или токенов. Дозапросы — часть той же попытки; попытка оценивается по результату (Т0).

ФОРМА ОТВЕТА — задана заранее, проверяется по схеме вопроса (действующая проверка формы):
  · MC2, задание РАСКРЫТИЕ УЗЛА: предложение слоя на ЭТОТ узел (или его часть) — узлы, заполнения его обязательств (для работ — с портом и местом в коде), локальные связи, зависимые определения, явные замены с точной базой. Всё, что код умеет досчитать сам, модель не присылает (действующий досчёт: тесты работы по владельцу, реализуемые требования, входы объединений).
  · MC2, задание РЕШЕНИЕ О НЕДОСТАЮЩЕМ ПОЛЕ ВХОДА: на КАЖДЫЙ вопрос пакета отдельный результат {цель, поле, значение, основание}. Значение — только то, чего не хватает: для адресации вопроса — узел-потребитель и вид знания; для привязки контракта — id блоков; для границы — id узлов и участников; для критерия — вид проверки. Верхнего узла у такого задания может не быть вовсе — предложением слоя оно не является. Код проверяет: вопрос существует, id есть в карте, значение из допустимого перечня, ссылка строгая. Применение — принятый переход M5: заполняется только недостающее, уже известные поля производителя сохраняются, получается новая версия входа. Для АДРЕСАЦИИ сам содержательный вопрос остаётся открытым обязательством своего вида; заполненная привязка контракта, граница или вид проверки закрывают именно пробел ЭТОГО поля. Обязательное поле записи новой эры, отвергнутое воротами входа G1, этим маршрутом не обходится — оно возвращается производителю стадии.
  · MC1: значение поля и цитаты по адресам. ОСНОВАНИЕ вычисляет КОД из цитат (действующий расчёт с пределами доказательности: наблюдение репозитория / цитата намерения требует атрибуции / сообщённое — не доказательство исполнения).
  · Законные управляющие ответы (действующие действия протокола) — не провал формы, и у каждого свой определённый исход:
      «нужен такой-то источник» (адресно) → код доставляет адрес в ЭТУ ЖЕ попытку по правилу дочитывания; режим планирования, в который это действие переключало прежний обработчик, не используется;
      «нужно решение владельца» → попытка завершается исходом «ожидает владельца»: вопрос с причиной записывается владельцу с адресатом и потребителем; серия по этому вопросу ждёт ответа. Это сохранённое ожидание, а не остановка по Т0 и не попытка без продвижения; но и НЕ продвижение: накопленный счёт попыток без продвижения оно не обнуляет. Причина обращения и недостающее решение видны владельцу. Ответ владельца возвращает вопрос в работу, но утверждение о репозитории доказанным фактом не делает — проверка по виду знания сохраняется;
      «ответить не могу — почему» или пауза → попытка завершена без результата (Т0); названная причина входит в пакет следующей попытки и в объяснение владельцу при остановке.
    Выдумывать модели незачем.
  · Рассуждение вне формы результатом не считается и никуда не сохраняется как основание.

ПРОВЕРКА — сначала код, потом (только для MC1) независимая оценка:
  1. форма ответа; 2. актуальность базы; 3. детерминированные проверки — по заданию:
     · MC2, раскрытие узла — предложение проходит каркас и действующие проверки графа и слоя (G3, G5) в составе собранного кандидата слоя;
     · MC2, решение о поле входа — по договору соответствующего пробела: значение допустимо (id есть в карте, перечень соблюдён), известные сведения производителя сохранены; затем решение применяется к новой версии входа. Сборка кандидата слоя к этому заданию не относится;
     · MC1 — адреса цитат разрешаются, значение подходит полю.
  4. MC1: независимый оценщик — другая роль, совпадение с исполнителем запрещено (действующее правило); вердикт supported | insufficient | conflicting; принимается только supported. Оценщик получает вопрос, ответ и основания-цитаты — НЕ весь проект и не все наблюдения. Оплачивается только после прохождения шагов 1–3.
  5. MC2: оценщика-модели нет — проектное решение проверяет код; принятие — по правилам каркаса и G4b (предложение работ допускается к сборке, принимается после M7 и G5).
  Роли планировщика чтения и отдельного читателя НЕ вводятся — это ВЫБРАННАЯ КОНСТРУКЦИЯ в направлении цели владельца («одно обращение… ответила по делу»), а не его дословное предписание: исследователь отвечает по пакету, чтение — по адресам, оценка — отдельной ролью. Ровно одного физического вызова схема не обещает: остаются дочитывание по адресам и оценщик.

КУДА ИДЁТ ПРИНЯТЫЙ ОТВЕТ-ФАКТ (MC1)
  Фиксирует шаг принятия (код), одной транзакцией: запись принятого ответа {обязательство: цель и поле; ОТПЕЧАТОК ДОГОВОРА ВОПРОСА — что устанавливается, потребитель, существенные требования, форма результата; версия входа, при которой задан вопрос; значение; основания — точные ссылки на источники и их состояние, вычисленные кодом из цитат; ссылка на оценку с вердиктом supported и оценщиком}. Способ вычисления отпечатка — детализация модуля. Образец в движке — принятие исследованного ответа (Discovery.researched и связывание ответа с вопросом и полем).
  Находит M6 при следующем проходе — по обязательству, с проверкой применимости: тот же договор вопроса И те же текущие источники (правила M6).
  Получает и использует тот механизм, который породил пробел: пробел входа — сборка входа F1.1 подставляет значение в НЕДОСТАЮЩЕЕ поле (известные поля не трогает) и даёт новую версию входа; факт, нужный проектному вопросу, — входит в пакет вопроса MC2 как известный факт со ссылкой на основание; факт для проверки реализуемости — M8.
  Основание закрытия линии M5 «заполнено» выдаёт тот же шаг принятия: ссылка на принятый ответ, связанная с линией и полем. Неприменимый ответ линию не закрывает.

ЧТО ХРАНИТСЯ: запись вызова (действующая: отпечаток запроса, ответ, расход четырьмя полями, статус, время) с привязкой к попытке, серии и пробелам; ответ MC1 (значение, основания, вердикт оценщика); предложение слоя MC2. Модель сама ничего не меняет: все режимы, кроме исполнения задач, только читают.
ОТКАЗ И ПРОДОЛЖЕНИЕ: ответ не по форме, не на вопрос, с неразрешимыми адресами или отклонённый проверкой — попытка завершена без результата (Т0); отказы возвращаются модели в следующей попытке по этому вопросу; автоматического повтора того же запроса нет. Вердикт не supported — ответ не принят, пробел открыт. Остановка — по Т0: третья подряд попытка без продвижения; дальше — лестница после остановки (правила вызовов модели): разбор с независимым ревьюером, затем владелец.
```

## Карточки единиц карты — дословно

#### G5 · Ворота атомарности  `gate-atomic`
- **что проверяет:** Действующие проверки графа, слоя и семантики движка (как есть) плюс новые правила атомарности из решения владельца 12.09.2026: один артефакт у работы; точные пути записи без предела на их число; пакет задачи вместе с соседями помещается в техническую вместимость запроса исполнителя; у работы нет блокирующего пробела БЕЗ РЕШЕНИЯ (пробел, решение которого проверяется в этом кандидате, проверяется по связи «обязательство → предложение → кандидат»). Отдельной механической проверки «одной обязанности» нет: тест вправе покрывать входящие связи работы; смысловую неделимость код не доказывает. Пакеты соседей: ровно один на работу, равен выведенному заново, вход без источника задачу не пускает. Исход записывается с хэшем кандидата и базовыми ссылками; принятие меняет статус предложений работ. Правила — карточки «G5 · атомарность работы и пакет задачи» и «M7 · работы и соседи».
- **коды отказа:** Действующие: boundary_mismatch; realization_boundary_conflict; endpoint_code_missing; endpoint_code_foreign; layer_port_unbound; test_obligation_missing; connector_test_missing; test_entrypoint_unbound; counterfactual_missing; write_ownership_overlap; ownership_transfer_missing; work_packet_boundary; future_dependency_unanchored; multiple_producers. Новые: work_artifact_not_single; work_write_scope_unbounded; work_packet_over_capacity; work_blocking_gap_open. Соседи и доставка: packet_missing; packet_foreign; packet_duplicate; packet_neighbors_forged; neighbor_undelivered; neighbor_chain_broken; neighbor_chain_ambiguous; neighbor_contract_missing; available_basis_missing; available_basis_mismatch; available_basis_unresolved; available_basis_foreign; available_basis_stale; available_basis_ambiguous; ownership_predecessor_missing; horizon_execution_missing; horizon_producer_unrefined; proposal_node_reserved; sleeping_wake_test_missing; sleeping_anchor_underivable; work_port_unbound; frame_layer_drift; frame_rebase_required. НЕ ВВЕДЁН: work_responsibility_not_single.

## Карточки записей-соседей — дословно

#### пакет соседей работы (часть пакета контекста задачи)  `st-packets`
- **что хранит:** { work, neighbors[{ connector | control, artifact, contract{id, hash, external}, direction: reads | writes | receives | sends | requires, port, codeRef, neighbor{ work{id, title, outcome, represented?}, operation{…}, block{…}, port, codeRef }, returnsTo, delivery: in-plan | available | external | sleeping | undelivered, anchor?, wakeTest?, basis?, path?, condition? }], hash } — hash от neighbors; список упорядочен по хэшу записи, порядок обхода на него не влияет. Потребители: G5 (пересчитывает и сверяет), M9 → компилятор (taskContext.neighbors), исполнитель задачи. Ровно один пакет на работу: дубликат отклоняется до выбора пакета. Выданный пакет — КОПИЯ: его правка не меняет граф, из которого ворота выводят пакет заново.

#### Журнал отказов ворот  `store-refusals`
- **что хранит:** Каждый отказ: ворота, код, цель, что исправить, происхождение (название + этап + точное основание). Потребители: G7 — класс отказа по происхождению и возврат ответственному производителю (ошибка предложения → модель; ошибка входа → производитель данных, в том числе стадия-предшественник; ошибка вывода → производитель кода; неизвестно → остановка на разбор); объяснение остановки владельцу, которое собирает код. Вес и место блока в очереди отказы НЕ меняют (M3: очередь — только порядок); наличие вопросов влияет на то, к каким блокам идёт обращение, а не на их вес.

#### Записи OM в SQLite  `store-records`
- **что хранит:** om-input, horizon и om-horizon, series-transition, block-weight, call-record, gaps, answers, graph и graph-layer, feasibility — все с id/revision/hash; проекции только читают (инвариант). Состав каждой записи — в её карточке уровня 2; серии исправлений, ведомость расхода и журнал отказов — отдельные карточки.
