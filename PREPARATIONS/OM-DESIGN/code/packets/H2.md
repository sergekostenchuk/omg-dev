## Как работать

- Ты воркер блока OM движка OMG. Рабочая копия — твоя копия, названная в сообщении о выдаче (на точной базе из карточки). Основную копию `~/OMG`, базу `.omg/state.sqlite` и `live-source` не трогай и не читай на запись.
- Писать разрешено ТОЛЬКО в эти файлы: `src/product/commands.ts`, `src/product/engine.ts`, `test/om-commands.test.ts`. Нужен другой файл — остановись и сообщи: это отход от задачи, а не твоё решение.
- Источник истины — правила ниже. Они приняты ревьюером. Если правило кажется неверным, неполным или противоречит движку — НЕ обходи его кодом: остановись и опиши противоречие с примером. Поведение продукта сам не выбирай.
- Отсутствующая возможность — типизированный отказ с адресом, не заглушка и не значение по умолчанию.
- Код движка, названный «как есть», не правится. Пробный код `PREPARATIONS/OM-DESIGN/proto/` — сценарии и контрпримеры ревью, а не код к переносу: он возвращался ревьюером 15 раз.

Факты о движке: `PREPARATIONS/OM-DESIGN/code/engine-facts-infra.md` и `engine-facts-reuse.md` — сверяй с кодом перед использованием.

- Проверяй все предусмотренные отказы СВОЕЙ единицы и существенные стыки с соседями, а не внутренние отказы неизменённого движка. Правило отсутствия — для ОБЯЗАТЕЛЬНЫХ данных. Публичной команды у модуля ещё нет (до H2): граница — функции твоей единицы и записи, законно приходящие от соседей.
- Готово, когда: обязательные тесты написаны и зелёные; изменения НЕ закоммичены, а проиндексированы только в разрешённых путях (`git add <пути>`), рабочая копия равна индексу; на этих финальных байтах ОДИН раз запущен `npm run check:backend` и он зелёный целиком; если `om/module` ушёл вперёд — перед прогоном перенеси работу на актуальный `om/module` (этот прогон и есть проверка слияния). ## Карта рисков этой задачи — обязательные регрессии

Выведена кодом из путей, чтений и цели задачи. В отчёте по КАЖДОМУ пункту — имя теста, который его закрывает, либо одна фраза, почему класс здесь неприменим.

- **ЭРА ВЫВОДА (урок 41).** Ты меняешь файлы, которые уже выводят или проверяют сохранённые записи: `src/product/commands.ts`, `src/product/engine.ts`. Регрессия: код базы `f6c9ddd035cb` (загруженный из Git целиком, отдельный процесс) пишет свои записи → новый код читает их после перезапуска с тем же результатом. Если вывод меняется — маркер договора в новых записях, история по правилу своей эры, без перебора. Если это только выделение общего механизма — докажи неизменность вывода прежними тестами без правки их ожиданий.
- **ДВИЖОК.** Прежние тесты движка — без правки ожиданий; прежние записи движка читаются своими правилами; новое обязательное основание задним числом не вводится.
- **ЧТЕНИЕ НЕ СЛАБЕЕ ЗАПИСИ (урок 45, решение владельца 26.09.2026).** Обязателен, если задача вводит читателя, потребителя, исторический путь, повтор, возобновление, поставщика или вторую проверку поверх сохранённой записи — своей или другого производителя. Признаки стыка: новый код на записях прежнего производителя; производная запись над источниками (журнал, ведомость, индекс, серия); флаг current/historical или отдельный путь истории/повтора; вторая реализация проверки того же договора; физический или облегчённый читатель либо код отказа как положительное доказательство; ветвь эры по наличию поля; основание из нескольких точных ссылок разных производителей. Каждый такой путь принимает только то, что законный производитель этой эры мог записать: запись заново выводится из её точных источников ТЕМ ЖЕ общим читателем, что у производителя (одна реализация, включая совместность оснований и обязательные поля эры); форма, хэш, Ref, kind, наличие поля, код отказа и местные копии правил доказательством не являются. Регрессия на каждый вид читаемой записи: в отдельном временном Store — изменённая копия настоящей записи с пересчитанным hash/id под точным Ref (подмена содержания; удаление каждого обязательного поля; противоречивое сочетание полей; подлинная часть другого среза) → типизированный отказ ДО записи (без новых ревизий и сдвига голов) и при историческом чтении, в том числе после переоткрытия Store; контроль — законная запись и история прежней эры читаются. Мутация: в общем читателе заменить повторный вывод на успех после сверки хэша с Ref — регрессии обязаны упасть. В отчёте — таблица «запись · производитель · общий ВЫВОД · тест» по ВСЕМ читаемым сохранённым записям: в клетке «общий вывод» — функция, которая ЗАНОВО строит тело записи (включая все производные поля: результат, offset/cursor, счётчики, состояние) из точного исходного состояния и источников и используется И производителем, И историческим читателем; клетка, где указана лишь проверка вида, формы, привязок, hash или Ref, считается НЕЗАПОЛНЕННОЙ (так вернули D8.4, №1235-1: result/offset синтеза проверялись формой). Пустая или незаполненная клетка — сдача не принимается.
- **ФОРМАТЫ СВОИХ ЗАПИСЕЙ OM (решение владельца 28.09.2026, ответ ревьюера №1636).** Пока у блока OM нет живых данных (в настоящих базах записей OM ноль), собственный формат записи OM меняется НА МЕСТЕ: одна действующая схема под одним именем контракта — без второй версии рядом, без веток выпуска и чтения прежней схемы разработки, без тестов «новый код воспроизводит старые байты». Производителя и всех его потребителей в путях задачи меняй согласованно; прежние фикстуры и ожидаемые хэши переводи на действующий производитель с сохранением проверяемого поведения и перечисли в отчёте как изменённые ожидания; потребитель вне путей — вопрос до кода. НЕ относится к: записям общего движка вне OM (исследование, опрос, model-call, runtime — реальные данные в базе); действующим предметным вариантам (пакет works-v1 и om-packet/v3; режим legacy серии до первой активации); неизменяемости сохранённой ревизии (новое состояние — новая ревизия); чтению завершённого по сохранённым ссылкам. Отдельную чистку принятого кода не делай. С первыми живыми данными OM правило для них перестаёт действовать.
- **ПОДДЕЛКА СОБСТВЕННЫХ ЗАПИСЕЙ — НЕ ДЕЛАТЬ (решение владельца 28.09.2026, ответ ревьюера №1661).** Живой прогон ведёт один оператор: отдельные матрицы тестов и проверки против РУЧНОЙ подделки или порчи собственной локальной базы (пересчитанный хэш, подменённое поле своей записи, искусственная classification) не делать.   Места: соответствие «обязательство → конец связи» в каркасах операций и работ; адрес соседа в пакете задачи; основание готовности блока (M2 → M7); адресация вопроса (M5).

```text
Т2. Отношения между узлами — действующая семантика движка, а не приближение. Уточнение = вложенность ИЛИ явное «реализует» (RefinementRelations). Необходимые предшественники = связи данных + requires + передачи владения (controlPredecessors). Годность квитанции — формула компилятора. Владение путём — правила writeGrants.
  Места: замыкание горизонта; принадлежность заполнения верхнему узлу; зона работ; план исполнения; адрес соседа; сверка доставки.

Т3. Производная запись проверяется повторным выводом из зафиксированных источников, а не по собственным полям.
  Места: набор пробелов (G4, G4b); пакеты соседей (G5); кандидат слоя — принимается только граф из записи кандидата (G3, G5).

Т4. Отсутствие — типизированный отказ с адресом. Нет обязательного источника, поля или набора — отказ; значений по умолчанию у обязательного нет; «пусто» передаётся явно.
  Места: вход M1 (правило эры: в записи прежней эры отсутствие структурированного поля — адресный пробел, в новой — отказ производителю стадии); готовность блока в горизонте; источники M5; аргументы всех ворот.

Т5. Переход состояния проверяет, из какого состояния идёт. Повтор того же — без изменений; противоречащее — отказ; запоздавшее не отменяет более позднего.
  Места: принятие кандидата; переход каркаса на новую базу; адресация вопроса; закрытие линии пробела; переход серий; закрытие вызова модели; учёт исхода попытки.

Т6. Порядок записей ничего не решает, кратность доезжает до потребителя.
  Места: несколько привязок одной связи (потоки); несколько потребителей; работа, уточняющая несколько операций; адреса внешних входов; ровно один пакет на работу.

Т7. Проверка и запись — одна транзакция с охраной по точным ссылкам; окна между «проверил» и «записал» нет.
  Места: учёт вызова в ведомости (запись и однократное закрытие); принятие кандидата (граф + каркас + статусы предложений); переход серий; переход каркаса на новую базу.

Т8. Отказ адресный и с маршрутом: что именно, у какого узла, кому возвращается — производителю данных, в пробел M5, владельцу, на пересмотр готовности в M2. Сам отказ ничего не переключает: не разрешает повторное исполнение, не меняет готовность, не открывает новую попытку. Обратные пути идут через G7.

Т9. Каждый пробел заполняется (решение владельца 21.09.2026). Отложенное не теряется и не закрывается без основания; нужное текущей сборке не переносится строкой результата; вес блока — только очередь.
  Места: отсрочка и линии в M5; G4b; M3.

Т10. Продуктовый выбор в коде не делается. Если для исправления надо выбрать СМЫСЛ ограничения (что считать продвижением, что считать несоразмерным расходом, замена адресации, аварийная защита бюджета) — это карточка решения владельца; до решения действует названное осторожное умолчание.

Т11. Политика неизменяема, выданное — копия. Таблицы правил не меняются во время работы; запись, отданная потребителю, не делит изменяемых объектов ни с политикой, ни с источником, из которого ворота выводят эталон. Это требование к модулю; решений схемы оно не меняет.
```

```text
Получает: принятые записи пяти стадий по точным ссылкам; инвентарь репозитория, если он есть.

Открытое: состав доказательства готовности у поставщика оснований — стык с M8.
```

### Уровень 2 · Правила · M3 · очередь блоков  `rules-m3`

```text
РЕШЕНИЕ ВЛАДЕЛЬЦА 21.09.2026: вес блока — ТОЛЬКО очерёдность. Каждый пробел заполняется; вес не даёт права проработать блок слабее. Потолки, доли бюджета и число попыток «по важности» отменены.
Получает: принятый верхний слой и запись горизонта — этого достаточно для первой очереди; позже — набор пробелов M5 после маршрутизации, чтобы выбрать из очереди блоки с вопросами.
Достоверное основание: структура принятого слоя блоков; политика веса с версией (заметка «Вес блоков»: три структурных признака — уникальные зависимые блоки, путь к результату, состояние и полномочия). Формулы веса в движке нет — это новое; готовая устойчивая сортировка в движке есть.
Выдаёт и хранит: запись очереди {порядок: [{блок, вес, место}], хэш горизонта, версия политики, явная перестановка владельца с причиной — если была}. Предохранителей (потолок вызова, потолок блока, лимит попыток) в записи НЕТ — они отменены.
Правила:
  · Порядок: тяжёлые блоки раньше; при равном весе — по id блока, чтобы порядок воспроизводился. Блоки, исключённые владельцем, в очередь не входят — это решено в M2, M3 сам ничего не отсеивает.
  · ДВА ПРИМЕНЕНИЯ одной очереди. Базовая очередь строится ДО раскрытия операций (M4) — только по слою и горизонту; набор пробелов её обязательным условием не является. После M5 и M6 из неё выбираются блоки, у которых есть вопросы: пробелы решают, ВХОДИТ ли блок в очередь вопросов, но не его место.
  · На что очередь ВЛИЯЕТ: в каком порядке блок OM берёт блоки горизонта в работу — раскрытие операций, затем вопросы к модели. Отдельного правила «производитель раньше потребителя» нет: предложение потребителя опирается на известный верхний контракт, согласованность нижних концов проверяется при сборке целого.
  · На что очередь НЕ влияет: глубина проработки, число попыток, расход, приёмка кандидата (принимается собранное целое), закрытие пробелов, остановка (Т0).
  · Пересчёт: новая запись горизонта — новая очередь. Смена места блока не начинает его работу заново, не сбрасывает историю серий и не открывает новых попыток.
  · Перестановка владельцем — явная запись с причиной; она меняет порядок и больше ничего.
Разрешённые изменения: только новая запись очереди; граф и пробелы M3 не меняет.
Отказ и продолжение: ворот нет — значения журналируются; нет записи горизонта или принятого слоя — отказ по Т4.
Открытое: на порядок ЗАДАЧ у компилятора очередь блоков не влияет — там порядок задают зависимости, при равенстве он устойчив. Этого достаточно для выхода к компилятору; влияние очереди на исполнение — отдельное решение, если оно понадобится.
```

### Уровень 2 · Правила · G7 · ворота повтора: класс отказа, попытки, продвижение, остановка  `rules-g7`

```text
Стоит на ВСЕХ обратных путях: отказ проверки слоя операций (G3), отказ атомарности (G5), отказ компилятора по карте, отказ реализуемости, оказавшийся дефектом карты, отказы по основаниям готовности.
Получает: исход завершённой попытки — её заранее названную цель и набор отказов (названия и цели); историю серии блока и среза; линии пробелов M5.
Достоверное основание: исход учитывается по записи попытки и записи кандидата, а не по словам модели; продвижение — только НОВЫЙ принятый результат (правила вызовов модели, Т0).
Правила:
  · КЛАСС ОТКАЗА определяется не одним названием, а ПРОИСХОЖДЕНИЕМ: название отказа + этап, на котором он возник + точное основание, которое различает три случая:
      ошибка ПРЕДЛОЖЕНИЯ — негодное или недостающее определение находится в самом предложении модели → проектный отказ: в M5 и MC2 с отказами ПО ЭТОМУ узлу;
      ошибка ВХОДА — негодна принятая запись производителя (стадия, верхний слой, каркас) → ответственному производителю данных через журнал отказов;
      ошибка ВЫВОДА — определение было в принятой базе или в полном предложении, но потеряно или искажено сборкой кандидата, выводом пакетов или другим кодом блока → производителю этого кода; в проектный вопрос модели НЕ идёт.
    Пример: «артефакт отсутствует» в собранном графе. Определения нет в новом предложении — исправляется предложение. Оно было в принятой базе или в предложении и потеряно сборщиком — исправляется сборщик: модель не должна компенсировать его ошибку. Происхождение проверяется механически: отказной объект сверяется с предложением и с принятой базой.
      Ещё два класса по этапу: условия (репозиторий, среда, исполнитель — из проверки реализуемости) → владельцу или среде; готовность (основание не годится, устарело, не названо; результат «есть», а настоящей работы нет) → пересмотр готовности в M2: исправить основание либо снять признак готовности решением. Сам отказ ничего не переключает (Т8).
    НЕИЗВЕСТНЫЙ или НЕОДНОЗНАЧНЫЙ отказ — происхождение не установлено → сохранённая остановка с адресом для разбора; проектный вопрос автоматически НЕ назначается.
    СМЕШАННЫЙ набор: каждый отказ получает свой класс и свой маршрут; ни один не теряется за выбранным «главным»; отказы входа и вывода модели вместе с проектными не передаются.
  · ПОПЫТКА И ПРОДВИЖЕНИЕ — по принятым правилам Т0: попытка — завершённый цикл по заранее названной цели, исход учитывается один раз; повтор доставки и промежуточные шаги попыткой не считаются; продвижение обнуляет счёт попыток без продвижения, отсутствие продвижения увеличивает его на один. Новые отметки времени, ревизии и id того же пробела продвижением не являются; цикл без обращения к модели, вернувший тот же отказ, — тоже попытка без продвижения. ПРЕРВАННАЯ ПОПЫТКА: «прервана» — это ПРИЧИНА ЗАВЕРШЕНИЯ, а не вывод о продвижении. После перезапуска сначала восстанавливается исход ТОЙ ЖЕ попытки: потерянное уведомление и повторная доставка новой попытки не создают и принятый результат не отменяют. Продвижение определяется по сохранённым принятым результатам цели: есть новый принятый результат (например, по одному из вопросов пакета до сбоя) — действует обычное правило, счёт обнуляется; нет — завершённая прерванная попытка увеличивает счёт на один.
  · ОСТАНОВКА: третья подряд попытка без продвижения → сохранённая остановка с причиной и точкой продолжения, затем ЛЕСТНИЦА ПОСЛЕ ОСТАНОВКИ (правила вызовов модели): ступень 1 — разбор причины с независимым ревьюером, ступень 2 — ВЫЗОВ ВЛАДЕЛЬЦА. КОНТЕКСТ ОСТАНОВКИ собирает КОД из записей попыток, модель для его сборки не вызывается: какие цели ставились; какие результаты приняты; какие отказы повторяются; АДРЕС конкретного препятствия и ОТВЕТСТВЕННЫЙ по классу отказа; причины завершения попыток; основание предлагаемого изменения. Если остановку вызвали сбои, объяснение и адресат говорят о сбое СРЕДЫ, а не о неудачной конструкции продукта. Причина не установлена — так и пишется, с известными фактами; причина, названная моделью («ответить не могу — почему»), остаётся версией, а не фактом. Один и тот же контекст получает ревьюер на первой ступени и владелец на второй (владельцу — вместе с записью разбора и тем, почему он не помог). Перезапуск остановку не снимает; продолжение — только по основанию своей ступени: запись разбора с ревьюером либо подтверждённое исправление входа — на первой; решение владельца — на второй и на любой. Состояние лестницы — какие окна были, использована ли первая ступень, требуется ли решение владельца — хранится в серии и переживает преемника и смену среза.
  · Лимита ЧИСЛА попыток нет; «ожидает владельца» — не попытка без продвижения и не продвижение (счёт не обнуляет).
Выдаёт и хранит: в серии — исход попытки, счёт попыток без продвижения, состояние остановки; в журнале отказов — отказ с классом и адресатом.
Разрешённые изменения: G7 не меняет граф, вход, готовность и пробелы — только серию и журнал отказов.
Отказы самого G7: «остановка без продвижения»; «отказ не исправим средствами блока» (уходит владельцу); «отказ передан производителю». Прежние «лимит серии исчерпан» и «состояние не изменилось» — история: первое отменено владельцем, второе теперь частный случай попытки без продвижения.
Открытое: нет.
```

## Карточки единиц карты — дословно

#### goal-om  `goal-om`
- **цель:** Из принятых замысла, дискавери, ТЗ и фич построить одну карту продукта и довести выбранный горизонт до глубины, на которой компилятор без участия модели выводит атомарные задачи с достаточным контекстом. Каждый элемент карты опирается на основание с происхождением. Вес блоков задаёт только порядок работы; работу регулирует продвижение к цели, а не потолки и счётчики: расход учитывается, но ответ не обрывает (редакция 21.09.2026, вечер, по решению владельца).
- **критерии успеха:** 1. Компилятор выдаёт задачи горизонта без ручного авторства. ⏎ 2. Пакет контекста каждой задачи помещается в техническую вместимость запроса исполнителя (это вместимость, а не экономия токенов). ⏎ 3. У каждого узла выбранного горизонта есть требование, потребитель и проверка; на L1 — исход и потребитель, без тестов (правило l1_detail_leak). ⏎ 4. Реализуемость выбранного горизонта подтверждена против конкретной версии репозитория и среды (id, revision, hash), какой бы подстадией это ни делалось. ⏎ 5. У каждого платного вызова модели есть адресный вопрос (пробел с потребителем) и запись учёта: расход по факту, однократное закрытие; вызова без адресного вопроса нет.
