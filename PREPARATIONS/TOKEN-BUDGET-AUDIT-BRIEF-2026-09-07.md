# Бриф: аудит резервов по токенам на проходе OMG по карте

Дата: 2026-09-07. Автор: Fable по поручению владельца. Основание: журнал 202 вызовов модели в `.omg/state.sqlite`, код на коммите `d88b89c`, схема прохода `PREPARATIONS/OMG-MAP-SCHEME/omg-map-scheme.html`, аудит R2 `PREPARATIONS/OMG-MAP-SCHEME/omg-r2-audit.html`.

## 1. Цель и мерка

Цель: сократить расход токенов на проход по карте без потери назначения OM: одна карта, факты только с доказательствами, независимая оценка, неизвестное не прячется, отказы типизированы.

Мерка растраты одна: **токен, который не оставил долговечного результата, который кто-то потребляет.** Каждый вызов модели относится к одному из четырёх классов:

| класс | признак |
|---|---|
| полезный | дал принятый факт, решение, чтение или вердикт |
| переделка | повтор после отказа кода или оценщика |
| справка | дозапрос контекста, который уже был или мог быть в пакете |
| петля | вызов без сдвига состояния |

Доля трёх последних классов и есть резерв. По журналу 202 вызовов это считается за час.

Что нельзя трогать:
- цитата на файл репозитория с хэшем как доказательство факта;
- разделение исполнителя и ревьюера;
- идентичность карты и привязка входов хэшами;
- запрет тихо закрывать неизвестное.

## 2. Разрезы аудита

### 2.1 Потребитель каждого ответа
Для каждого поля, которое просят у модели: кто его читает, код или модель, и что делает с ним.
Уже найдено: ответ `journey` стадии карты в коде не читает никто, он уходит только текстом в контекст модели следующей стадии как часть полей принятой стадии (уточнение Codex по блоку 1.1 принято); отчёты R2 компилятор не читает, они текст для одного вызова L3; поле `reason` не имеет машинного потребителя (у `applicability` он есть: research_report_empty и research_applicability_conflict; уточнение Codex по 2.1 принято). Всё без потребителя либо убирается, либо сокращается до того, что потребитель реально использует.

### 2.2 Состав пакета против действия
Для каждой роли: какие поля пакета нужны для действия, которое просят. Мерить долю пакета, побайтно совпадающую с предыдущим пакетом той же пары вопрос-роль.
Известные повторы: история с содержимым чтений на стадийном пути (до 37 097 знаков за чтение) повторялась в каждом пакете; каталог источников с выдержками по 3 000 знаков на каждый документ владельца в каждом вызове; полная JSON-схема графа в каждом вызове стадии карты; в R1 постоянная часть уходила в каждом из 99 вызовов аналитика до появления упаковщика.

### 2.3 Цена каждого отказа
По каждому отвергнутому ответу: класс причины (формат пути, тип ссылки, правило пробелов, «недостаточно» от оценщика, схема), сколько стоила переделка, было ли правило содержательно необходимо, позволял ли текст отказа исправиться за один вызов.
Известно: первый ответ стадии карты отвергнут из-за ссылки на принятую стадию вместо источника (`source_missing`); отказы R2 по пробелам повторяли слова модели и не называли правило, три круга; в R1 отвергнут 21 ответ из 71.

### 2.4 Петли и возвраты
Где число вызовов внутри одного шага ничем не ограничено, кроме бюджета.
Известно: 23 адресных запроса подряд в `integrations` на 1,33 млн токенов; 12 в R2 на 0,42 млн; пять возвратов в исследование в `evidenceAndTests`; два полных круга в `recovery`.
Проверять: есть ли ограничитель до отправки, помнит ли сессия выданные адреса, учитывается ли отказ валидатора как продвижение.

### 2.5 Вызовов на единицу результата по ролям
Доли в R1: аналитик 77%, читатель 12%, оценщик 8%, планировщик 3%. Единственная роль, добывающая новое, это читатель.
Считать: вызовов аналитика на один принятый факт по каждому вопросу; страниц оценщика на один вердикт; возможность переиспользовать чтения между вопросами (сейчас чтения привязаны к вопросу).

### 2.6 Контракт приёмки против достижимости
Обязательства, которые нельзя закрыть чтением: 9 из 33 требуют результатов запуска или сведений о среде, 1 требует живой базы. Правило пробелов на R2 отвергает любой пробел при пустом горизонте. Горизонт выбирается после R2.
Каждый такой пункт это токены, потраченные на невыполнимую цель; они больше любой оптимизации пакетов.

### 2.7 Гранулярность вопросов
Девять вопросов R1 с полной постоянной частью каждый, пересекающиеся области (`recovery`, `persistence`, `stateAndRecovery`, `runtime`). Тринадцать вопросов R2.
Проверять: что из этого нужно узлам ближайшего горизонта, а что для всей области.

### 2.8 Модели и режимы
Astra/high на каждом адресном запросе, где модель лишь просит следующий указатель. Кэш: в журнале есть `cachedInputTokens`, посчитать долю кэшированного входа; если постоянная часть не попадает в кэш провайдера, это отдельный резерв. Уровень усилия по ролям.

### 2.9 Наблюдаемость
Что нельзя аудировать, потому что не измерено: токены стадий до R1 (только знаки пакетов: discovery 1,42 млн, concept 0,73, operation-map 3,09, specification 1,25, features 0,89), пакеты оценщика на стадийном пути, сырые пакеты до коммита `d88b89c`. Без журнала на каждом вызове аудит невозможен; это первое требование к движку.

## 3. Метод

Порядок по блокам схемы: стадия карты → механизм R1 → девять вопросов R1 → L2 → механизм R2 → тринадцать вопросов R2 → L3 → компилятор.

На каждом блоке:
1. реестр вызовов из журнала с классом (полезный / переделка / справка / петля);
2. реестр отказов с ценой переделки;
3. состав пакета с долей повторов;
4. потребители каждого ответа.

Два правила от прежних ошибок:
- сначала считать по журналу, потом чинить, а не наоборот;
- не оптимизировать пакет там, где цель недостижима: там сначала контракт.

## 4. Формат результата

Каждый резерв записывается строкой:

| блок | механизм | доказательство из журнала | оценка экономии (токены, %) | что меняется | чем рискуем | цена правки |
|---|---|---|---|---|---|---|

Заявление «стало дешевле» принимается только с разницей по журналу, не по фикстуре: сухие прогоны доказывают форму, а не расход.

## 5. Порядок работы: по блокам, не одним проходом

Аудит идёт по стадиям и внутри стадии по блокам в нумерации схемы `PREPARATIONS/OMG-MAP-SCHEME/omg-map-scheme.html`:
1.1–1.6 (вход в карту), 2.0 (механизм R1), 2.1–2.9 (девять вопросов R1), 3.1 (слой L2), 4.0 (механизм R2), 4.1–4.13 (тринадцать вопросов R2), 5 (слой L3), 6.1–6.4 (R3 и компилятор).

Список блоков с номерами, именами и именами файлов записей — `PREPARATIONS/TOKEN-AUDIT/BLOCKS.json`, сгенерирован из атрибутов data-anchor схемы; идти строго по его порядку. По каждому блоку отдельная запись Codex в `PREPARATIONS/TOKEN-AUDIT/<file из BLOCKS.json>`, не раньше, чем закончен предыдущий блок. Записи вида «обзор стадии» (номера без точки) пишутся после всех блоков стадии. Состав записи фиксированный:
1. что блок получает и что отдаёт, кто потребитель каждого выхода;
2. реестр вызовов модели блока из журнала с классом каждого вызова (полезный / переделка / справка / петля) и итогом по классам в токенах;
3. реестр отказов с причиной, ценой переделки и суждением, было ли правило необходимо;
4. состав пакета с долей повторов относительно предыдущего пакета той же пары;
5. строки резервов в формате раздела 4, с оценкой экономии и риском;
6. что не удалось установить по базе и почему.

### 5.1 Оценка и переход (решение владельца от 07.09.2026)

- После записи блока Fable проверяет факты по журналу и коду и пишет вердикт в `PREPARATIONS/TOKEN-AUDIT/<номер блока>.verdict.md`: оценка из 10 и основания.
- Оценка **9/10 и выше — переход к следующему блоку автоматически**, без слова владельца.
- Оценка ниже 9: в вердикте аргументация по пунктам. Codex отвечает в том же файле записи блока, раздел «Обсуждение», раунд 1. Fable либо пересматривает оценку и пишет новую в вердикт, либо указывает, в чём ошибочность суждения. **Не больше трёх раундов.** Если за три раунда оценка не достигла 9, вопрос по блоку остаётся владельцу: Fable сообщает ему, обе стороны идут к следующему блоку.
- **Если нерешённых блоков подряд больше трёх, работа останавливается** до решения владельца.
- Вахты: Codex после заполнения записи блока ставит вахту на чтение файла вердикта с интервалом 1 минута; после решения по блоку снимает её и идёт дальше. Fable держит вахту на чат Codex ARCHITECTOR OMG и на папку `TOKEN-AUDIT`, докладывает владельцу ход работ и проверяет каждую запись.
- Общие выводы по стадии пишутся после всех её блоков, не вместо них.
- Это правило заменяет любое требование разрешения владельца перед каждым блоком; CODE FIRST не нарушается: ворота две, запись блока и вердикт, владелец подключается только к нерешённым блокам.

### 5.2 Форматы файлов

- Запись блока и вердикт — Markdown, для чтения людьми. Раунды обсуждения дописываются в запись блока в раздел «## Обсуждение», подзаголовки «### Раунд N — Codex» и «### Раунд N — Fable».
- Первая строка каждого вердикта фиксированная и машиночитаемая: `оценка: N/10 · раунд: K · статус: принят|обсуждение|владельцу`.
- Состояние всех блоков — `PREPARATIONS/TOKEN-AUDIT/STATE.json`, ведёт Fable. Вахта Codex читает только его:
  `{"blocks": {"1.1": {"grade": 9, "round": 1, "status": "принят", "verdict": "1.1.verdict.md", "updated": "2026-09-07T03:40:00+03:00"}}, "unresolvedInARow": 0, "stopped": false}`.
  Переход к следующему блоку разрешён, когда статус текущего `принят` или `владельцу`; при `stopped: true` работа стоит.
